# AIMS 项目审批栏渲染延迟

## 现象

- 项目设置页主体先出现，右侧审批栏长时间空白。
- 早期线上计时中，审批标题约 6.9 秒出现，真实操作内容约 9.8 秒出现。
- DevTools 显示单次进入设置页会在同一时刻产生 6 个 `instances/by-biz` 请求。

## 根因

1. `ProjectNavbar` 每次挂载都会并行查询立项、暂停、恢复、结项 4 类审批，且每个查询都携带全量历史。
2. 项目标题中的 `WorkflowBadge` 又单独查询一次立项审批，审批栏本身再查询一次，共 6 个同时请求，导致 Workflow Runtime 竞争。
3. `WorkflowPanel` 监听整个 `launchPayload` 对象。项目仓库、里程碑、立项书并行加载时会重建 payload，从而再次查询同一业务实例。
4. 右侧布局以“审批动作已计算完成”作为渲染条件，项目、角色和完整性数据未就绪时整个审批栏不存在。
5. Workflow 读请求原先还会等待无关全局 outbox 和项目总监补偿逻辑，已在第一阶段修复中移到受信定时任务。

## 修复

- 项目设置页不再执行导航栏的 4 动作全量补偿查询，也不再重复渲染独立流程徽标；其他项目页仍保留原有生命周期补偿能力。
- `WorkflowPanel` 只监听 `appCode/resourceCode/actionCode/bizId` 组成的稳定业务键，展示字段和完整性数据更新不再重复查询。
- 直接使用 `by-biz` 完整响应渲染实例，不再串行补查实例详情；历史记录改为后台异步加载。
- 页面一声明审批流程即渲染“项目审批 / 加载审批信息”占位栏，并用显式 `initializing` 状态覆盖项目权限和业务数据的整个初始化周期，中间不再闪空。
- Workflow Runtime 普通读不再排空无关 outbox，项目总监补偿仅限里程碑场景。

## 线上验证

- 修复前：同一导航周期在 `startTime ≈ 8.8s` 同时发起 6 个 `by-biz` 主查询，审批栏的立项主查询实测 4,781 ms。
- 修复后：只有 1 个立项主查询和 1 个非阻塞历史请求；主查询 1,828 ms，历史请求 1,500 ms。
- 审批主查询数下降 83%，主查询耗时下降约 62%。
- 外层 Shell 整页刷新时，审批占位栏在缓存/网络不同时约 3.3–6.6 秒出现，一旦出现会持续到真实审批内容替换，未再出现中途空白。
