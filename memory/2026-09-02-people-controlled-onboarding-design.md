# Design: People 受控员工入职编排

Generated by office-hours on 2026-09-02  
Status: REVISED DRAFT（已吸收 `2026-09-02-people-controlled-onboarding-design-review.md`）  
Mode: Intrapreneurship / Startup

## Problem Statement

当前钉钉 HR 同步在无法命中既有 Directory identity 或唯一邮箱时，会为员工生成确定性的 `dt-*` UID，并立即写入 `people_employees`、冻结 People → Console employment lifecycle。对于 LDAP 托管企业，如果钉钉首次快照缺少企业邮箱，而 LDAP 用户稍后以 `liukai` 一类 UID 创建，就会形成两个长期主体：People/DingTalk 使用 `dt-*`，LDAP/SSO 使用 `liukai`。

该问题不是单纯的用户名显示错误，而是员工业务主键、登录身份和授权主体发生分叉。直接修改 username、删除目录用户或依赖后续邮箱同步都不能安全恢复。

## Demand Evidence

- 生产同步后已经出现员工显示名和邮箱正确，但 canonical UID 为 `dt-*`，无法按企业 SSO 主体正常登录或继承授权的真实案例。
- 当前代码只在钉钉 identity 尚不存在时执行唯一邮箱匹配；一旦 `dt-*` identity 已建立，后续邮箱补齐不会触发重新归并。
- People 当前所有任职、成本、绩效、离职和跨应用生命周期记录均依赖非空 `employee_uid`，说明临时 UID 进入正式员工表后修复成本很高。

## Status Quo

现有链路：

```text
钉钉员工快照
  → Data Runtime 解析 Directory UID
  → 未匹配时生成 dt-* UID
  → People employee / assignment
  → People → Console employment operation
  → Directory user + DingTalk identity
  → Console → Platform subject / position role
```

现有能力可以复用：

- People 已有 employee/assignment、Workflow 入职确认语义和可靠 `integration_operation`。
- Console 已有 LDAP managed provisioning、重复创建检查、加密初始密码和可靠 Connector operation。
- Console employment lifecycle 已能幂等 upsert Directory user、绑定 DingTalk identity并投影 Platform。
- Platform 已能根据 People 主岗位映射系统角色，并撤销之前的岗位来源角色。

缺失能力：

- 正式 employee 之前的入职候选实体。
- UID/企业邮箱的受控预留与唯一性确认。
- LDAP 创建成功回执与 People 入职单之间的可靠关联。
- 已生成 `dt-*` 主体与 LDAP 主体之间的受控归并。
- 一份覆盖 People、Console、LDAP、Platform 的可见状态机。

## Target User & Narrowest Wedge

主要用户是 HR 管理员。其目标是在 People 的一个入职页面中完成资料确认、账号开通和结果跟踪，不需要理解 Connector、Directory identity 或跨应用 operation。

最窄可交付范围：只处理“钉钉新入职、LDAP 托管、正式员工”场景。调岗、离职、外包、返聘和历史批量归并继续沿现有流程或后续扩展。

## Premises

1. `employee_uid` 是正式员工进入业务链路后的全系统不可变 canonical UID；正式 `people_employees` 不接受空值或临时值。上线前遗留 `dt-*` 错误主体只能通过专用修复流程处理，并且必须先证明跨应用引用为零；该修复是唯一例外，不属于日常 UID 修改能力。
2. 钉钉入职事实可以先形成独立候选记录，不立即创建可登录账号或正式 employee。
3. LDAP、Directory、Platform subject 和 baseline 基础权限全部完成后，入职单才进入 `completed`；岗位角色没有匹配时产生管理员待办，但不阻塞普通员工入职完成。
4. People 拥有员工与任职事实；Console 拥有 UID、登录名、邮箱、LDAP/DingTalk identity 和账号状态；Platform 拥有角色与授权。
5. 跨模块步骤必须使用现有可靠 operation/receipt 模型，浏览器不能串联多个不可靠写请求。

## Approaches Considered

### A. 最小候选表 + 人工跨模块确认

钉钉只写候选表，HR 分别在 Console 和 Platform 操作，最后回 People 确认。

优点是改动小；缺点是步骤易遗漏、无法可靠确认 LDAP/授权结果，不满足最终体验目标。

### B. People 受控入职编排

People 维护入职单状态机，Console 承担 UID 预留和 LDAP 开通，Platform 消费现有 employment lifecycle 自动建立主体和基础岗位角色。所有步骤通过可靠 operation 和 receipt 串联。

该方案解决真实问题，并最大限度复用现有边界和基础设施。

### C. 引入独立 person_id，彻底解耦员工与登录身份

长期模型最完整，但会影响 People、Aims、Assets、Finance、通知和授权中的大量 `employee_uid` 契约，不适合作为本轮修复。

## Recommended Approach

采用方案 B。保留现有 canonical UID 跨模块模型，在正式员工之前增加独立入职单，并把账号创建和授权投影变成可恢复的系统编排。

评审后的关键取舍：

- 遗留 UID 归并采用“全应用引用扫描必须为零”策略，首期不引入 `directory_user_aliases`。用户别名无法自动修复各业务库已经持久化的精确 UID，容易把双主体永久化。
- LDAP 开通以前置改造“Console 生成随机初始密码并提供一次性激活/揭示凭据”为准，不允许 People 传递或保存明文密码。
- 干净的唯一邮箱匹配继续自动复用，不把全部存量员工推入人工冲突队列。
- `completed` 只要求基础登录与 baseline 权限成功；岗位角色缺失单独形成管理员待办。
- Platform 岗位自动授权必须新增高风险角色闸门，不能把现状当作已经安全。

## Domain Model

### `people_onboarding_cases`

建议核心字段：

| 字段 | 说明 |
| --- | --- |
| `onboarding_code` | People 内部稳定业务键，例如 `ONB-*` |
| `provider_code` | 首期固定 `dingtalk` |
| `provider_subject` | 钉钉用户唯一标识，仅作外部 identity，不作员工 UID |
| `source_revision` / `source_hash` | 钉钉快照版本和规范化摘要 |
| `candidate_name` | 钉钉权威姓名 |
| `planned_onboard_date` | 计划入职日期 |
| `canonical_uid` | UID 预留成功后写入；此前为空 |
| `employee_no` | People 工号；完成前必须唯一 |
| `corporate_email` | Console/LDAP 企业邮箱；完成前必须唯一 |
| `dept_code` | canonical Directory 部门编码 |
| `position_code` | People 岗位编码 |
| `rank_code` | People 职级编码 |
| `manager_uid` | 上级 canonical UID，可为空但需显式确认 |
| `source_onboard_date` | 钉钉下发的入职日期原值，只读，用于与 HR 确认值比对 |
| `mobile` | 钉钉下发手机号，仅用于开户与 Directory 落地，不作为 People 事实源 |
| `source_field_status` | 逐字段来源状态 JSON：`provided` / `empty` / `absent` / `invalid`，至少覆盖 `onboard_date`、`mobile`、`email`、`employee_no`。`empty` 与 `absent` 必须分开，前者是 provider 明确下发了空值，后者是根本没下发 |
| `manager_provider_subject` | 钉钉上级外部标识，只用于解析，不得转换为 `dt-*` UID |
| `manager_onboarding_code` | 上级也在入职中时的候选单引用，可为空 |
| `status` | 入职状态机 |
| `object_version` | 与 `people_offboarding_cases` 对齐的 CAS 版本，API 表达为 `vN` |
| `last_error_code` | 去敏、稳定错误码 |
| `created_by` / `updated_by` | 操作审计 |
| `completed_at` / `completed_by` | 完成终态审计 |
| `cancelled_at` / `cancelled_by` / `cancellation_reason` | 取消终态审计 |

唯一约束：

- `(provider_code, provider_subject)` 唯一，保证钉钉重放不重复建单。
- `canonical_uid` 非空时唯一。
- 同一未取消入职单的 `employee_no` 和 `corporate_email` 不得重复。
- 增加与离职单对称的终态 CHECK：`completed` 必须同时具备 `completed_at/by`；`cancelled` 必须具备 `cancelled_at/by/reason`；非对应终态不得伪造终态审计字段。

入职候选不是 employee，不参与员工列表默认统计、任职、成本、绩效、资产、项目成员或权限范围计算。

### Operation 关联

继续复用 `integration_operation`，不另建第二套投递账本。入职单保存以下 operation key 或通过业务键查询：

- `people.directory.identity-reserve.v1`
- `people.directory.user-provision.v1`
- 既有 `people.directory.employment-sync.v1`
- 既有 `console.platform.employment-sync.v1`

每条命令绑定 tenant、source/target deployment、`onboarding_code`、`object_version`、command hash 和原始 HR actor。

## State Machine

```text
awaiting_profile
  → ready_for_provisioning
  → reserving_identity
  → provisioning_account
  → activating_employee
  → projecting_authorization
  → completed
```

可恢复异常状态：

```text
profile_conflict
identity_conflict
reservation_expired
provisioning_failed
authorization_failed
```

终态：

```text
completed
cancelled
```

状态含义：

- `awaiting_profile`：钉钉事实已接收，尚未满足必填项。
- `ready_for_provisioning`：HR 已确认姓名、工号、UID、邮箱、部门、岗位、职级和入职日期。
- `reserving_identity`：Console 正在原子检查并预留 UID/邮箱。
- `provisioning_account`：LDAP Connector 正在创建账号；不得重复提交。
- `activating_employee`：LDAP/Directory 已成功，People 正在创建 employee 和首个 onboard assignment。
- `projecting_authorization`：Console/Platform 生命周期尚未完成。
- `completed`：Directory active、LDAP identity active、DingTalk identity 绑定到同一 UID、People employee active、Platform subject active，baseline 基础权限投影已得到成功回执。岗位角色未匹配时产生待办，不阻塞完成。
- `reservation_expired`：预留到期且 LDAP 尚未创建；释放旧预留后，以新 `object_version` 回到 `ready_for_provisioning`。

异常出口固定如下：

- `profile_conflict`：HR 修正资料并递增 `object_version` 后回到 `awaiting_profile`。
- `identity_conflict`：有权限管理员确认复用目标 UID后递增 `object_version`，回到 `ready_for_provisioning`；拒绝复用则回到 `awaiting_profile` 或取消。
- `provisioning_failed`：可重试错误复用冻结 command；资料性错误修正后递增版本并回到 `ready_for_provisioning`。
- `authorization_failed`：保持 Directory 和 People 已成功事实，回到 `projecting_authorization` 重试。

钉钉重复同步只更新允许由钉钉管理的候选字段。进入 `ready_for_provisioning` 后，如果姓名、入职日期或部门等关键事实变化，应使 HR 确认失效并回到 `awaiting_profile`；已经开通账号后则走员工资料变更，而不是重开入职单。

## Detailed Workflow

### 1. 钉钉发现新员工

Connector 提交员工快照。Data Runtime 按 DingTalk identity 查找：

- 已绑定正式 Directory UID：进入现有员工资料同步。
- 没有绑定且唯一邮箱干净命中一个 active Directory 用户，并且该用户没有其他 active DingTalk identity、来源不冲突：自动复用该 canonical UID。
- 唯一邮箱命中的用户已绑定其他 DingTalk identity、状态非 active，或来源/身份事实冲突：进入 `identity_conflict`，由有权限管理员处理。
- 邮箱命中多条：进入 `identity_conflict`，禁止自动选择。
- 没有绑定：创建或更新 onboarding case，状态 `awaiting_profile`。

这一阶段禁止生成 `dt-*` employee UID，禁止写 `people_employees`，禁止冻结 employment lifecycle。

经理解析遵守同一原则：只有经理已存在 canonical Directory identity 时才写 `manager_uid`。经理尚未落地时保存 `manager_provider_subject`，能够关联到对方候选单时写 `manager_onboarding_code`，否则进入待补办清单；禁止为经理合成 `dt-*` UID。

### 2. HR 完善资料

People 入职单页面展示：

- 钉钉只读事实：姓名、钉钉部门、入职日期、钉钉账号标识的脱敏摘要。
- HR 必填事实：员工编号、canonical 部门、岗位、职级、用工类型、经理。
- 账号字段：建议 UID、企业邮箱。
- 校验结果：UID、员工编号和邮箱是否可用，LDAP Connector 是否 ready。

UID 建议由企业规则自动产生，例如姓名拼音规则加冲突序号；HR 可以在预留前调整，但提交后不可随意修改。企业邮箱由 UID 和企业域规则生成，避免 UID 与邮箱分别手输后不一致。

### 3. Console 预留身份

People BFF 在校验 `onboarding:provision` 后，以固定 Console service capability `console:directory-identity:reserve` 和签名 actor command 调用身份预留接口。

Console 在一个事务中检查：

- UID 不存在且没有活动预留。
- username/邮箱在 Directory 与未完成预留中唯一。
- 不存在同一 DingTalk subject 指向其他 UID。
- LDAP managed 且 Connector ready。

成功后返回带有效期的 reservation receipt。预留只阻止冲突，不创建 active Directory 用户，也不投影 Platform。

### 4. 创建 LDAP 账号

People 以 reservation 调用 Console；Console 复用现有 `console.directory-connector.create-user.v1` 可靠 operation。

安全要求：

- People 数据库、operation command 和日志不得保存明文初始密码。
- Console 契约已改造（已实现）：`initialPassword` 变为可选。缺省时由 Console 就地生成 20 位、四类字符齐备、排除易混字符的随机密码，只在内存中用 Connector 公钥加密进 operation command。
- 明文只出现在本次创建响应中一次，服务端不做任何可读留存：`console_mutation_receipts.result_json` 持久化的是不含明文的 `result`，明文只加在返回给调用方的副本上。因此用同一 `Idempotency-Key` 重放只会拿到不含密码的结果，不存在“反复取回初始密码”的路径。
- 该实现比“存一次性凭据 hash”更强：没有任何可揭示的服务端状态需要保护或过期。
- 自助改密不适用生成逻辑：缺少 `newPassword` 仍然报错，不得替用户生成一个他不知道的密码。
- People 只持有 provisioning operation/receipt，不接收初始密码、密文或揭示凭据。
- 同一 UID 存在 pending/processing operation 时返回既有 operation，不再次创建。

**凭据交付路径已定案并实现：一次性激活链接直达员工。**

- 建号请求带 `issueActivationCredential` 时，Console 生成的口令是一次性抛弃值，不返回给任何调用方；同时签发激活凭据。
- `directory_activation_credentials` 只保存令牌 SHA-256，明文令牌只在签发响应里出现一次，由 Console BFF 直接经通知投递给员工本人。People 只拿到 `activationDelivered` 与有效期。
- 员工在 Console `/set-password` 页面自行设定密码；该页面与两个激活 API 不要求登录会话，令牌本身是唯一授权材料。
- 兑换在单事务内完成校验、消费与排队 `console.directory-connector.reset-password.v1`（管理员绑定改密，不需要当前密码），并发兑换只有一个能成功。
- 令牌无效、已兑换、已过期、已作废统一返回同一错误码，不泄露令牌是否真实存在。同一 uid 同时只允许一条 active 凭据。

Connector 成功后，Console 写入同一 UID 的 `directory_users` 和 LDAP `directory_identities`。

### 5. 激活 People 员工

People 收到并验真 LDAP 成功 receipt 后，在一个事务中：

1. 重新检查 onboarding case 仍为当前 revision。
2. 创建 `people_employees(employee_uid=canonical_uid)`。
3. 创建首个 `people_assignments(change_type=onboard)`。
4. 把 onboarding case 改为 `activating_employee`。
5. 冻结既有 `people.directory.employment-sync.v1`。

Console employment operation命中现有 LDAP Directory user，更新 People 权威字段、绑定 DingTalk identity 到同一个 UID、写 membership，并冻结 Platform operation。任何 identity 已绑定到其他 UID 的情况必须进入 `identity_conflict`，不能覆盖。

### 6. Platform 授权

Platform 继续消费现有 employment lifecycle：

- 创建或激活 tenant subject。
- 根据 `position_code/position_name` 自动匹配岗位来源的系统角色。
- 撤销不再适用的旧岗位来源角色。
- 普通员工基础访问通过 baseline 或岗位角色自动获得。

本轮必须同时修正岗位自动授权闸门：只有明确分类为 `main_position` 的角色才允许自动授予。`high_risk_privilege`、未分类角色以及仅凭岗位编码/名称碰巧命中的角色都不得自动授予，并增加契约测试覆盖当前 exact-code 绕过路径。

HR、财务管理员、系统管理员等敏感角色继续由显式授权或审批完成。敏感角色和岗位角色都不是普通员工入职 `completed` 的必要条件；基础登录和 baseline 权限成功即可完成入职，缺失岗位角色单独生成管理员待办。

## 钉钉字段落地：入职日期与手机号

生产反馈：钉钉同步后入职日期不更新、手机号取不到。逐段核对后，传输链路本身是通的，缺陷在**存储归属**与**可观测性**，因此必须在本方案内一并处理，否则受控入职会继承同一类静默丢字段问题。

### 现状缺陷

链路已具备的部分：

- 连接器已正确映射两个字段：`notification-runtime/internal/providers/dingtalk.go:351,356`；`dingTalkDateValue` 已把毫秒时间戳转成 `YYYY-MM-DD`。
- Data Runtime 已透传：`data-runtime/internal/apps/directory/adapter.go:212,222`。
- People → Console 生命周期命令确实携带 `mobile`/`email`：`data-runtime/internal/apps/people/directory_lifecycle_operation.go:213`。

缺陷在这三处：

1. **手机号在 People 侧没有第一类存储。** `people_employees` 没有 `mobile` 列，手机号仅以副作用形式存活在 `metadata->$.directory_user`，而每次同步执行 `metadata = VALUES(metadata)` 全量覆盖（`data-runtime/internal/apps/people/sync.go:151`）。生命周期命令又恰好从该 JSON 路径读取（`directory_lifecycle_operation.go:168-169`）。因此任何一次钉钉快照缺手机号，metadata 覆盖即丢失该字段，后续命令永远送空值。
2. **空值语义等同于“不更新”，导致失败静默。** Console 落库用 `mobile=COALESCE(NULLIF(VALUES(mobile),''),mobile)`（`console_lifecycle.go:281`），People 落库用 `onboard_date = COALESCE(VALUES(onboard_date), people_employees.onboard_date)`（`sync.go:149`）。连接器返回空字符串时 `VALUES` 为 NULL，字段永不写入，同步结果仍报成功——与「同步成功但两个字段没变」的现象完全一致。
3. **没有字段级信号。** `ResolveDingTalkPeopleBatch` 只统计整条用户级 `skipped`，链路中没有任何一处能区分「钉钉没有下发」和「我们中途丢了」。

### 处理原则

- 身份属性归 Console：手机号和企业邮箱是 Directory 事实，People 不做第二事实源，但必须显式承载并可观测，不能依赖 metadata blob 的副作用。
- 入职日期归 People：它是任职事实，钉钉是初始来源，HR 可修正；来源优先级必须显式声明，不能靠 SQL 的 `COALESCE` 隐式决定。
- provider 未下发是需要 HR 看见并处理的正常状态，不是静默成功。

### 1. 入职候选阶段

`planned_onboard_date` 默认取 `source_onboard_date`。`source_field_status.onboard_date` 为 `absent` 或 `invalid` 时，入职单停在 `awaiting_profile`，由 HR 显式填写；不允许以空入职日期进入 `ready_for_provisioning`。

手机号 `absent` 不阻塞入职（可选字段），但入职单与员工详情必须显示「钉钉未提供」，而不是显示为空白——空白无法与「已同步且确为空」区分。

### 2. 存量员工同步

- `people_employees` 增加 `mobile` 列，由同步与 HR 共同维护；生命周期命令改为读该列，`metadata` 退回纯审计快照用途，不再承担事实源职责。
- `people_employees` 增加 `onboard_date_source`（`dingtalk` / `manual`）。来源为 `manual` 时钉钉同步不得覆盖，避免 HR 修正被下一次同步冲掉；当前 `COALESCE` 写法下钉钉恒定获胜。
- 区分「provider 未下发该字段」与「provider 下发了空值」两种语义：前者保留旧值，后者按来源优先级决定是否清空。今天两者都被 `COALESCE` 归并为「保留旧值」，导致陈旧值无法纠正。

### 3. 连接器权限前置检查

钉钉 `topapi/v2/user/list` 的 `hired_date` 与 `mobile` 依赖应用权限；缺权限时字段被整体省略，而接口仍返回 `errcode=0`——这正是失败静默的外部成因。

- 连接器在同步任务开始时做一次能力探测：抽样活跃用户，统计 `hired_date`、`mobile` 的下发比例。
- 全批次 0 下发时，作业结果标记 `partial_fields_missing`，携带稳定错误码与「需在钉钉后台授予对应权限」的可操作提示，不得报完全成功。

### 4. 同步结果可观测

同步作业回执增加字段级计数：每个受管字段的 `provided` / `empty` / `absent` / `invalid` 条数。HR 在「人事事实源」页面能直接看到「入职日期：120 人中 0 人下发」，无需查库排查。

### 验收

- 钉钉下发入职日期时，`people_employees.onboard_date` 与入职单 `planned_onboard_date` 都更新到该值。
- 钉钉未下发入职日期时，作业标记 `partial_fields_missing` 并给出权限提示；入职单停留在 `awaiting_profile`，不会以空日期完成。
- HR 手工修正入职日期后来源标记为 `manual`，后续钉钉同步不覆盖。
- 钉钉下发手机号时 `directory_users.mobile` 更新；单次快照缺手机号不再导致该字段被静默固化。
- 员工详情与入职单能区分「钉钉未提供」与「值为空」。

## Permissions

2026-09-03 决定：不新增权限资源，复用既有 `employees`：

- 入职单读取 → `employees:view`
- 资料完善 → `employees:edit`
- 账号开通、员工激活、主体归并 → `employees:admin`

原方案的独立 `onboarding:*` 动作需要 Platform 重新导入 manifest 并逐一授权，
对一次性恢复与小范围功能而言成本不成比例。代价是归并与「编辑员工」落在同一
授权层级，失去独立隔离；补偿措施是强制填写确认理由，以及结构约束——只能
`dt-*` 并入真实主体，canonical 已有员工行或旧主体有在途操作时一律拒绝。浏览器不得提供 target tenant、deployment、service client 或 operation code。

Console service capability 固定为 `console:directory-identity:reserve` 与 `console:directory-user:provision`（归并复用后者），不能复用宽泛的 `directory_users:edit`。两者需要 Console 与 data-runtime 双 audience 的 grant seed/verify。Platform 不接收 People 浏览器直接写角色。

## Idempotency and Consistency

- 钉钉候选自然键：`provider_code + provider_subject`。
- HR 提交键：`onboarding_code + object_version`。
- UID 预留、LDAP 创建、employee 激活和 Platform 投影各自使用稳定 operation key。
- 同键同 hash 返回既有结果；同键异 hash 返回 409。
- 后续步骤只消费上一步已验真的成功 receipt，不相信浏览器声称“LDAP 已创建”。
- 所有 retry 必须复用冻结 command；资料变化产生新 revision 和新 operation，不修改旧 command。

## Failure and Compensation

| 失败点 | 系统行为 |
| --- | --- |
| UID/邮箱冲突 | 进入 `profile_conflict`，不创建账号 |
| DingTalk identity 已属于其他 UID | 进入 `identity_conflict`，要求受控归并 |
| 身份预留到期且 LDAP 尚未创建 | 释放旧预留，进入 `reservation_expired`；HR 确认后以新版本重新预留 |
| LDAP 暂时不可用 | operation retry，入职单保持 `provisioning_account` |
| LDAP 明确拒绝 | `provisioning_failed`，显示稳定错误码并允许修正后新 revision 重试 |
| LDAP 成功、People 激活失败 | 保留 Directory 账号但标记 onboarding pending；禁止重复创建 LDAP，重试 People 激活 |
| People 成功、Platform 暂时失败 | 员工和登录账号保持有效；Platform operation retry，状态 `projecting_authorization` |
| HR 取消且尚未创建 LDAP | 释放 reservation，状态 `cancelled` |
| HR 取消但 LDAP 已创建 | 不直接删除账号；进入显式撤销/离职流程并保留审计 |

## Existing `dt-*` Recovery

新流程上线前必须提供一次受控修复能力：

1. 预览 `dt-*` Directory user、DingTalk identity、People employee、LDAP UID、邮箱和部门关系。
2. 由运维执行 `docs/runbooks/dt-uid-merge-precheck.sql` 逐库核查跨应用引用；任一非 0 即停止自动归并。产品内不提供扫描能力（2026-09-02 决定）。
3. 只在管理员明确选择 canonical UID 后生成归并计划。
4. 暂停该员工的新 HR lifecycle operation，并确认不存在运行中的旧 UID operation。
5. 把 People employee、`employee_no=dt-*` 污染值及全部 People 外键引用迁到 canonical UID/真实工号。
6. 将 DingTalk identity 重绑到 canonical UID，合并 Directory membership并撤销旧会话。
7. 停用旧 `dt-*` Directory/Platform subject，重建 canonical subject 与授权。
8. 用同一 DingTalk 快照重跑并验证幂等。

不得仅修改 username，不得无报告地直接删除 `dt-*` 行，也不得按邮箱自动跨主体归并。首期不引入用户 UID alias；若真实数据证明大量旧 UID 已被业务应用引用，应另立跨应用迁移设计，而不是放宽本归并闸门。

## Success Criteria

- LDAP 托管租户中，新的未匹配钉钉员工不会创建 `dt-*` 正式 employee 或 active Directory user。
- 钉钉、LDAP、CAS/OIDC、People、Console 和 Platform 对同一员工最终使用同一个 canonical UID。
- 钉钉重复同步、浏览器重复点击、Connector 回执丢失均不会创建第二个 LDAP 用户或第二个 employee。
- HR 可从一个 People 页面看到每个入职步骤和可执行恢复动作。
- 普通员工在 LDAP 创建成功后可以通过 SSO 登录并获得基础权限。
- `completed` 只要求 Platform subject active 与 baseline 基础权限成功；岗位角色没有匹配时产生管理员待办，不阻塞入职。
- 只有明确分类为 `main_position` 的角色可以由岗位同步自动授予；高风险、未分类或仅文本/编码碰巧匹配的角色均不得自动授予。
- 已存在的刘凯类 `dt-*` 分叉可以通过受控归并恢复，旧主体在 Platform 中被撤销。
- 未解析经理不会生成 `dt-* manager_uid` 或指向不存在主体的正式引用。
- 预留过期、冲突解除和各异常状态都有确定出口与新版本规则。
- 钉钉下发的入职日期和手机号能够真正落地；未下发时作业标记 `partial_fields_missing` 并给出权限提示，不再静默报成功。
- HR 手工修正的入职日期不会被后续钉钉同步覆盖。

## Dependencies

- LDAP managed source 与 Directory Connector 必须 ready。
- Console 随机初始密码与一次性揭示已完成；仍需身份预留和 People 发起 LDAP provisioning 的精确 service contract，以及 People 发起时的凭据交付路径定案。
- People 需要 onboarding schema、状态机、权限和 operation executor。
- Platform 需要收紧岗位自动授权分类闸门；无主岗位映射时仍允许基础登录，但必须给出管理员待办。
- 发布前需要真实 LDAP、CAS/SSO、DingTalk 和 Platform 的端到端验收账号。
- 钉钉企业应用需具备读取 `hired_date` 与 `mobile` 的权限；权限不足时同步只能标记字段缺失，不能靠代码补齐。

## Open Questions

- UID 规则是全拼、姓名组合、工号还是企业自定义模板；冲突时如何编号。
- 入职日期在未来时，LDAP 账号何时创建、何时允许登录和何时激活授权。
- 在已证明每个主体跨应用引用为零的前提下，历史 `dt-*` 归并是否仍要求逐人确认，还是允许管理员批量批准。
- provider 明确下发空手机号时，是清空 Directory 现有值还是保留并提示 HR 确认。
