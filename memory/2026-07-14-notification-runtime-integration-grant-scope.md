# DEBUG REPORT — Notification Runtime Integration Grant Scope

- **Symptom:** Notification Runtime health, JWT authentication, WeCom integration configuration, and SQLite verification all passed, but Console test delivery returned `404 Not Found` from `/api/v1/console/notification-runtime/wecom-test`.
- **Root cause:** The notification-runtime installer created the required `integration_config:view` and `credential_vault:resolve` grants with only a `source` marker in `scope_json`. Console intentionally treats `scope_json.integrationCodes` as an executable allowlist; a missing or malformed allowlist denies access. Runtime token introspection therefore succeeded, but its subsequent read of `wecom.default` was hidden as 404. The configuration checker only compared resource/action strings, so it incorrectly reported the grants as complete.
- **Fix:** Centralized the notification-runtime grant contract, explicitly granting only `wecom.default` on both grants and `usageTypes=['integration']` for vault resolution. The installer now writes the complete scope. The explicit admin configuration check repairs historical service identity and grant-scope drift, and validates the actual integration allowlist. Runtime `Integration not found` responses are mapped to an actionable 409 message.
- **Evidence:** Cloudflare production tail showed `/oauth/introspect` returning 200 followed by `/api/v1/console/integrations/wecom.default` returning 404 for `client:notification-runtime`; the outer Runtime request then reported `console_request_failed: Integration not found`.
- **Regression test:** `console/test/notificationPublishPermission.test.ts` verifies the canonical `wecom.default` allowlist, vault usage type, installer scope generation, self-repair, actual allowlist validation, and actionable error mapping. `console/test/integrationSecretResolveAuthorization.test.ts` continues to verify fail-closed service integration authorization.
- **Follow-up found during production verification:** Once the 404 was removed, Runtime reached `/api/v1/console/vault/resolve` but still sent legacy caller-selected `secretRef` and `purpose` fields. The current Console contract only accepts `integrationCode`, then derives the active secret binding, fixed version, and audit purpose server-side. This returned `400 integrationCode is invalid`.
- **Follow-up fix:** Runtime secret resolution now sends only `integrationCode`; the WeCom provider no longer forwards the integration response's secret reference. A Go regression test asserts the exact request body and rejects secret/version/purpose fields.
- **Production verification:** Console Cloudflare version `3049421a-262c-465e-bd98-ac7550320f7d` was deployed after lint, typecheck, build/dry-run, and 307 tests (306 pass, 1 skip). The explicit WeCom configuration check repaired the production grant rows and then reported every item as pass. Notification Runtime `0.1.6` was published to R2; the customer timer upgraded the live instance from `0.1.5` to `0.1.6` with SQLite still ready. Final Cloudflare tail showed token introspection 200, integration read allowed, vault resolve 200, and the outer `/api/v1/console/notification-runtime/wecom-test` request 200.
- **Status:** DONE.
