### 1.2 客户画像与核心诉求

目标客户：ToB/ToG 项目制中小企业（IT 服务商、系统集成商、方案型销售团队，约 20–200 人）。

他们的核心诉求只有三件事：

1. **现金流看得见** —— 本月该收多少、哪些逾期、发票开了没有。
2. **项目盈亏算得清** —— 每个项目赚了还是亏了，不要做完才知道。
3. **日常协作跑得顺** —— 报销、付款、开票审批别卡在微信里。

### 1.3 排序原则

按「客户价值 × 落地速度」排序，所有方向都建立在约 80% 的存量代码上，做验证、收口和体验，不另起炉灶。

## 2. 五个优先方向

### 方向 ① 现金流闭环打磨 + 回款逾期预警 ⭐ 第一优先

**SME 场景**：老板和财务每天问：这个月该收多少？哪些合同回款逾期了？发票开了没有？现金流是 SME 生死线。

**范围**：

- 用一家真实客户的真实数据跑通「合同生效 → 项目交付 → 开票申请 → 审批 → 开票 → 到账 → 核销 → 回款计划状态回传」全链路，修掉沿途问题（含 altoc 看板/商机 403 验证）。
- 回款计划逾期自动标红；账龄视图（应收 / 实收 / 逾期 / 未开票四象限）。
- 逾期提醒推送企业微信 / 钉钉（复用 notification-runtime）。

**为什么快**：主链路 Phase 1 已完成，本方向做验证、修补和预警，不是新开发。

**验收标准**：

- 试点客户一份真实合同从生效到核销全程在系统内走完，无手工补数据。
- 逾期回款计划在列表和看板标红，且 IM 通知到负责人。
- 全链路跨模块契约测试覆盖：正常流 + 幂等重放 + 下游失败重试。

**涉及模块**：altoc、finance、aims、workflow、notification-runtime

### 方向 ② Finance 高频操作工作台

**SME 场景**：财务只有 1–2 个人，开票、到账登记、核销是每日高频操作，必须几分钟内完成；配置驱动通用页字段多、易填错。

**范围**：

- **开票工作台**：待开票回款计划 → 一键发起开票申请 → 审批 → 开票 → 登记，一条龙串联。
- **到账核销工作台**：银行到账登记 / 导入 → 智能匹配发票 → 一键核销。
- `[...slug]` 配置驱动通用页保留，只服务低频对象（银行账户、字典等）。

**为什么快**：106 个后端 API 全部就绪，只做 3–4 个专门前端页。

**验收标准**：

- 财务完成一笔「开票申请 → 开票登记」不超过 3 分钟、不超过 2 个页面。
- 到账核销支持按合同 / 发票自动匹配建议，核销结果实时回传 altoc 回款计划。
- 工作台符合 `docs/STANDARD_LIST_PAGE.md` 规范（分页、防抖搜索、空态、确认对话框）。

**涉及模块**：finance（主）、altoc、workflow

### 方向 ③ 老板经营驾驶舱（最小版）

**SME 场景**：老板不会钻进五个模块翻数据，他要打开首页一眼看到经营状况。这张屏是老板愿意付费的理由。

**范围**（一个聚合首页，落在 console shell 或 altoc dashboard）：

- 现金流卡片：本月应收 / 实收 / 逾期金额。
- 商机漏斗：altoc 各阶段商机数量与金额。
- 项目毛利 Top/Bottom 5：finance 项目核算摘要。
- 待办审批数：workflow 当前用户待办。

**为什么快**：全部是已有 API 的只读聚合，1 个页面，预计 1–2 周。相当于把 Phase 5 驾驶舱的核心价值提前落地。

**验收标准**：

- 老板角色登录后首屏即见上述四区，数据均为实时服务端聚合。
- 每区可点击下钻到对应模块列表页。
- 数据范围严格按服务端授权过滤（不得前端隐藏代替）。

**涉及模块**：altoc（承载）、finance、aims、workflow、foundation

### 方向 ④ 工时极简填报 + 项目盈亏自动核算

**SME 场景**：项目制公司最怕"项目做完才知道亏了"；但员工抵触填工时，填报必须极简。

**范围**：

- aims 工时填报减负：按周批量填报、默认值预填、企业微信 / 钉钉入口。
- 收尾 Phase 3 链路：people 成本快照 → finance `sync-people-costs` → 项目损益（收入 − 人力成本 − 资产/采购成本）。
- aims 项目详情页直接展示「当前毛利」。

**为什么快**：Phase 3 契约已冻结（finance CLAUDE.md），API 已在，主要是端到端联调 + 填报体验优化。

**验收标准**：

- 员工填报一周工时不超过 2 分钟。
- 项目损益页按月展示人力成本（people 快照）与资产成本（assets cost-summary）的自动归集结果，毛利 = 合同财务摘要 − 成本合计。
- 成本数据修改后有重算入口和审计记录。

**涉及模块**：aims、people、finance、assets

---

### 方向 ⑤ 审批与 IM 通知闭环

**SME 场景**：没有专职行政，报销、付款、开票审批卡在老板微信里，天天被问"批了没"。

**范围**：

- 三类高频审批（费用报销、付款申请、开票申请）走 workflow 标准链路，审批动作与业务终态同步。
- 审批待办 / 结果推送企业微信 / 钉钉（复用已有 OAuth 与 notification-runtime）。
- 审批中心聚合页：跨应用待办一处看（注意已知的跨应用 403 问题模式，workflow apiUrl + grant 矩阵需按部署拓扑核对）。

**为什么快**：workflow 引擎与通知基建现成，本方向是打通和模板配置。

**验收标准**：

- 三类审批从发起到终态全程系统内完成，审批结果自动回写业务单据状态。
- 待办产生后 1 分钟内 IM 通知到审批人。
- 审批中心跨应用拉取无 403（覆盖 workflow 子域名 + static token 部署形态）。

**涉及模块**：workflow、finance、notification-runtime、console、foundation

## 4. 明确不做（本阶段）

以下方向对 SME 首次落地性价比低，试点跑起来前不投入：

- assets 深化（IT 服务商资产体量小，现有能力够用）。
- Phase 4 服务工单 / 维保执行（等试点客户提出真实运维诉求再启动，启动前需先做 altoc 工单入口 vs aims service-desk 的事实源归属裁决）。
- Phase 5 完整驾驶舱与 AI 分析（方向③已提前拿到核心价值）。
- people 绩效复杂化（评分校准、360 等，保持 Phase 3 最小实现）。
