# 13 Insights 研发效能

**做什么**：代码仓库监测与研发效能分析——提交、贡献者、部门维度的统计与异常监控。
**谁在用**：技术管理者、研发负责人、部门负责人。

## 13.1 菜单结构

| 分组 | 页面 |
| --- | --- |
| **工作台** | 效能概览 |
| **仓库** | 管理、采集 |
| **分析** | 贡献者分析、仓库分析、部门分析、关系图 |
| **监控** | 事件、规则、设置 |
| **报表** | 提交报表、贡献者报表、部门报表、仓库报表 |
| **设置** | 仓库源、贡献者映射、部门同步、用户、参数 |

## 13.2 先做数据准备

Insights 的分析质量完全取决于数据准备。上手顺序：

### 第一步：配置仓库源

设置 → 仓库源。接入 Git / SVN 仓库。GitLab 的连接凭证在企业控制台的集成中心配置。

### 第二步：采集数据

仓库 → 采集。首次采集会拉取历史提交，仓库大的话需要一段时间。之后按配置增量采集。

采集失败常见原因：凭证过期、仓库地址变更、网络策略变更。

### 第三步：贡献者映射（最关键）

设置 → 贡献者。

**同一个人在不同仓库常有不同的 Git 提交身份**（个人邮箱、公司邮箱、不同用户名）。不做映射的话，一个人会被算成三个贡献者，所有统计都是错的。

把这些身份归并到同一个员工，并关联到企业目录的 `uid`。

### 第四步：部门同步

设置 → 部门。把贡献者关联到部门，部门维度的报表才有数据。

> **顺序不能跳。** 没做贡献者映射就看报表，得到的数字会误导决策。

## 13.3 分析视图

| 视图 | 看什么 |
| --- | --- |
| **贡献者分析** | 个人的提交量、活跃度、涉及仓库 |
| **仓库分析** | 单个仓库的活跃度、贡献者分布、变更趋势 |
| **部门分析** | 部门维度的研发投入与产出 |
| **关系图** | 人与仓库、仓库与仓库的关联关系 |

## 13.4 监控

| 页面 | 用途 |
| --- | --- |
| **规则** | 定义什么算异常（提交模式、代码量、时间分布等） |
| **事件** | 触发的异常事件列表 |
| **设置** | 扫描配置、事件级别 |

监控用于发现异常模式，比如异常的大批量提交、非工作时间的密集变更。它是**提示**，不是结论——看到事件要人工判断。

## 13.5 报表

提交报表、贡献者报表、部门报表、仓库报表，支持导出（需要 `insights:report_exporter` 角色）。

## 13.6 角色一览

| 角色 | 能做什么 |
| --- | --- |
| `insights:viewer` | 查看研发效能看板与仓库统计 |
| `insights:analyst` | 查看效能明细、部门视图、贡献者画像和异常监控 |
| `insights:report_exporter` | 导出看板和统计报表 |
| `insights:contributor_manager` | 维护贡献者画像、人员归并和贡献者映射 |
| `insights:ingestion_operator` | 查看采集状态并手动触发采集或聚合任务 |
| `insights:monitoring_operator` | 查看异常监控并处理监控事件（不维护规则） |
| `insights:monitoring_admin` | 维护监控规则、事件级别和扫描配置 |
| `insights:repository_admin` | 管理代码仓库源、采集配置和采集任务 |
| `insights:settings_admin` | 维护全局参数、用户映射和部门同步 |
| `insights:admin` | 管理仓库源、采集任务、监控规则与全局配置 |

## 13.7 使用建议（重要）

1. **先把贡献者映射做干净，再看任何数字。** 这是 Insights 唯一的前置条件，也是最常被跳过的一步。
2. **提交量不等于产出。** 重构、删代码、写文档都会让提交量"变差"。把它当趋势参考，不要当 KPI。
3. **不要用它做个人考核。** 一旦拿来考核，行为立刻扭曲（拆分提交、灌水），数据就失去价值了。
4. **看趋势，不看单点。** 单周数据波动很大，看月度和季度趋势有意义。
5. **异常事件要人工判断。** 规则只是提示，别自动下结论。
