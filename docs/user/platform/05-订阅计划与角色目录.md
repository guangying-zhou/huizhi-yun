# 05 订阅计划与角色目录

这一章覆盖三个页面：订阅计划 `/admin/plans`、企业角色 `/admin/enterprise-roles`、应用权限角色 `/admin/system-roles`。它们回答三个不同问题：**企业资格是否生效 → 客户能配什么角色 → 每个角色能做什么**。企业全量功能资格不等于给每位员工授权；员工仍须有岗位角色和对象范围，详见 [企业角色与权限](../tenant/05-角色与权限管理.md)。

## 5.1 订阅计划

`/admin/plans` 保留 Starter / Pro / Advanced 等计划资料，供订单、账务和历史合同核对使用。它们不是企业全量模式下逐应用功能门槛。

新企业使用固定的 `enterprise-full` 企业资格：资格在有效期内且状态为 active 时，企业具备全量功能资格；应用是否能进入还取决于模块是否部署、是否完成企业配置，以及当前员工是否拥有相应岗位角色和对象范围。不要通过修改某个旧套餐的应用或 capability 开关来让企业恢复某个模块入口。

新建计划（`/admin/plans/new`）需要填：

| 字段 | 说明 |
| --- | --- |
| 计划 Code | 唯一标识，发布后不建议更改 |
| 计划名称 | 对客户展示的名字 |
| 档位 | 计划的层级定位 |
| 说明 | 卖点描述 |
| 状态 | 草稿 / 上架 / 下架 |
| 计费模式 | 按什么口径计费 |
| 基础价 / 币种 / 结算周期 | 商务参数 |

计划详情页 `/admin/plans/{code}` 的旧应用和 capability 资料用于保留历史商业事实，不应覆盖已生效的企业全量资格。

**设计计划时的三条经验：**

1. **历史计划按商业事实维护**。人数、价格和旧套餐不再决定企业模式下的单项功能资格。
2. **技术模块以 Manifest、部署和企业配置为准**。不要把配置开关误当成付费权益。
3. **不要把具体客户名称编进计划**。特殊需求应走受控实施记录，不要新建“某某公司专版”来改变运行时权限。

### 5.1.1 旧套餐转换预览

为老企业准备全量资格前，先运行[只读转换预览](../../../platform/server/utils/enterpriseEntitlementRepository.ts)。预览会列出订阅、订单、License 和部署凭证的映射及冲突，并保留原订单、License、旧套餐和账务事实；它默认 dry-run，**不会**修改合同、续期、收费或租户资格。

预览结果为 `needs-review` 时，按冲突逐项核对有效期、来源关联和凭证状态，再由有权人员走正式变更流程。不要因为预览显示历史套餐不同，就手工给员工增加角色或放宽对象范围。

## 5.2 应用权限角色

`/admin/system-roles` 是**应用权限角色**清单——定义"在某个应用里能做什么"，来源是各应用 Manifest 的 `recommendedRoles`。

角色编码格式为 `<app>:<role>`，例如：

- `aims:pm`（AIMS 项目经理）、`aims:qa`、`aims:project_approver`
- `finance:cashier`（出纳）、`finance:invoice_approver`（开票审批人）
- `assets:procurement`（采购经办）、`assets:asset_approver`（资产审批人）
- `console:directory_manager`（目录管理员）、`console:security_admin`（安全管理员）

**页面顶部的覆盖告警很重要**：如果提示"存在未被应用权限角色覆盖的授权动作"，说明某个 `requires_grant` 的动作没有任何角色能授予它——客户永远配不出能做这件事的人。这类告警必须在应用上架前清掉，处理方式是回到应用侧补 Manifest 角色，而不是在平台侧手工加角色。

**职责分离原则**：高风险动作要与主岗位拆开。注意 Manifest 里已经这样设计了——采购经办（`assets:procurement`）与资产审批人（`assets:asset_approver`）是两个角色，应收会计（`finance:ar_accountant`）与出纳（`finance:cashier`）也是两个角色。审核时不要允许把它们合并。

## 5.3 企业角色母版

`/admin/enterprise-roles` 维护平台预置的**企业角色母版**，并配置每个企业角色默认包含哪些应用权限角色。

它是客户开通后能直接用的一组"现成岗位"，例如：

```
企业角色「销售负责人」
   ├─ altoc:sales
   ├─ altoc:contract_manager
   ├─ codocs:editor
   └─ finance:viewer
```

**关键规则：**

- 企业角色**组合**应用角色，应用角色**定义动作**，数据范围**定义能对哪些对象做**。三者职责不能混。
- **不要把具体部门、项目、客户编进角色名**。"华东区销售经理"是错的——地域应该由数据范围表达，角色只叫"销售经理"。
- 母版只是默认值。租户可以自建企业角色，只要 `app_code` 为空、状态 active、可分配，就必须能生效；不要以"不是平台预置的"为由限制租户自定义角色。

## 5.4 三层关系速查

```
企业全量资格             「这家公司在有效期内可使用全量功能」
      ↓
应用权限角色 App Role  「aims:pm 能管项目计划、迭代、人员、工时审核」
      ↓
企业角色 Enterprise Role「项目经理 = aims:pm + codocs:editor」
      ↓
数据范围 Scope         「张三这个项目经理只管 P-2026-001 这个项目」
```

企业资格由 Platform 维护；角色和数据范围由租户管理员维护（见 [tenant/05](../tenant/05-角色与权限管理.md)）。运营不要替客户决定数据范围，也不要把企业资格当作个人角色。

## 5.5 常见问题

**Q：企业资格 active，但员工看不到 Finance 菜单。**
按顺序查：模块是否已部署 → 是否完成企业配置 → 员工是否被授予任一 finance 应用角色及所需对象范围。企业全量资格不会自动给全员 Finance 权限；具体处理见 [tenant 常见问题](../tenant/14-常见问题.md#企业资格与应用入口)。

**Q：改了企业角色母版，已开通租户会跟着变吗？**
母版是新开通时的默认值。已开通租户的角色配置属于租户自己的数据，改母版不回溯覆盖，需要客户自行调整或运营协助。

**Q：能给某个角色单独加一个 `approve` 动作吗？**
不能在平台侧手工加。`approve`、`confirm`、`export`、`close`、`deploy` 属于敏感动作，必须由应用 Manifest 显式声明并有契约测试。回到应用侧补 Manifest。
