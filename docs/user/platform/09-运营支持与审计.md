# 09 运营支持与审计

## 9.1 工单管理 `/admin/tickets`

集中查看租户支持工单、优先级、处理人和当前状态。

**分级建议：**

| 级别 | 判断标准 | 响应 |
| --- | --- | --- |
| P0 | 客户全员不可用、数据风险 | 立即响应，同步通知相关方 |
| P1 | 核心功能不可用、影响一个部门 | 当日响应 |
| P2 | 单个功能异常、有替代方案 | 按排期处理 |
| P3 | 咨询、优化建议 | 汇总后统一回复 |

**处理工单时先取三样信息**：租户编码、发生时间、具体操作路径。没有这三样，`/admin/audit` 里查不到对应记录。

## 9.2 公告管理 `/admin/announcements`

查看平台公告的受众、级别、发布时间和有效期。

用于：版本发布通知、计划内维护窗口、重要变更提醒。

**写公告的三条原则：**

1. 说清楚**影响谁**（全部租户 / 指定租户 / 指定应用）。
2. 说清楚**影响什么**（哪些功能、什么时间段不可用）。
3. 说清楚**客户要不要做什么**（无需操作 / 需要升级 / 需要重新登录）。

维护类公告要设置有效期，过期自动下架，避免陈旧公告长期挂在客户界面上。

## 9.3 Feature Flag `/admin/feature-flags`

查看平台功能开关、默认值和定向规则数量。

用法见 [04 章 4.7 节](./04-Runtime发布管理.md#47-灰度)。补充两点：

- 每个开关要有**负责人和退出条件**（什么时候可以删掉这个开关）。
- 定向规则数量增长过快是个信号，说明这个开关正在变成事实上的"客户定制"，该考虑收敛成正式能力或独立套餐了。

## 9.4 审计日志 `/admin/audit`

查看 Platform 管理操作的主体、对象和发生时间。

**能查到什么**：谁在什么时间对哪个租户/订阅/角色/部署做了什么操作。

**排查时的用法**：

- 客户说"权限突然没了" → 按租户编码 + 时间范围过滤，找角色或订阅相关的变更记录。
- 客户说"数据被改了" → 平台审计记录的是**管理面操作**；业务数据变更要看租户侧的应用审计日志（Console `/admin/logs`）。
- 内部复盘 → 按操作人过滤，还原一次变更的完整动作序列。

审计日志是只读的，不提供删除。这是设计如此。

## 9.5 平台账号 `/admin/accounts`

查看能够登录 Platform Admin Console 的账号及其角色。

**账号管理规范：**

- 一人一号，禁止共用。审计日志按账号追溯，共用账号等于没有审计。
- 新同事入职：建号 → 分配最小必要角色 → 发激活邮件。
- 同事离职或转岗：**当天**停用或调整角色，不要等。
- 定期（建议每季度）复核一次账号清单，清理不再需要的账号。

## 9.6 平台角色 `/admin/platform-roles`

查看平台运营账号使用的角色目录和可分配状态。

分配角色时记住：`admin` 只默认蕴含同一资源的 `view/edit/admin`。`approve`、`export`、`deploy` 这类敏感动作必须显式授权。给运营同事配权限时按实际职责给，不要图省事给超管。

**职责冲突要拆开**：负责下单的人不应同时拥有确认到账的权限；负责配置部署的人不应同时拥有审核 Manifest 的权限。

## 9.7 运营记录习惯

以下动作建议在系统内留下书面记录（工单备注、租户详情备注或公告）：

- 停服、恢复服务
- 手工确认收款
- 手工调整订阅期限或 capability
- 强制下线用户
- 灰度开关的开启与关闭

写清楚：**做了什么、为什么、谁批准的**。三个月后回头看，只有这三样能救你。
