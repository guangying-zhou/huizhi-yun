版本：1.2。初始日期：2026-09-16。修订日期：2026-09-20。

## 1. 本次确定什么，不改变什么

**确定的目标是：六个主业务入口＋两个辅助入口、一条统一业务侧栏、一套公共顶部栏；一级业务区常驻，保留其下可折叠的二级/三级功能导航和适用的对象树。**

不是把原来的多个应用菜单简单拼到一页，也不是把完整业务树压缩成几个横向按钮。变化的是用户发现和组织工作的方式，不是各领域的数据主责、权限、状态机或数据库结构。


| 层次          | 本规范的安排                              | 不应产生的变化                          |
| ----------- | ----------------------------------- | -------------------------------- |
| 一级入口        | 工作台、产品、销售、交付与服务、经营、人力资源；辅助为协同文档、控制台 | 不再默认显示 Aims、Assets、Altoc 等内部工程名称 |
| 二级菜单        | 按具体工作领域分组                           | 不因为一个分组包含多域，就要求用户拥有该分组全部权限       |
| 三级菜单        | 进入列表、工作区、办理中心或既有页面                  | 不为新增/编辑/审批/发布等动作另造空页面            |
| 对象工作区       | 产品、合同、项目等有自己的上下文与返回路径               | 不复制一份“统一产品”“交付项目”或“个人工时”数据       |
| 项目集/产品线等对象树 | 在业务页、选择面板或同一侧栏的对象模式按需显示             | 不因固定功能菜单最多三级而删除对象层次              |
| 临时双栏        | 可保留业务区窄栏＋业务树，共用同一导航合同               | 不建设两套长期导航产品或重新初始化第二套会话           |


完整目录是目标归属建议。表内没有标“后续”，也不等于当前 Host 已具备该页面；必须逐项核对路由、必要 API、权限和业务闭环。原来可用但尚未迁入的功能保留正式兼容入口；确实未实现的能力不显示空菜单。

## 2. 一级导航与业务边界

### 2.1 固定名称和位置


| 用户入口  | 位置  | 拟定稳定导航 ID        | 职责                        |
| ----- | --- | ---------------- | ------------------------- |
| 工作台   | 主区  | `nav.workspace`  | 当前用户的任务、审批、个人事务与日常协作      |
| 产品    | 主区  | `nav.product`    | 产品定义、规划、版本、研发协同和支撑产品的资产   |
| 销售    | 主区  | `nav.sales`      | 客户关系、销售机会、报价、合同、结算与回款安排   |
| 交付与服务 | 主区  | `nav.delivery`   | 项目执行、成果验收、客户交付资产和持续服务     |
| 经营    | 主区  | `nav.operations` | 财务、资金、业务成本核算、经营分析和企业自用资源  |
| 人力资源  | 主区  | `nav.people`     | 组织岗位、员工生命周期、人员成本事实与绩效管理   |
| 协同文档  | 辅助区 | `nav.documents`  | 跨业务文档发现、协作、评审与复用          |
| 控制台   | 辅助区 | `nav.console`    | 企业基础配置、身份权限、规则、流程、集成和安全治理 |


导航 ID 仅为本版命名建议，不冒充仓库现有字段。标签可本地化，ID 应稳定；这些 ID 不能直接替换后端 `appCode`、资源编码或 scope。

主区顺序默认如表，辅助区在同一侧栏的下部或独立分隔区。只有实际能力和当前权限满足时才显示相应入口；不要求每个员工看见八个完整入口（六主两辅）。

### 2.2 名称的解释

“产品”不是产品资产台账的简称，包含产品如何定义、规划、演进和发布；“销售”包含客户、合同和续约，而不仅是销售漏斗；“交付与服务”明确包含维护和持续服务，而不止一次性验收。

“经营”聚焦财务、资金、业务核算和企业资源，不能只做驾驶舱；“人力资源”作为独立主入口，覆盖组织岗位、员工生命周期、人员成本事实和绩效管理。人力资源不是人员成本的一个财务子项，也不是重新独立部署的 People 应用。

一级显示名称使用“人力资源”；不在同一导航混用“HR”“人事”作为不同一级入口。财务人员可默认进入经营的财务收支，人事人员可直接进入人力资源的员工管理；这些是视图偏好，不是角色切换、权限前置条件或提权。

“控制台”表示企业管理和配置，不是 Platform 租户/发布治理后台。员工入职、报销、合同办理等正常业务不因使用者是管理员而移入控制台。

### 2.3 一级首页不是新增看板要求

工作台直接进入个人首页。产品、销售、交付与服务、经营、人力资源可进入已经存在且获授权的概览，或登记的默认列表。缺少专用概览时可以直接展开菜单并进入合适页面，不为每个一级节点再开发一套综合看板。

有首页的节点将“进入首页”和“展开分组”设置为不同点击目标；没有首页的纯分组只展开。默认目的地必须可达且符合当前用户权限，不能固定跳到只有管理员可看的页面。

## 3. 完整一二三级菜单

本节标题是一级菜单；第一列是二级分组；第二列每个以顿号分隔的名称是独立三级入口。三级入口可以复用同一正式页面的过滤视图，不能因此复制实现。

### 3.1 工作台

定位：个人工作的统一入口。


| 二级菜单 | 三级菜单                | 组织规则                                     |
| ---- | ------------------- | ---------------------------------------- |
| 今日工作 | 我的待办、我的任务、工作日历      | 聚合当前用户工作；工作日历展示与我有关的事项，不等于控制台的工作日历规则配置   |
| 审批办理 | 待我审批、我发起的、我已办理的     | 同一审批体系的不同视图；打开对应业务单据办理                   |
| 个人事务 | 我的工时、我的周报、我的报销、我的绩效 | 复用正式业务页并附加获准的个人范围；个人绩效视图具备后再展示，不新建个人业务系统 |
| 日常协作 | 日常事务、我参与的项目         | 保留非研发、非客户交付的日常项目入口                       |


个人首页可以显示最近访问、收藏、提醒与快捷操作。不再额外建立“工作台→工作总览→工作台首页”的冗余层级。业务单据与审批状态仍由原领域维护，聚合待办不产生第二套审批规则。个人首页的版式、区块数据契约、授权前提与四态见[企业工作台设计与实现规范](./Enterprise-Workbench-Design-Spec.md)。

### 3.2 产品

定位：统一产品定义、能力、规划、发布与研发协同。


| 二级菜单     | 三级菜单                  | 组织规则                                |
| -------- | --------------------- | ----------------------------------- |
| 产品目录     | 全部产品、产品线              | 用户从统一产品目录进入，不再分别寻找“资产里的产品”和“项目里的产品” |
| 产品规划     | 产品管理空间、功能清单、产品需求、规划看板 | 保留主档与规划空间差异；可以先选择产品/空间再进入既有页面       |
| 版本与发布    | 版本计划、发布记录             | 区分计划范围与已经正式发布的事实                    |
| 研发协同     | 研发项目、执行协调             | 连接规划与执行；研发项目复用同一项目对象与详情             |
| 产品资产     | 技术底座、知识产权、产品资料        | 组织支撑产品的可复用能力及资料，不将企业自用设备混入          |
| 商业规格〔后续〕 | 可售规格、授权规格、标准价格        | 管理租户对外产品如何销售；按实际建设进度接入              |


不为每个三级菜单强制新增跨产品总列表。没有聚合接口时，使用产品/管理空间选择器进入现有工作区；选择只能在用户可见对象范围内进行，不能自动取第一条关联。

商业规格针对租户对外销售的产品，不是恢复汇智云自身基础版/专业版或应用购买门槛。标准价格与某次报价、合同成交价格分别记录。

“产品业务工作台”是界面概念，“产品管理空间”是现有规划对象。一个产品可以关联多个空间或组件关系；导航不得改成默认一对一。

### 3.3 销售

定位：从客户与机会形成商业合同，安排结算、回款和续约。


| 二级菜单  | 三级菜单           | 组织规则                         |
| ----- | -------------- | ---------------------------- |
| 客户经营  | 客户档案、联系人、跟进记录  | 以客户组织关系与销售活动                 |
| 销售机会  | 线索、商机、续约机会     | 保留线索/商机区别；续约与增购属于商业机会        |
| 报价与投标 | 报价单、投标项目       | 管理具体商务过程                     |
| 合同管理  | 销售合同、维保合同、服务权益 | 记录商业约定；维护服务的执行进入交付           |
| 结算与回款 | 结算事项、回款计划、逾期跟进 | 关注应收安排与办理跟踪；到账、发票及核销引用财务正式事实 |


“维保合同”“续约机会”只规定发现入口，不要求因此合并或拆分既有实体。服务权益的商业约定在销售维护，交付按授权读取作为服务依据，不建立两份独立可改的权益。

结算事项可以是合同执行事项的授权列表或过滤视图；尚无独立列表时从合同工作台进入，不为菜单补齐而新造结算状态机。

### 3.4 交付与服务

定位：履行客户承诺、组织项目执行，并持续提供维护服务。


| 二级菜单  | 三级菜单                | 组织规则                      |
| ----- | ------------------- | ------------------------- |
| 项目管理  | 项目总览、项目集、项目模板       | 默认面向交付/维护项目；保留有权限的全部项目视图  |
| 执行协同  | 任务中心、工时日历、周报汇总、项目资源 | 面向执行团队的跨项目视图；没有聚合能力时先选择项目 |
| 成果与质量 | 交付物、验收事项、质量检查、项目文档  | 面向交付成果，不用任务完成率代替验收        |
| 客户资产  | 客户交付资产、交付环境、部署记录    | 回答交付了什么、运行在哪里、当前使用哪个版本    |
| 维护服务  | 服务工单、服务履约           | 管理问题、咨询、变更处理和服务承诺执行       |


项目总览、研发项目、我参与的项目可以是同一项目中心的不同默认过滤。交付区不应成为研发和日常事务项目的唯一入口，也不得通过默认类型筛选删除其正式可达路径。

项目集/项目树保留在项目中心、切换面板或对象模式中。维护服务可以提供进入维护项目的快捷入口，但最终打开同一项目详情。

项目模板的使用可以放在项目中心；模板维护等管理动作仍需既有权限。不能因为它出现在交付菜单中，就给普通成员模板管理权限。

### 3.5 经营

定位：财务收支、资金、业务成本核算、经营分析与企业自用资源。


| 二级菜单  | 三级菜单                     | 组织规则                                |
| ----- | ------------------------ | ----------------------------------- |
| 经营分析  | 经营概览、销售与履约分析、经营报表        | 引用有明确口径的授权汇总，不为每个来源应用保留重复驾驶舱        |
| 财务收支  | 开票申请、发票管理、收款核销、费用支出、付款申请 | 正式财务处理入口；“收款核销”是导航分组/页面组织，不合并两类业务事实 |
| 账户与资金 | 银行账户、账户余额、资金变动           | 资金账户及其变化                            |
| 成本核算  | 合同核算、项目核算、成本分摊、绩效金额      | 连接工时、成本与经营结果；不改既有冻结/核算语义            |
| 企业资源  | 自用资产、资源台账、采购事项           | 内部设备、资源与采购，优先接入现有能力                 |


经营区不再增加“财务→财务管理→发票管理”等额外包装。经营分析、财务收支、账户与资金、成本核算、企业资源五个二级组直接呈现；不再在此维护“人事管理”或“成本与绩效”的人员业务分组，也不要求每次从经营概览重新查找。

经营中的“绩效金额”继续管理财务奖金/提成等正式金额口径；评价、周期和确认进入人力资源的“绩效管理”。经营中的人工成本归集与分摊引用人力资源提供的人员成本事实，不在经营区再维护一套员工成本基数。不得因人力资源独立而删除已获准的项目/合同成本汇总。

查看项目/合同成本汇总不自动授予个人薪酬明细权限。合并导航不要求建设完整总账、税务申报或工资发放系统，也不把缺失的经营分析值显示为零。

### 3.6 人力资源

定位：以员工及其任职为主线，独立管理组织岗位、员工生命周期、人员成本事实和绩效评价；不要求通过经营或控制台进入正常人事业务。


| 二级菜单  | 三级菜单                | 组织规则                                     |
| ----- | ------------------- | ---------------------------------------- |
| 组织与岗位 | 组织架构、岗位管理、职级管理      | 使用正式组织、岗位和职级事实；组织树按权限读取，不新建第二份 Directory |
| 员工管理  | 员工档案、入职管理、任职变更、离职交接 | 由既有人事领域办理；离职通过正式流程衔接账号与资产交接              |
| 人员成本  | 职级与成本标准、人员成本快照      | 维护标准、期间及已确认人员成本事实；与岗位/职级定义区分，同一成本来源供经营引用 |
| 绩效管理  | 绩效周期、贡献快照、绩效结果      | 保留周期、贡献、评价与确认语义；奖金/提成等财务金额继续在经营处理        |


“岗位管理、职级管理”维护定义，“职级与成本标准”维护适用成本口径。若当前正式页面合并承载这些内容，使用同页分区或兼容入口，不为菜单拆分复制字典、表单或数据。

组织架构继续按 Console Directory、People 和外部正式人事事实源的既有责任读取或修改。外部源维护的组织/任职字段显示来源并遵守编辑限制；本规范不决定把组织权威迁到 People，也不让控制台和人力各有一套组织主档。

员工基本信息、任职、人员成本及绩效结果分别授权，部门范围和敏感字段规则继续生效。普通员工原则上通过工作台办理个人事务；“我的绩效”只展示本人获准查看的正式结果，不因开放人力入口资源自动披露尚未发布或无权查看的评价。

招聘、考勤、培训、工资发放等未纳入当前范围的能力仍需单独评审，不为了一级入口完整而补空页面。人力资源导航先承接已有正式能力和受控兼容路径，不以新增完整 HR 系统为本轮前置条件。

### 3.7 协同文档

定位：跨业务发现、协作、评审与复用同一份文档。


| 二级菜单  | 三级菜单                | 组织规则                     |
| ----- | ------------------- | ------------------------ |
| 文档空间  | 我的文档、共享文档、部门文档、企业文库 | 按权限与归属提供不同视图             |
| 文档协作  | 文档评审、发布审核           | 个人待办可汇总到工作台，正式状态仍由文档领域维护 |
| 模板与复用 | 文档模板、方案资料           | 组织已经具备的模板和可复用资料          |


产品资料、合同文本和项目文档不从业务工作区撤走；业务页面在上下文中使用文档，文档入口用于跨业务查找和管理。多入口引用相同文档，不分别存两个版本。

文档编辑器和协作运行边界按 ADR-018/019 保留。统一文档入口不等于将所有编辑器脚本加入 Host 首屏。

### 3.8 控制台

定位：企业配置与治理，不承接正常业务记录办理。


| 二级菜单  | 三级菜单                | 组织规则                                        |
| ----- | ------------------- | ------------------------------------------- |
| 企业与组织 | 企业资料、组织目录、工作日历配置    | 企业基础资料与目录治理；组织目录与人力组织视图共用正式事实，不新增第二套组织编辑实现  |
| 身份与权限 | 成员账号、角色授权、服务身份      | 登录访问和服务调用治理；不同于员工档案                         |
| 业务配置  | 产品字典、项目规则、财务规则、人事字典 | 对应业务参数与规则；岗位、职级和成本标准的主要发现入口在人力，相关快捷入口引用同一实现 |
| 流程配置  | 审批流程、审批表单           | 流程定义维护；员工审批办理留在工作台与业务对象                     |
| 集成与运行 | 外部集成、运行组件、同步任务、跨域操作 | 正式集成、状态和受控失败处理；不提供通用数据访问                    |
| 安全与审计 | 登录审计、操作审计、凭证管理      | 按明确安全权限开放；不增加数据库直达或通用 SQL 控制台               |


控制台并非只能由超级管理员使用。财务规则由获授权的财务管理员维护，产品字典由相应业务管理员维护；只展示其有权管理的部分。组织目录治理和人力资源业务视图不是两套组织数据。适用的人事配置可由获授权人员从人力资源或控制台发现，但不得重复实现岗位、职级、成本标准表单；未迁移的旧配置路径按 §8 保留兼容。

人事人员办理离职不自动获得角色授权、服务凭证或账号管理权限；账号停用与资产回收经正式流程协作，失败和重试按各领域既有规则处理，不在前端连续调用多个写接口伪装事务。

“角色授权”仅进入企业获准使用的正式授权界面，不能把 Platform 的全平台租户治理、发布治理和权限权威复制到 Host。“服务身份”和“凭证管理”分别负责使用关系和秘密材料治理，入口相关不等于普通业务可以读取秘密。

## 4. 容易重复的对象与入口归属

### 4.1 主要发现位置与其他入口


| 内容                | 主要发现入口            | 其他位置的使用方式               | 不能做什么                     |
| ----------------- | ----------------- | ----------------------- | ------------------------- |
| 产品主档、技术底座、知识产权    | 产品                | 销售与交付引用产品；经营使用授权汇总      | 为不同业务区维护不同产品主档            |
| 产品管理空间、功能、需求与版本   | 产品                | 研发项目进入同一规划/版本上下文        | 将产品主档与管理空间强制一对一           |
| 研发/交付/维护/日常项目     | 产品/交付与服务/工作台的不同视图 | 共用一套正式项目详情和类型规则         | 按导航来源复制项目系统               |
| 客户交付资产、客户部署环境     | 交付与服务             | 产品、客户和合同显示关联            | 与公司自用设备混成一类，或新增中央关系主档     |
| 企业自用设备、内部资源       | 经营                | 离职交接和项目资源按权限引用          | 以统一菜单为由改变资产主责             |
| 销售/维保合同、商业服务权益    | 销售                | 交付查看履约依据，经营读取核算关系       | 因多个入口形成两套合同或权益事实          |
| 服务工单和维护执行         | 交付与服务             | 客户/合同详情提供关联入口           | 在销售和交付各自维护处理状态            |
| 回款计划和催收跟进         | 销售                | 合同与经营分析按规则读取            | 将计划当作到账或确认收入              |
| 到账、发票与核销          | 经营                | 销售及合同聚合获授权摘要            | 让前端摘要成为可独立改写的财务记录         |
| 组织架构、岗位与职级        | 人力资源              | 控制台目录治理或配置快捷入口引用正式事实/实现 | 因一级名称改变而重建组织主档或改写外部权威源    |
| 员工档案、入转调离与绩效评价    | 人力资源              | 工作台个人视图；交付使用获授权人员信息     | 将员工事实与登录账号混为一表，或与绩效金额混同   |
| 人员成本标准、月度成本快照     | 人力资源              | 经营按权限引用用于归集/核算          | 在经营区维护第二套员工成本，或用当前值覆盖历史快照 |
| 项目投入与工时           | 工作台 / 交付          | 人力或经营按获准契约引用            | 为人力资源入口复制工时、状态和确认规则       |
| 项目/合同人工成本、分摊与绩效金额 | 经营                | 项目或人力页面可引用获授权摘要         | 汇总访问自动变成个人薪酬明细访问，或重写人力评价  |
| 账号、角色、身份源与集成      | 控制台               | 各业务消费正式身份/权限结果          | 菜单组名称取代 scope 或变成新角色      |
| 审批待办              | 工作台               | 原业务对象保留办理入口和历史          | 重建并行审批状态机                 |
| 产品/项目/合同文档        | 业务区和文档的多入口        | 同一文档 ID、版本和权限           | 跨区复制文件和版本，或绕过文档权限         |


### 4.2 未列入目标主目录的旧功能怎样处理

本节不是确认当前代码有哪些功能，而是防止目标目录被误用为删除清单。FE-0 必须扫描完整旧菜单、正式路由、对象内动作和通知深链接。

此前讨论提及的数字资产、文件柜、演示文稿、资讯、细分采购/资产操作、项目度量等，若在旧正式系统中已经可用，不能因为 §3 收敛名称而消失。应映射为所属二级组的扩展三级项、相应业务页中的子视图、对象内页签，或过渡期正式兼容入口，并在台账记录具体决定。

例如：原数字资产可归入产品资产的适用视图；项目度量保留在项目工作区；文件柜/演示文稿归文档相关空间；原资产分类/字典维护归控制台的适用业务配置。以上是兼容映射建议，不是本版擅自新增或宣布下线的功能。

原入口的合并只改变发现方式：合并为一个页面时保留需要的筛选/页签与旧链接解析；删除需有单独批准的业务退役理由和消费者归零证据。

### 4.3 人员投入到经营核算的协作链

业务链保持为“人力资源：人员成本事实 → 交付与服务：工时与投入事实 → 经营：归集、分摊和项目/合同核算”。工作台提供个人填报或查询入口，控制台提供身份与权限治理，不替代上述业务事实。

期间、标准/实际口径、确认状态及已冻结历史按正式核算契约引用；页面需要的汇总由获授权查询返回。人力资源调整当前人员成本时，不反向覆盖已冻结的项目/合同核算和绩效金额；确需修正按原有调整、版本及审计规则办理。

人力资源独立不要求用户同时拥有两区全部权限，也不要求为了查看获准的成本汇总开放底层个人薪酬。菜单、详情、接口、导出和缓存都遵守同一对象/字段授权；隐藏按钮不能替代服务端校验。

```text
    ▾ 产品目录                   列表、详情、表单或看板
        全部产品
        产品线                   对象内仅使用必要的局部分组
    ▸ 产品规划
    ▸ 版本与发布
```

六个主入口、两个辅助入口在同一侧栏组织，不在外面再固定显示一条 Aims/Assets 等应用图标栏。辅助入口的配置管理属性不意味着其权限较高或可自动访问全部内容。

桌面侧栏以 224 像素为默认宽度，允许在 208～256 像素间调整，折叠后为 56 像素；移动端抽屉为 288 像素。业务表格和看板使用剩余宽度，表单可在页面内部局部限宽，不让所有页面都固定居中窄列。

### 5.2 展开、高亮与滚动


| 情况          | 规则                              |
| ----------- | ------------------------------- |
| 首次进入某业务区    | 一级业务区常驻；展开当前业务区中匹配页面的二级/三级祖先，其他业务区的分组默认收起       |
| 返回使用过的业务区   | 一级业务区仍常驻；在当前权限允许范围内恢复该区二级/三级分组的展开偏好与位置          |
| 深链接进入三级页/对象 | 按路由及对象上下文定位，不能依赖先点过菜单           |
| 节点既有首页又有子项  | 文字/链接负责进入；独立箭头/按钮负责展开，两种动作可键盘区分 |
| 纯分组没有首页     | 只展开，不跳转到空白概览                    |
| 很多二三级项      | 侧栏自身可滚动；避免默认展开所有业务区；不增加新的应用切换层  |
| 收藏或最近访问     | 引用同一正式目的地，仍校验权限；不复制页面或业务对象      |
| 临时服务失败      | 在目标页面/已授权状态区说明，不随机移除菜单或自动切旧数据源  |


高亮按正式路由匹配与导航归属计算，不依赖可见中文标签或任意子串前缀。相同对象多入口时保持一份详情；来源只影响合理的返回与所在业务区显示，不改变数据权限。

### 5.3 折叠、窄屏与键盘

折叠侧栏可提供有名称的图标、提示或点击展开面板；没有鼠标悬停时仍然能访问所有入口。窄屏使用同一数据源的抽屉或覆盖导航，选择页面后关闭并恢复合理焦点，不保留两套不同菜单。

分组按钮具有展开状态，页面链接具有当前状态；焦点可见。采用标准 disclosure/navigation 模式时支持 Tab、Enter/Space；若采用 tree widget，则按其实际语义完整实现方向键等操作，不能只添加 `role=tree` 而不实现交互。

支持长名称换行/截断后的完整提示、触屏点击目标和不覆盖主要操作的抽屉。常驻全局搜索和快捷键可以后续增强，不作为一级入口基本可达的替代。

### 5.4 公共页头只出现一次

全局企业标题、通知、个人菜单、退出入口只显示一份。产品名、项目名、合同号可作为对象摘要出现，但不能附带另一套完整应用导航和登录菜单。

在旧 Console 容器中打开 Enterprise 时，必须选择唯一公共 chrome 所有者。可以用受控路由直接进入 Host，或为兼容嵌入提供明确无重复页头模式；不能只用任意 query 参数隐藏所有权限/会话校验，也不能同时保留外层与内层的退出逻辑。

若暂时导航到旧独立应用，要明确这是兼容路径及实际文档切换；不宣称旧应用的内存状态仍属于同一个常驻 Shell。

## 6. 对象工作区与对象树

### 6.1 产品：业务侧栏＋对象内分组


| 对象内分组 | 内容                       |
| ----- | ------------------------ |
| 总览    | 产品摘要、阶段状态、近期规划、发布与必要提醒   |
| 产品定义  | 基本信息、产品线、能力及资料入口         |
| 规划与发布 | 相关产品管理空间、需求、版本、执行关联及发布证据 |
| 商业与客户 | 后续接入的可售规格、合同、客户交付与在用情况   |


产品名称和正式 code 标识当前对象；关联空间不唯一时，让用户选择有权访问的关联。产品线/产品树可放在产品中心或产品切换面板中，不将每个版本、需求、任务追加为全局菜单的固定第四级。

当前主档名称跟随后续正常读取更新；已发布内容、签署内容及其他有历史语义的快照不因改名而改写。

### 6.2 合同：保留事实、执行、管理分组


| 对象内分组 | 内容                      |
| ----- | ----------------------- |
| 总览    | 关键事实、履约进展、结算/回款摘要与待办    |
| 合同事实  | 基本信息；合同标的；合同条款；合同文本     |
| 合同执行  | 履约；结算与回款，内部按业务对象或锚点明确区分 |
| 合同管理  | 关联与管理；操作历史              |


付款、质保约定属于合同事实；结算、回款及财务入账/核销引用各自正式事实。统一导航不能重新把结算条件、付款条款、回款计划混为三个没有边界的同级页面。

进入项目、客户交付资产或维保服务后，可以返回合同相应上下文；前端只传受控引用，不连续发送多个写请求伪装成后端事务。

### 6.3 项目：允许同一侧栏切换为上下文导航

复杂项目工作区可使用如下分组，依据类型和权限裁剪：


| 对象内分组 | 内容                   |
| ----- | -------------------- |
| 概览    | 项目目标、状态、进度、风险        |
| 计划与执行 | 里程碑、目标、任务看板、适用的需求与变更 |
| 交付与质量 | 成果、验收、质量检查、项目文档      |
| 团队与投入 | 成员、工时、周报、资源、获授权成本摘要  |
| 项目管理  | 设置、关联产品与合同、操作历史      |



项目切换器可以弹出按项目集组织的项目树。项目中心仍保留项目集浏览、项目收藏与选择；侧栏模式切换只改变导航呈现，不重新登录、不改变角色、不卸载全部公共 Shell。

无需对所有详情强制使用对象模式。一般产品/合同详情保留业务侧栏即可；只有确实需要长时间工作和密集导航的对象工作区才替换同一侧栏，避免增加固定第三栏。

### 6.4 返回、深链接和无权状态


| 场景           | 应有行为                                |
| ------------ | ----------------------------------- |
| 从产品进入研发项目    | 打开同一项目详情，保留返回产品或相关版本/规划的受控来源        |
| 从交付项目列表进入项目  | 返回原列表的允许筛选、排序、分页及对象树状态              |
| 从合同进入交付项目    | 返回对应合同工作区，不只跳转到销售首页                 |
| 首次打开项目/产品深链接 | 从路由和正式对象事实建立上下文；没有可信来源时提供登记默认返回     |
| 刷新或浏览器前进/后退  | 内容、面包屑、活动菜单和对象保持一致                  |
| 原对象被删除或访问权撤销 | 清理其摘要/树节点，显示适当的不可访问状态与安全去向；不残留名称或计数 |
| 正在编辑时换对象/业务区 | 明确处理未保存内容，完成后才切换；敏感草稿不放 URL         |


返回来源只接受本站受控路由或登记 origin，不允许开放重定向。禁止根据用户提供的来源参数选择租户数据库、权限身份或旧权威数据源。

## 7. 最小技术路线与导航合同

### 7.1 仍采用构建时组合，不引入新的微前端平台

继续使用 Enterprise Host、Foundation、显式业务 UI Layer 和业务组合页面。单域面板和表单由原领域公开导出；Host 负责区域编排与公共导航，Runtime 负责数据和业务规则。

统一侧栏不依赖物理合库完成，也不要求当前 SSR/客户端模式改变。首轮可以通过现有正式 API 完成菜单和页面整合，随后按 ADR-018 优化 Runtime 内部查询。

### 7.2 复用旧侧栏能力，不复制完整旧应用布局

应从原布局拆出菜单描述、项目/产品上下文 UI、对象选择器及适用的操作入口。公共心跳、会话 bootstrap、权限快照和重预取由 Host/Foundation 统一协调；不要把旧 `default.vue` 连同这些副作用整体复制。

按业务组合不等于增加巨大 Foundation，也不允许 Host 直接依赖其他 Layer 的私有 store、私有 server utils 或绕过领域写入命令。双栏过渡与统一单栏使用相同数据和上下文协议。

### 7.3 拟定导航声明字段

以下是最小合同建议，不是新增后端模型或已经存在的 API；最终字段可复用仓库已有等价结构。


| 字段/信息                     | 用途                                       |
| ------------------------- | ---------------------------------------- |
| `id`                      | 稳定菜单节点标识，不随中文名称变化                        |
| `label`、`icon`            | 显示名称、适用图标，不包含鉴权规则                        |
| `area`、`parentId`、`order` | 一级业务区、父节点与排序                             |
| `kind`                    | 纯分组、正式页面或快捷引用；对象上下文由相应协议承载               |
| `destinationRef`          | 命名路由/正式目的地引用；快捷入口指向相同实现                  |
| `activeMatch`             | 当前菜单与对象路由的确定性匹配                          |
| `permissionRefs`          | 引用既有 resource/action，组合语义明确为任一/全部；不按标签推导 |
| `availabilityRef`         | 服务端受控的部署/配置与接入信息，不承载购买模块资格               |
| `contextPolicy`           | 允许的对象种类、选择器与返回来源语义                       |
| `legacyMappingRef`        | 旧地址、参数与当前正式兼容映射的引用                       |


运行环境里的当前目的地由受控租户/环境/发布配置解析，不将所有环境硬编码进浏览器菜单，也不允许 query/cookie 自行改变数据面。

### 7.4 权限清单、导航清单、API 登记各司其职

权限资源/动作继续来自既有 manifest。导航声明只引用它们；构建或契约检查验证引用合法。不能通过新增“经营管理员”或“人力管理员”自动覆盖现有 Finance、People、Assets、Console 的全部授权，也不按 `nav.people` 推导新的后端身份或 scope。人力与经营分别按可见子项显示，成员可以依据既有合并权限同时使用两区；成本和绩效敏感字段仍单独控制。

页面与 BFF/API 可以仍由不同领域提供，但必须有可核验的依赖关系。就绪性中间件使用同源接口登记，或与正式 handler 表做双向一致性测试；不长期手写一份与路由各自变化的放行列表。

构建检查至少发现重复路由名/路径、重复或缺失接口方法、孤立菜单、失效快捷引用、不存在权限引用和循环分组。通过检查不代表用户流程已通过，实际 Host 链路仍需测试。

### 7.5 UI 偏好不能成为权限或秘密存储

展开/折叠、固定菜单和默认业务页按适用企业/环境/用户隔离。优先持久化稳定菜单 ID 和非敏感偏好；不得在可共享的 localStorage 或日志里存全企业对象树、敏感名称、Token 或授权快照。

恢复时按当前正式权限重新过滤。退出、切换企业或撤权后取消旧请求并清理对象摘要、面包屑、树与缓存，旧代次的迟到结果不得重新填回当前界面。主题等非敏感全局偏好可采用独立规则。

## 8. 迁移映射与旧功能保留

### 8.1 每个旧入口必须有去向


| 要登记的信息            | 要回答的问题                 |
| ----------------- | ---------------------- |
| 稳定菜单/路由标识与原入口     | 原来用户从哪里进入，包括正式深链接和对象内页 |
| 目标一级/二级/三级或对象导航位置 | 新组织中放在哪里               |
| 正式页面及必要 API       | 实际走哪个页面，依赖哪些方法/路径与业务合同 |
| 权限、对象和字段范围        | 谁能进入/操作，不能泄漏什么         |
| 租户、环境和发布版本        | 当前环境是否已经切入该实现          |
| 迁移状态              | Host、旧正式兼容、后续规划或已退役    |
| 旧参数/ID/code 与来源翻译 | 书签、通知、返回和 hash 怎么保持语义  |
| 负责人和证据            | 谁验收、在哪个提交及环境验证、何时允许退役  |


状态说明：这些是拟定登记语义，不代表当前分支已有同名枚举或后台接口。实际进度仍在统一实施台账维护。

### 8.2 示例映射，不替代完整清点


| 旧业务入口类别                 | 目标发现位置                        | 迁移要求                         |
| ----------------------- | ----------------------------- | ---------------------------- |
| Aims 产品中心               | 产品→产品规划→产品管理空间；产品工作台引用        | 保留空间标识与业务语义，不变成第二产品主档        |
| Assets 产品主档             | 产品→产品目录→全部产品                  | 一套正式产品详情，规划/版本从同对象进入         |
| Aims 项目总览/项目集           | 交付与服务→项目管理→项目总览/项目集           | 全部项目视图保留，研发与个人入口是同页不同过滤      |
| Aims 项目内菜单              | 项目上下文导航                       | 目标、里程碑、工时、文档、成果、度量等各有明确位置    |
| 财务收款/核销                 | 经营→财务收支→收款核销                  | 可使用两个子视图，不合并到账与核销事实          |
| 原方案“经营→人事管理”及既有员工生命周期入口 | 人力资源→员工管理→员工档案/入职管理/任职变更/离职交接 | 正式页面与权限不变；不再要求先进入经营或取得经营权限   |
| 原方案“经营→成本与绩效”的岗位职级入口    | 人力资源→组织与岗位→岗位管理/职级管理          | 如原页面合并承载，保留同页分区或批准兼容映射，不复制字典 |
| 既有职级成本标准、人员成本入口         | 人力资源→人员成本→职级与成本标准/人员成本快照      | 保留人员成本事实、期间及历史；经营核算仍引用同一来源   |
| 原方案“经营→成本与绩效”的周期与评价入口   | 人力资源→绩效管理→绩效周期/贡献快照/绩效结果      | 不把评价结果迁成财务金额；历史链接与权限保持       |
| 控制台组织目录、适用岗位职级配置入口      | 人力资源的组织与岗位主入口；控制台保留必要治理/快捷入口  | 组织事实源和修改权限不变，指向同一正式对象/实现     |
| 客户服务工单                  | 交付与服务→维护服务→服务工单               | 销售的客户/合同可关联进入相同工单            |
| 旧文档空间和编辑链接              | 协同文档及产品/项目/合同的引用入口            | 同一文档及权限；编辑器必要独立边界保留          |
| 旧应用“跨应用操作”诊断页           | 控制台→集成与运行→跨域操作                | 后台可靠操作语义、精确权限和审计不变           |


### 8.3 四类状态的呈现


| 状态       | 呈现和操作规则                        |
| -------- | ------------------------------ |
| 已接入 Host | 在新导航进入正式页面；全部必要读取/写入链路通过才视为可用  |
| 旧正式兼容    | 保留受控跳转或经批准的适配；明确返回；不得重建一套旧数据源  |
| 后续规划     | 普通用户不显示空页面；管理员可在适当配置说明中查看真实条件  |
| 已退役      | 有批准、替代与消费者归零证据后移除；需要的历史链接按合同处理 |


临时网络故障、未部署和人员无权不是上述迁移状态。不能通过健康检测临时自动将业务写入切回旧实现，也不能把所有不可访问错误显示成未购买。

### 8.4 双栏过渡如何退出

确需过渡时，最外侧窄栏使用六主两辅业务名称，内侧显示当前业务树；同一 Host 控制两者，数据来自同一份导航登记。不是再维护一个“应用菜单”事实源。

达到下列条件后退出：已迁移业务的统一单栏可达、对象树/上下文可用、旧链接兼容、代表性角色任务与窄屏测试通过。退出时仅替换呈现，不再次改业务路由、权限或数据库。

默认不同时提供两套长期用户可选布局。确有岗位测试数据证明需要另一种形式时，另行评审范围与维护成本。

### 8.5 本轮人力资源独立的迁移规则

本轮首先调整业务归属、父节点与排序，不强制更名全部路由、API、manifest 资源或后端 appCode。拟新增的一级 `nav.people` 只表达业务区；已登记的员工、成本、绩效等叶节点 ID 与 `destinationRef` 尽量保持稳定。

原“人事管理”“成本与绩效”两个分组拆入人力资源四个分组。确需调整节点 ID 时，在同一发布的导航映射中登记旧 ID/父节点到新位置的关系，恢复收藏、固定入口、默认首页和允许的展开偏好。恢复前重新过滤当前权限；无权页面不得因历史收藏继续显示人员名称或敏感内容。

旧经营位置的书签、通知与正式深链接继续解析到同一业务对象；路径可保留或由既有兼容解析器转换，不能仅用新的中文菜单名推断路径。POST/PUT/PATCH/DELETE 等写入协议不随页面重定向或重放。控制台的适用配置快捷入口保留同源引用，不复制组织、岗位、职级或成本标准。

人力资源导航与旧能力的映射先于完整页面迁移。已有正式能力可先走获批准的兼容路径，未实现能力继续不显示空菜单；迁移批次、负责人和验收证据只在原统一实施台账登记，不另建一套 People 发布或权限平台。

## 11. 完成标准与后续维护

完成不等于一级名称改完、Worker 合并或树组件出现。至少要满足：有权用户能沿正常菜单和深链接完成代表性任务；同一对象多入口不复制事实；原项目树和业务导航有位置；公共外壳不重复；页面与必要接口闭环；撤权与回退可靠。

本规范的菜单目录可以随业务发展按版本调整，但八个一级名称（六主两辅）及单一侧栏方向的变更应同步更新 ADR。新增菜单先明确所代表的业务对象/工作、已有正式实现和权限，不先占一个空位置再补数据。

涉及新的商业目录、跨域报表或尚不存在的列表，按独立业务需求评审；不能把菜单目标当作这些功能已批准开发或已完成的证明。

维护时保持三个不同事实源：模块 manifest 管权限资源/动作，导航声明管发现与布局，业务服务管权威数据与规则。统一的是用户工作过程，不是把这三类事实揉成一个万能菜单模型。
