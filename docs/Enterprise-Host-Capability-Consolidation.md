# Enterprise Host → Runtime 服务能力收敛方案

状态：用户已批准方向（2026-09-28）；实施与环境步骤按本文分批送审。作者：Claude（整合负责人）。

## 1. 问题

Enterprise Host 调自身 Data Runtime 的 `/v1/enterprise/**` 用户委托路由时，每个操作都要求一个独立 service capability。截至 `ed4765a1`：

| 项 | 数量 |
| --- | --- |
| Foundation 登记的 Host 操作（`enterpriseRuntimeClient.ts`） | 292（aims 194、codocs 54、assets 29、altoc 13、console 2） |
| 不同的 capability | 172 |
| 每新增一个操作需同步的制品 | Foundation 操作表、Runtime 路由常量、模块 manifest 服务资源、Console grant seed + verify + MySQL 测试、egress scope 生成物、readiness 生成物、all-routes 契约测试 |

这些 capability 没有提供独立的安全边界：

- Host 根据用户权限快照选择 capability，同时把同一判断写进 permit 的 `resource/action`（例如 `collab-documents/review-admin`、`review-history/company-read`）。Runtime 本来就会校验 permit 与路由期望的 resource/action 一致。
- [许可一致性审查](./Enterprise-Permit-Consistency-Review-20260928.md)已确认：permit 由 Host 断言；Host 被攻破时，它持有 `enterprise.runtime` 的全部 capability，细粒度 capability 挡不住。
- 代价是真实的：每个 capability 都要单独签发、缓存 Token，这加重了 Console 的签发 CPU 开销；grant 漂移曾多次导致 403；模块 manifest 里还混入了只供服务使用的资源（例如 `aims/admin-projects`）。

## 2. 决策

**适用范围**：仅限 `enterprise.runtime` 服务客户端调用 `/v1/enterprise/<domain>/**` 的用户委托路由，即经 `authenticateEnterpriseRequest` 认证、要求签名 actor 的路由。

**新模型**：

1. 每个业务域一个服务能力：`<domain>:enterprise-host:execute`，domain ∈ {`aims`、`assets`、`codocs`、`altoc`、`console`}。继续满足 `<target-app>:<resource>:<action>` 格式，Runtime 仍要求 `domain == route.LogicalTarget`，拿 codocs Token 调不了 aims 路由。按域授权还可以用作单个域的服务级停用开关。
2. 路由只声明 `LogicalTarget`。capability 由统一 helper 从 domain 推导，路由构造处不再写字面量。
3. Foundation 操作表保留 `operation → 精确 path` 白名单，删除 `capability` 字段；Token scope 由 path 的域段推导。浏览器仍然不能选择 path 或身份。
4. **以下保持不变**：service token 的 JWKS、iss、aud、`token_use=service`、tenant/deployment 绑定；Console 当前凭据与 grant 的实时撤销校验（`verifyEnterpriseCredential`，改为校验域 capability）；签名 actor；permit 的 actor、tenant、deployment、≤15 s 过期、resource/action 校验；Runtime 对对象关系与数据范围的复核；Host 使用 Foundation 统一授权 helper 判断用户权限；幂等键规则；401/403/503 错误语义。

**不在范围内（保持精确 capability）**：

- 调度与 worker 路由（`authenticateEnterpriseScheduler*`），它们遵守根 `CLAUDE.md` 的 worker 精确 scope 规则；
- cutover/control token；
- 独立应用之间的 `/api/v1/service/**`；
- Workflow、Console 等其它服务客户端；
- Altoc 读取的额外请求体签名（保留签名，只把 scope 换成域 capability）。

## 3. 必须先完成的分类（安全关键）

删除任何一个 capability 之前，先对 172 项逐一分类，结果写入本文附录：

- **A 冗余**：路由已经绑定期望的 permit resource/action，并由 Runtime 校验，直接删除。
- **B 能力选择了更宽的数据或行为**：例如 `*-admin`、`company-read`、`admin-projects:*`、`project-authorization`、`authorization-object`。要逐项确认 Runtime 按 permit 的 resource/action（或等价的结构化字段）区分行为，而不是靠 capability 区分。凡是只靠 capability 区分的，先补 Runtime permit 校验和反例测试，再删除该 capability。
- **C 无 permit 路由**：`product authorization-object`、`directory self`。确认改为域 capability 后，Host 能拿到的东西和现在一样（Host 原本就持有这些 capability），在附录中写明。

任何一项分类不明确时，该项暂停，交 Claude 裁定。

## 5. 验收

这次改动触及信任边界，按根 `CLAUDE.md` 执行完整回归矩阵：

- 正确调用 200；
- 缺少域 capability 403；
- 用其它域的 capability 调用 403；
- 错 audience、错来源应用或错 client 403；
- 错 tenant 或 deployment 403；
- Token 过期 401；
- grant 或凭据撤销 403，Console 状态不可用时 503；
- 缺签名 actor 403；
- permit 缺失、过期或 resource/action 不符时 403；
- 每个 B 类项的越权反例；
- 写请求的幂等重放。

另外补一项效果观察：同一会话打开项目详情和文档页时的 Token 签发次数（改动前后对比）。

完成标志：Foundation 操作表与 Runtime 路由里不再出现字面 capability；`enterprise.runtime` 的 active data-runtime grant 只剩 5 条加调度专用项；新增页面的迁移不再需要改 Console SQL。

## 8. 批 1 审查结论（Claude，2026-09-28）

**结论**：B/C 分类通过，批 2 可以在 PA-04 C 提交后开工。计数已核对为 A93/B77/C2（`aims:product-versions:edit` 因轻量计划子操作带额外 permit 归入 B 类，已在本次审查范围内）。

**抽查结果**：以下几项的行为分支都由路由决定，与 capability 无关。

| 项 | 分支依据 |
| --- | --- |
| `aims:admin-projects:*` | 管理员分支由独立路径注册决定（`server.go:732/735`）；`validateEnterpriseProjectUpdatePermit` 在 admin 分支固定期望 `admin/admin` + `mode=admin-static` |
| `assets:admin:admin` | 分类管理由 path→action 映射决定（`enterprise_assets_products.go:25-26`），并要求 `admin/admin` 且 scope 仅为 `all` |
| `codocs:collab-documents:review-admin` | 由 action 设置受信标志 |
| `codocs:review-history:company-read` | 由 action 设置受信标志 |
| C 类两项 | 只接受已验签的 actor，输入精确 |

**系统性核对**：在 `data-runtime/internal` 中搜索了“按 token scope 值切换行为”的代码。结果：Enterprise Host 通道里除通用校验（`enterprise_context.go:59`）外，没有别的分支依赖 scope 值。其余按 scope 分支的代码属于不在本次范围内的通道，批 2 不得修改：

- 独立应用通道：Assets `product_catalog.go` 要求 `assets.runtime`；Altoc `command_helpers.go`；Console Token 签发；
- 其他服务客户端：`routeAimsMilestoneReceivableWorkflowCallback` 使用 `aims.runtime` 加 `altoc:receivable:mark-billable`；
- 调度通道：`authenticateEnterpriseScheduler*`，只接受 `<app>.runtime`。

**批 2 附加要求**：

1. 同时改造 `authenticateEnterpriseRequest` 与 `authenticateEnterpriseAltocRead`；Altoc 读取的请求体签名保留。
2. 新增静态契约测试：`internal/server/enterprise_*.go`（非测试文件）中，除通用域 capability 校验外，不得读取 `identity.Scopes` / `Service.Scopes`，防止以后重新出现按 scope 分支的代码。调度与 milestone receivable 文件按文件名列入白名单。
3. 高风险 B/C 项逐项反例，要求在持有正确域 capability 的前提下仍返回 403：
   - admin 路由携带 `projects/edit` permit；
   - Assets 分类管理的 permit 缺少 `scope=all` 或带有额外 scope；
   - list-admin 路由携带 `read` permit；
   - company-read 路由携带 `read` permit，或路径不以 `codocs/company/` 开头；
   - `project-authorization`、`ip-asset:link-product`、`product-adoption:read` 缺第二个 permit；
   - C 类的 actor 不一致或输入多余。
4. 跨域反例：aims 域 Token 调 codocs、assets、altoc、console 路由均返回 403。
5. §7 中“调度专用项”：调度路由只接受 `<app>.runtime`，所以要确认 `enterprise.runtime` 是否真持有调度 grant。如果没有，收敛后它的 data-runtime grant 应恰好是 5 条。
