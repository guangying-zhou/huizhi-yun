# Finance 开票申请审批流配置建议（2026-08-29）

> 来源：走查 ISSUE-B-025 的生产端到端复验。代码链路已全部打通，最后卡在
> **租户未配置 Finance 审批流**：
>
> ```
> 404 action_def_not_found — "Finance invoice approval action is not configured"
> SELECT COUNT(*) FROM hzy_workflow.flow_action_defs WHERE app_code='finance';  → 0
> ```
>
> `flow_action_defs` 现有 aims 12 条、altoc 3 条，**finance 一条都没有**。
> 这与走查最初的结论一致：这条链在生产从未被端到端执行过，所以配置缺失一直没暴露。
>
> **本文只给建议，不含审批人和层级的业务决策**——那需要业务方拍板。

---

## 1. 代码写死的部分（不可改，必须精确匹配）

`data-runtime/internal/apps/workflow/finance_invoice_receipt.go` 用固定三元组查找动作定义：

```go
actionDefByKeyOn(ctx, tx, "finance", "invoices", "request")
```

因此配置必须**精确**为：

| 字段 | 值 | 说明 |
| --- | --- | --- |
| `app_code` | `finance` | 不可改 |
| `resource_code` | `invoices` | **复数**，不是 `invoice` |
| `action_code` | `request` | 不是 `approve` |

目标页与回调由 Workflow 侧自行派生（见 MR !36），**不需要**在配置里填：

- `biz_url` = `/finance/invoices/requests/{invoiceCode}`
- `callback_url` = `/finance/api/v1/finance/workflow/callback`

> 冻结命令里不得出现 `bizUrl` / `callbackUrl` 字段——安全持久化校验按字段名后缀
> 拒绝一切 `url`/`uri` 结尾的字段，带上它们会让整条链 400。这是 !36 修掉的死锁。

## 2. 需要业务方决定的部分

只有一件事：**开票申请由谁审批、几级**。

现有可直接复用的流程模板（`hzy_workflow.flow_schemas`，`is_template=1`）：

| id | code | 名称 | 适用 |
| --- | --- | --- | --- |
| 7 | `tpl_self_approval` | 自行审批 | 创建者自行确认，等于不实质审批 |
| 8 | `tpl_single_approval` | 单级审批 | 部门经理审批 |
| 9 | `tpl_two_level_approval` | 二级审批 | 部门经理 → 分管领导 |
| 10 | `tpl_three_level_approval` | 三级审批 | 部门经理 → 分管领导 → 上级部门负责人 |
| 11 | `tpl_committee_vote` | 委员会表决 | 指定角色全员会签 |

**建议按金额分档**，这是开票场景的常见做法，也用得上 `flow_routes.conditions`：

| 档位 | 建议模板 | 理由 |
| --- | --- | --- |
| 小额（如 ≤ 5 万） | 8 单级审批 | 走量业务不宜过重 |
| 中额（如 5–50 万） | 9 二级审批 | 分管领导把关 |
| 大额（如 > 50 万） | 10 三级审批 | 与合同审批（altoc 用 8）相比更重，因为开票直接触发收入确认 |

> 金额阈值必须由财务负责人定，本文的数字只是占位示例。
> 若暂时不想分档，用**单档 + 默认路由**最省事（见 §3 方案 A）。

## 3. 两种落地方案

### 方案 A：单档，最小可用 ✅ **已于 2026-08-29 在生产执行并验证通过**

> 执行结果：`flow_action_defs` id=18（16→17 行）、`flow_routes` id=19（17→18 行）。
> `source` 用 `manual` 而非 `sync`——这是人工配置，将来若有 manifest 同步机制不会被误覆盖。
>
> 回滚：
> ```sql
> DELETE FROM hzy_workflow.flow_routes WHERE id=19;
> DELETE FROM hzy_workflow.flow_action_defs WHERE id=18;
> ```
>
> 方案 B 保留在下方供后续按金额分档时参考，**尚未执行**。


与 altoc 合同审批同构（它就是单档默认路由 + 模板 8）。

```sql
-- 1) 动作定义
INSERT INTO hzy_workflow.flow_action_defs
  (app_code, resource_code, action_code, name, description,
   icon, embed_url_pattern, sort_order, status, source, created_by)

   'i-lucide-receipt', '{app_base_url}/invoices/requests/{biz_id}',
```

### 方案 B：按金额分档

动作定义同上，路由改为三条。`priority` **数值小的先匹配**，`is_default` 只能有一条。

```sql
-- 大额：> 500000
INSERT INTO hzy_workflow.flow_routes
  (action_def_id, flow_schema_id, name, conditions, priority, is_default, status, created_by)
SELECT d.id, 10, '大额开票', '{"amount":{"gt":500000}}', 10, 0, 1, 'system'
FROM hzy_workflow.flow_action_defs d
WHERE d.app_code='finance' AND d.resource_code='invoices' AND d.action_code='request';

-- 中额：> 50000
INSERT INTO hzy_workflow.flow_routes
  (action_def_id, flow_schema_id, name, conditions, priority, is_default, status, created_by)
SELECT d.id, 9, '中额开票', '{"amount":{"gt":50000}}', 20, 0, 1, 'system'
FROM hzy_workflow.flow_action_defs d
WHERE d.app_code='finance' AND d.resource_code='invoices' AND d.action_code='request';

-- 兜底
INSERT INTO hzy_workflow.flow_routes
  (action_def_id, flow_schema_id, name, conditions, priority, is_default, status, created_by)
SELECT d.id, 8, '默认路由', '{}', 100, 1, 1, 'system'
FROM hzy_workflow.flow_action_defs d
WHERE d.app_code='finance' AND d.resource_code='invoices' AND d.action_code='request';
```

> ⚠️ **`conditions` 的字段名需要先核对**。Workflow 侧用
> `prepareFlowContext(...)` 组装匹配上下文，`bizContext` 来自 Finance 冻结命令，
> 含 `amount`、`currency_code`、`contract_code`、`customer_code`。
> 分档上线前应先在测试租户用真实金额验证 `matchRoutesOn` 的匹配结果，
> 不要直接在生产用未验证的条件表达式——匹配不到任何路由会返回
> `409 workflow_route_not_found`。
>
> 若拿不准，先上方案 A，分档等验证后再加。

## 4. 落地后如何验证

```sql
-- 配置是否就位
SELECT d.id, d.app_code, d.resource_code, d.action_code, d.status,
       r.id AS route_id, r.flow_schema_id, r.priority, r.is_default
FROM hzy_workflow.flow_action_defs d
LEFT JOIN hzy_workflow.flow_routes r ON r.action_def_id = d.id
WHERE d.app_code='finance';
```

然后在 Altoc 回款计划页点「开票申请」，按下列顺序确认：

1. `hzy_finance.invoice_request` 出现新行（第一跳，**已验证可用**）
2. `hzy_finance.integration_operation` 的 workflow-submit operation 走到 `succeeded`
3. `hzy_workflow.flow_instances` 出现对应实例，`biz_id` = 发票编码
4. 审批中心能看到待办

**2026-08-29 复验结果：四步全部通过。** 配置落地后又在 Console 重新部署完成、
全部模块与 main 对齐的状态下，清空全部中间产物、从零重跑了一次完整链路：

| 环节 | 结果 |
| --- | --- |
| ① Altoc operation | `succeeded` → `IR202608292035253C7C` |
| ② Finance 开票申请 | 落库，`pending_approval`，¥1,000.00 |
| ③ Finance service_command_receipt | `succeeded` |
| ④ Finance→Workflow operation | `succeeded` → `WF202608300001` |
| ⑤ Workflow 审批实例 | `running`，`biz_id` 与发票编码一致 |

两跳的 `attempt_count` 均为 1，**没有任何重试**。发票状态由 `draft` 变为
`pending_approval`，证明审批链真正接上而非空跑；`biz_url` 为
`/finance/invoices/requests/IR202608292035253C7C`，由 Workflow 侧自派生
（即 MR !36 修复死锁时改动的那条路径）。

**这是该链路在生产的首次完整端到端执行。** 走查任务书要验证的
「自动编排是否真的自动」，至此有了肯定答案。
