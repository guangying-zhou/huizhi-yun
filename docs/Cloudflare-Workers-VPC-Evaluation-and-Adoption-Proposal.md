## 1. 建议结论

**Workers VPC 值得纳入汇智云的技术观察清单，但当前不落地，也不作为 ADR-017、ADR-018、ADR-019 的实施前置条件。**

若正式能力、费用和客户网络条件满足要求，优先考虑将其用于：

**Cloudflare 上的 Enterprise Host／必要的服务端协议门面 → 客户侧 Tenant Runtime 的私有 HTTP(S) API。**

推荐的候选组合是 **VPC Services＋Cloudflare Tunnel**：Tunnel 提供网络连接，VPC Service 将 Worker 的连接目标约束到正式登记的服务；Runtime 继续承担业务、授权、事务和数据访问。两者在该路线中配合使用，不是互相替代。[CF01][CF04][CF06]

不把“网络已经私有可达”解释为允许平台直连客户数据库，不将 VPC Networks 的广泛网络访问作为默认方案，也不强制纯本地部署经 Cloudflare 绕行。

### 1.1 当前允许与不允许的工作

| 当前可以做 | 当前不做 |
| --- | --- |
| 归档本方案，在既有架构评审中按需更新公开资料 | 新增 VPC adapter、提前重构 Runtime client、提交默认关闭但生产可达的接线 |
| 在收到正式能力或价格变化信息后人工复核 | 创建 Tunnel／VPC Service／Network、绑定 Worker、申请客户网络权限 |
| 记录未决问题、潜在客户需求及后续成本输入 | 修改 DNS、开放或关闭网络端口、更换证书、升级客户 `cloudflared` |
| 保持现有项目按已批准范围继续推进 | 调整 grants、服务身份、OIDC issuer／回调、路由或生产数据 |
| 将“不采用”保留为正常评审结论 | 以本方案为依据启动概念验证、购买套餐、迁移数据库或退役旧入口 |

**“保留候选路线”只发生在文档层，不要求现在预留代码、创建资源或安排上线日期。** 本文也不建立自动跟踪、提醒或监控任务。

## 2. 依据、范围与证据边界

### 2.1 已有项目边界

本方案依据本轮对话提供的架构材料，只沿用其中与网络接入直接相关的约束，不将材料中的历史状态当作当前部署回读结果。

| 已有约束 | 对本方案的影响 | 依据  |
| --- | --- | --- |
| 企业数据及认证权威由客户侧 Runtime 承载；平台 UI/BFF 不持有租户数据库与长期密码学私钥 | VPC 的目标是 Runtime API，不是数据库或 Vault 表 | [P01] §2.1～§2.4 |
| Host → Runtime 是真实信任边界 | 更换网络路径后，服务身份、用户委托、租户绑定、scope 和撤销检查继续执行 | [P02] §3.2 |
| 统一租户业务库不取消领域责任，不允许 Nuxt 获取数据库凭据 | 不引入 VPC／Hyperdrive 直连客户数据库的旁路 | [P02] §4.1～§4.2 |
| 统一前端、Auth 迁移与物理合库可以分阶段完成 | VPC 单独评估，不捆绑当前业务整合发布 | [P03] §2、§10 |
| 每个对象保持唯一权威写入方，旧新入口共享稳定操作身份 | 更换传输不改变 Runtime、幂等回执和业务数据事实源 | [P01] §4；[P02] §6 |

[P03] 的导航名称在后续版本中有调整，本方案不修改或重述这些名称，也不改变人力资源独立等已确认决策。

### 2.2 三类内容必须分开理解

**官方当前事实**仅指 §3 及引用资料在 2026-09-20 可核对的内容；正式上线后必须重新核验。

**项目候选设计**是本文针对汇智云的建议，包括传输适配、账户边界、成本模型、测试与放行标准，不是 Cloudflare 已替项目提供的保证。

**尚待验证事项**包括跨账户接入、共享 Worker 的规模化绑定、客户实际网络、性能、正式费用和协议兼容。本次没有运行 Worker、Tunnel、客户 Runtime、负载测试或真实账单核对，也没有重新审查远端分支的完整运行路径。

## 3. 当前能力快照及 Tunnel 的区别

### 3.1 官方资料快照

| 事项  | 本次核对结果 | 后续如何使用 |
| --- | --- | --- |
| 产品状态 | Workers VPC 官方仍标记 Beta；功能和 API 可能在正式上线前改变 | 不作稳定接口或生产保障承诺 [CF01] |
| 收费  | Open Beta 期间 VPC 自身免费；Worker 计算及请求仍按标准计费 | 不能据此估算正式期费用，也不等于整条链路免费 [CF02] |
| VPC Services | 绑定登记的目标主机与端口，通过 Tunnel 访问私有服务 | 作为首选候选 [CF04] |
| VPC Networks | 可访问所绑定 Tunnel 或 Mesh／WAN 范围内的多种目标，运行时地址决定目的地 | 访问范围更宽，不作为本项目默认方案 [CF05] |
| VPC 的 Tunnel 条件 | 当前要求 `cloudflared` 2025.7.0 或以上、实际使用 QUIC，允许出站 UDP 7844 | 正式期重新核验；现阶段不据此修改客户网络 [CF06] |
| 当前规模限制 | 每 Cloudflare 账户 1,000 个 VPC Services；仍受相关 Workers 请求限制约束 | 不是每 Worker 可绑定 1,000 项，也不是 1,000 个客户的容量保证 [CF03] |
| API 路由语义 | VPC Service 的登记决定实际连接目标；`fetch()` 主机用于 HTTP Host／HTTPS SNI，URL 端口不决定连接端口 | 未来适配必须分别核对连接目标与请求协议身份 [CF07] |

以上是资料快照，不是最终选型参数。正式期 API、套餐、限额、网络要求等均以重新核验的资料和批准合同为准。

### 3.2 不是“Tunnel 是公网、VPC 是私网”

Tunnel 由客户侧 `cloudflared` 主动建立出站连接；源站无公网 IP、无需开放互联网入站端口，本来就是 Tunnel 的能力。Tunnel 既有公开应用发布场景，也有私网连接用途。[CF08]

| 方式  | 主要作用 | 本项目如何评价 |
| --- | --- | --- |
| 现有正式 HTTPS API 路径，可包含 Tunnel 的公共域名发布及相应保护 | 使用可访问的 API 地址调用 Runtime | 当前继续使用已批准方案；本次不推定每个租户实际使用同一种拓扑 |
| VPC Service＋Tunnel | Worker 通过绑定访问特定私有后端，不必为该后端调用另设公开主机名 | 可能减少后端公共入口与配置负担，收益须用现有基线对比 |
| VPC Network＋Tunnel／其他接入方式 | 为 Worker 提供较宽网络范围内的动态访问 | 仅在明确需求与额外控制成立时另行评估 |

仅创建 VPC Service 不会自动撤销现有公共域名、关闭其他网络路径，或证明原 Access／WAF 规则在新链路继续执行。**是否减少实际暴露面，取决于未来调用方盘点、控制迁移和旧入口退役。**

普通 Tunnel 的自动协议选择允许在不能使用 UDP 时回退到 HTTP/2；VPC 当前要求 QUIC，因此“原 Tunnel 正常”不足以证明 VPC 可用。[CF09][CF06]

## 4. 预期收益与不解决的问题

以下为项目判断，不是已测量结果。

| 潜在收益 | 成立条件 |
| --- | --- |
| 减少客户 Runtime 的公共主机名和公开入口 | 所有需要保留的调用方已迁移或有正式独立入口；旧入口经过批准退役 |
| 将 Worker 网络访问限定到明确 Runtime | 服务登记、绑定权限、目标变更和 Runtime 身份核验共同生效 |
| 统一客户部署的服务接入描述 | 账户、租户、环境、实际服务之间具有可管理的映射，不为每个菜单复制服务 |
| 减少部分证书、DNS、外部入口维护 | 必须核算新增的 Tunnel、绑定、发布和支持成本，不能预先认定净收益为正 |

它不解决当前菜单和页面状态问题，不替代业务合库、授权整改和跨域事务，不自动提升客户网络或数据库可用性，也不承诺请求更快。

**平台侧 BFF 仍可能处理经授权的明文请求与响应。私有接入不等于平台端到端不可见，也不等于专线或离线能力。** 若某类客户要求平台托管前端完全无法接触明文，那是另一项信任与交付设计，不由 VPC 单独解决。

## 5. 若将来采用，建议的目标接入方式

本节以下均为未来候选，不代表当前已批准实施。

### 5.1 首选链路

```text
企业浏览器
    → 汇智云 Tenant Gateway
    → Enterprise Host／获准的服务端调用方
    → 既有 Runtime 客户端：正式 operation、服务身份、用户委托、幂等及审计
    → 经过租户／环境／部署绑定的 VPC Service
    → Cloudflare Tunnel
    → 客户侧 cloudflared
    → 同一客户侧 Tenant Runtime 的 HTTP(S) API
    → 原有权威数据库／安全域存储
```

浏览器继续使用汇智云正式页面；首轮只评估服务端到业务 Runtime 的传输，不调整浏览器认证协议或数据库。

客户同一环境中多个业务模块若由同一个 Runtime 入口承载，可评估共用这个网络服务目标；API 级权限仍由 Runtime 处理。实际独立的安全服务、端口或信任边界不能为了减少绑定而强行合并。

### 5.2 场景优先级

| 场景  | 候选处理 |
| --- | --- |
| Host → 客户业务 Runtime HTTP(S) | 首个未来试点，先只读，再受控写入 |
| Console 协议门面 → 客户 Auth／Directory Runtime | 后续单独评估；认证冷启动、撤销和恢复通过后再决定 |
| 调度、回调、Connector → Runtime | 按实际调用方逐条评估，不因普通页面 API 接通就宣布覆盖 |
| 私有 GitLab、对象存储及其他客户服务 | 有明确需求时单独登记，保留集成责任和原业务规则 |
| 编辑器、WebSocket、SSE、大文件与长任务 | 不纳入首次试点，须有具体协议、限制、恢复和费用证据 |
| Worker → Worker | 保留已批准的内部调用方式，本方案不要求改成 VPC |
| 客户内网的自托管 Host → Runtime | 保留受控内网或 loopback 路径，不强制依赖 Cloudflare |
| Worker → 客户数据库 | 不采用；不能绕过 Runtime [P01][P02] |

### 5.3 默认排除的做法

不为每个前端业务菜单创建一条 Tunnel；不为节省服务登记而将客户整个内网开放给共享 Worker；不把 VPC Service ID 当成租户身份；不将外部用户提供的 URL、Host、端口或 binding 名称作为可信目的地。

不把 VPC 免费期作为取消现有连接方案的理由，也不为了引入它提前拆分共享 Host、重写 Runtime 或迁移文档存储。

## 6. 多租户与 Cloudflare 账户方案

### 6.1 必须验证的绑定链

建议未来将以下信息纳入现有部署登记的受控扩展，而不是新建另一个独立网络控制平台：

```text
已验证 tenant + environment + runtime deployment + 正式调用服务
    → 当前批准的传输模式与配置版本
    → 对应 Cloudflare 账户中的服务／binding 引用
    → Tunnel 与客户侧正式目标
    → Runtime 自身再次验证租户、部署、调用方及动作
```

映射在请求级解析；缓存按适用租户、环境、部署及版本隔离，禁止使用全局可变“当前租户 binding”。目标不同但内网 IP 相同的客户必须通过明确绑定隔离。

VPC Service 的实际目的地不随 `fetch()` URL 的主机改变。因此，单纯将现有 `runtimeEndpoint` 改成客户私网 URL，不是完整接入方案。[CF07]

### 6.2 账户模式暂不选定

| 候选模式 | 可能的优势 | 必须先解决的问题 |
| --- | --- | --- |
| 平台账户管理 Worker 和相应连接服务，客户运行 connector | 便于统一发布与配置治理 | 客户认可的管理权限、单方断开方式、平台可影响范围、共享 Worker 绑定规模与账单归属 |
| 客户账户内放置 Worker 与连接资源 | 账户和基础设施控制可归客户 | 前端发布、运维授权、成本分散及客户支持复杂度；不能因此无授权改变部署模式 |
| 平台 Worker 与客户账户资源跨账户连接 | 可能兼顾统一运行与客户控制 | **本次未取得足以确认该跨账户模式完整受支持的官方依据**；必须获得正式支持说明并测试，不假定填写他方 Service ID 即可 |

跨账户尚未确认，不等于断言 Cloudflare 永远不支持；它是正式期的重要观察与采用前问题。

### 6.3 共享 Host 的额外门槛

正式评审需要核对每账户服务上限、每 Worker 绑定及配置容量、租户新增是否触发共享 Worker 重发、发布影响范围、环境隔离与撤销时效。**账户服务总数未超限，不代表共享 Host 的绑定与发布模型已经可规模化。**[CF03]

如果只有将所有客户网络聚合到一个广泛 binding 才能满足规模，不能直接认为问题已解决；应重新评估风险、正式支持方案和成本，必要时不采用。

## 7. 将来的最小技术改造范围

只有正式批准试点后，才按届时源码定位实施点。以下是职责层次，不是待立即执行的代码清单。

### 7.1 在集中传输层适配，不散落到业务 Handler

```text
业务 Handler
    → operation / capability / actor / receipt / trace
    → Runtime 请求准备和协议校验
    → 按受控部署配置选择传输
         · 现有正式 HTTPS 路径
         · 候选 VPC Service binding
         · 已批准的自托管内网路径
    → 同一个 Runtime 业务接口
```

不得由各模块分别挑选 binding、建立一套重试规则或复制签名逻辑。未使用 VPC 的部署应保持现状，不要求为了插件完整性同时实现所有传输方案。

普通用户 API、认证协议、后台任务和外部回调可能具有不同调用上下文；在移除任一公共入口前，必须盘点全部调用方。不能只修改浏览器 BFF 的路径就宣布 Runtime 已可完全转为私有服务。

### 7.2 需要冻结的最小契约

| 契约内容 | 建议约束 |
| --- | --- |
| 目的地 | 服务端配置绑定 tenant、environment、deployment、账户与服务引用；缺失或不匹配即失败 |
| 请求  | 保留正式方法、路径、body、签名覆盖字段、scope、actor、幂等键和 trace；不转发未经审查的浏览器头 |
| Host／TLS | 固定允许的协议、Host、SNI 和目标端口配置；禁止任意虚拟主机或重定向扩大访问范围 |
| 超时与取消 | 沿用业务 deadline；适配后验证取消、流式消费和超时，不把超时解释为业务未提交 |
| 响应与错误 | 保留业务 401／403／409／503 等原语义；网络不可达不得伪装为成功、空数据或零金额 |
| 配置版本 | 纳入现有发布清单与迁移登记；不与业务库 writer generation 混为一个无区分的开关 |
| 降级  | 缺 binding、目标错配、证书错误默认失败关闭；不自动降级为数据库直连或未受保护公共入口 |

API 当前要求绝对 URL，并支持方法、头、正文和取消信号；具体能力仍须正式期重新核验，不能只因方法名同为 `fetch()` 就认为与现有传输完全等价。[CF07]

### 7.3 不改变认证协议身份

网络连接地址与 OIDC issuer、audience、JWKS、callback 等协议身份必须分别处理。引入 VPC 不自动重命名这些协议地址，不将私网 Host 随意替换进已签发令牌。

网络映射与必要工作负载身份不能依赖“先完成一次用户登录后才能得到配置”，否则可能造成 Auth 冷启动循环。保留独立引导信任链；Tunnel 管理凭证不是 enrollment 身份，也不是业务访问授权。[P01] §2.4

## 8. 安全、运行与数据责任

### 8.1 必须持续成立的规则

| 边界  | 规则  |
| --- | --- |
| 应用授权 | binding 只提供网络访问能力；Runtime 仍验证用户委托、服务身份、租户／部署、scope、对象和字段 |
| 数据访问 | 不向 Worker/BFF 提供数据库 DSN、账号、签名私钥或 Vault 主密钥；不新增 SQL 代理 |
| 网络最小权限 | VPC Service 只登记必要目标；客户侧 connector 及其网络可达范围也应受控，不能依赖服务名称实现隔离 |
| 运维权限 | 管理 Tunnel、修改服务目标、绑定 Worker、管理业务角色分别授权；平台支持继续使用租户批准的受控 API |
| 凭据保管 | connector 运行凭证在获准客户部署中保管；Cloudflare 管理凭证只供受控部署流程使用，不下发浏览器或混入业务配置 |
| 日志  | 记录脱敏 trace、传输模式、配置版本、阶段耗时和错误分类；不记录 Token、Cookie、秘密或完整敏感正文 |
| 目标变化 | Tunnel／Service ID 不变时，底层目标仍可能变化；目标修改需审计，Runtime 身份核验和 TLS 仍不可省略 |

### 8.2 TLS、网络与已有控制的迁移

当前文档说明：HTTPS 保护 `cloudflared` 到目标服务的连接，HTTP 在最后一段为明文；当前默认 `verify_full`，信任公开 CA 或 Cloudflare Origin CA。[CF04]

项目候选策略是：跨机器或网段优先 HTTPS 并保留完整校验；同机 loopback 是否允许 HTTP 单独评审。不以 `disabled` 或跳过主机名验证来解决私有 CA、域名或证书配置问题。客户使用私有 CA 时，须在正式期明确受支持的做法。

原公共入口使用的认证、限流、审计、请求大小限制及其他保护，逐条确认在新路径由谁承担。未证明等价前，不关闭原保护，也不宣传新链路自动继承所有 Cloudflare 安全产品策略。

客户断开 connector 或撤销访问时，应有可验证的效果、负责人和恢复流程；“客户可控”不能只停留在部署位置描述。

### 8.3 可用性与不确定写入

Tunnel 副本不是 Runtime 或数据库高可用的替代。官方当前把副本定位于连接高可用，且提醒缩容可能中断既有连接。[CF06]

未来测试应将 Cloudflare 故障、客户出口网络故障、Tunnel 故障、Runtime 故障和数据库故障分别注入。若新 VPC 与旧 HTTPS 路径共用同一 Tunnel 或出口，它们具有共同故障点；“回退旧 URL”不应被描述为独立灾备。

对于写请求，连接异常或响应丢失可能发生在提交后。传输层不得重新生成幂等键并切换路径重发；应使用正式操作身份、回执查询和既有恢复规则。影子对比只用于获准的读取，不复制真实写请求。[P02] §6

## 9. 正式上线后的重点观察清单

建议按事件驱动人工复核：目标能力正式上线、正式价格／套餐发布、关键 API 或限制变化、客户出现明确需求时再更新。本文件不承诺自动持续监测，也不安排当前开发人员为观察专门实施改造。

| 编号  | 观察主题 | 需要拿到的证据 | 未满足时的处理 |
| --- | --- | --- | --- |
| OBS-01 | 正式状态与兼容承诺 | **目标 VPC Services 能力**的 GA 公告、接口／配置兼容及变更政策 | 保持 Deferred；其他 Cloudflare 产品 GA 不算通过 |
| OBS-02 | 正式费用与套餐 | 可用于目标账户、地区和用途的正式价格或报价，最低消费、附加产品、超额和调价条款 | 不批准采用，不把未知费用按零计算 |
| OBS-03 | 账户与客户治理 | 单账户／跨账户的明确支持方式，资源归属、委托权限和客户撤销方法 | 仅考虑已证明可行的模式，或不采用 |
| OBS-04 | 租户规模 | 账户服务数、每 Worker 绑定／配置限制、批量发布和撤销行为 | 不以扩大网络权限来绕过未知限制 |
| OBS-05 | 客户网络 | 正式期 Tunnel 协议、版本、出口条件；目标客户实际连接与重连证据 | 不适合的客户继续原正式方式 |
| OBS-06 | HTTPS 与请求语义 | Host/SNI、证书、头部、签名、body、取消、重定向、状态码和超时行为 | 缺关键合同即不进入生产试点 |
| OBS-07 | 特殊协议 | 所需 WebSocket／SSE／流式上传下载／长任务的明确限制与恢复方式 | 可限定为普通 API 采用，不借需求扩大首批 |
| OBS-08 | 可用性与支持 | 适用支持级别、故障排查、SLA 是否存在及覆盖范围、维护与故障公告机制 | 按客户等级评估，不能用 Workers 的承诺直接替代 VPC 的承诺 |
| OBS-09 | 数据和日志处理 | 所用链路与附加产品的处理区域、日志内容／保留期及客户要求的对应说明 | 不作未经核验的地域、合规或不可见保证 |
| OBS-10 | 运维与退出 | 资源导出、配置版本、撤销、回退、账单归属和供应商退出方案 | 运维与退出成本无法控制则不采用 |

**正式上线只是重新评审的触发条件，不是采用结论。** 服务能稳定使用但价格不适合、费用清楚但账户模型不适合，均可选择继续观察或不采用。

## 10. 收费与总成本评估方法

### 10.1 当前不填写未来单价

本次官方价格页仅确认 Beta 免费及标准 Workers 计费，未给出可据以完成正式采用测算的 VPC 正式期价格。[CF02]

下列维度是汇智云需要询价和核对的候选字段，**不是断言 Cloudflare 将同时按这些维度收费**。

| 核对项 | 需要确认的内容 |
| --- | --- |
| VPC 自身收费 | 是否按请求、流量、连接、服务数、账户或其他维度计费；实际维度以正式政策为准 |
| 套餐门槛 | 是否需要特定 Workers／Zero Trust／企业支持套餐，哪些费用是必选、哪些是可选 |
| 使用量计算 | 请求方向、计费单位、失败／重试／健康检查是否计费，阶梯和免费额度怎样共享 |
| 关联网络费用 | 云厂商出口、客户带宽、连接实例和冗余是否产生新增成本 |
| 平台成本 | Worker 请求／CPU、监控、日志、管理脚本及资源变更成本的实际增量 |
| 商务条款 | 最低承诺、地区和币种、税费口径、涨价通知、取消与停用后的收费 |
| 客户归属 | 平台账户集中承担还是客户账户承担，能否合理按租户归因 |

### 10.2 比较完整方案的增量成本

建议按同一业务量、同一可靠性与安全要求比较：

```text
新方案月度总成本
  = 按正式政策计算的 VPC 费用
  + Workers 及必需配套服务成本
  + 客户侧 connector／网络／冗余资源成本
  + 监控、维护和支持成本

月度净变化 ΔC = 新方案月度总成本 − 现有正式方案月度总成本

评估期总变化 = 一次性改造、验证、交付及退出准备成本 + 各月 ΔC 之和
```

两种方案已经共用的 Worker 或 Tunnel 成本应按相同口径计入，不能重复算成新增费用；可能节省的公共入口维护费用只有确实可取消时才扣除。美元／其他币种及含税／未税口径不得混用。

收益至少分为“安全与客户交付必要性”和“可量化维护节省”两类。为了满足明确客户安全要求，可以批准合理的净增成本，但必须记录预算与理由，不强行把它描述成省钱项目。

### 10.3 测算输入与压力场景

| 输入  | 获取方式 |
| --- | --- |
| 拟采用客户及环境数 | 经确认的目标部署清单，不用全部注册租户代替 |
| 每环境实际服务数 | 业务 Runtime、确有独立边界的其他服务分别计算；不按前端菜单数量计算 |
| API 访问量与字节量 | 脱敏基线，包含认证／授权依赖、调度、健康检查、实际扇出与重试 |
| 峰值并发和尾延迟 | 同地区、同客户网络、相同业务动作的对照测量 |
| 运维投入 | 单客户安装、证书／升级、故障支持、发布和撤销的实际工时 |
| 压力情景 | 正常月、明确假设的业务峰值、故障重试月；不得把未测场景写成预测事实 |

服务容量可用 `S = Σ（租户各环境实际登记服务数）＋额外独立登记的冗余服务数` 估算，再单独预留容量余量。connector 副本不应未经核对就按额外 VPC Service 计费或计数。[CF03]

客户级成本和平台共享成本分别展示。预算上限、单位业务量成本和可接受运维增量，在试点批准前填写；未填写表示商业评审未完成。

## 11. 重新评审与采用门槛

建议按两次批准处理：**先决定是否值得验证，再决定是否值得采用。** 不把“批准试点”写成“已经选定 VPC”。

| 门槛  | 必须满足的条件 | 放行结果 |
| --- | --- | --- |
| G0：当前观察 | 本方案归档；现有交付计划照常执行 | 不启动资源创建或代码接线 |
| G1：重新评审 | 目标能力正式上线，正式价格／套餐足以测算；账户与初步适用性有可核验资料 | 人工决定继续观察、不采用或准备试点申请 |
| G2：试点批准 | 明确客户／环境、账户、预算、数据、测试范围、负责人和退出条件；安全无不可接受缺口 | 仅授权隔离验证，不授权生产 |
| G3：限定采用 | 正式能力与费用核对、真实链路验收、可用性／性能／成本达标、客户同意、回退通过 | 仅在批准租户和服务范围启用 |
| G4：扩大或退出 | 观察期证据与账单稳定；规模和运维可接受 | 分批扩大、保持限定范围或退出 |

任何阶段都允许不采用。目标能力 GA 后若价格仍不透明、核心需求仍依赖未经批准的 Beta、或跨租户边界无法证明，继续 Deferred。

不预设 GA 日期、试点日期或正式采用期限。架构、产品／经营与部署／安全责任人共同评审，最终负责人及预算归属届时明确。

## 12. 仅在批准后的候选验证路线

**以下阶段均未启动。步骤是将来执行计划的输入，不是当前任务。**

| 阶段  | 建议范围 | 通过标志 |
| --- | --- | --- |
| V0：正式期复核 | 更新能力、API、价格、账户、网络与限制；形成适用性及总成本对照 | G1/G2 完成，明确批准隔离试点 |
| V1：隔离连接验证 | 专用测试资源、无生产数据，验证固定 Runtime、QUIC、DNS、TLS 与撤销 | 连接成功且错误目标、证书和未授权访问均拒绝 |
| V2：只读业务验证 | 通过正式 Host/Runtime client 访问少量 API，保留真实身份和对象授权；旧链路只作获准对照 | 同一主体同一数据结果一致，性能与日志符合预算 |
| V3：受控写入验证 | 使用测试对象覆盖成功、冲突、超时、提交后丢响应和同键重放 | 不重复写、不丢业务结果，单一权威存储不变 |
| V4：有限采用 | 批准的一个或少量租户／环境／服务；其他路径保持正式旧实现 | 技术证据、账单、支持、回退与客户确认齐备 |
| V5：逐项推广 | 按调用方和服务扩展；Auth／调度／编辑器分别审批 | 不以普通 API 试点结论替代其他协议验收 |

Auth／Directory 的接入应在业务 API 验证之后单列，冷启动、令牌签发、刷新、撤销、密钥轮换及 Runtime 离线均需覆盖。不能为了首批试点先迁移认证权威或更改 issuer。

## 13. 将来最小验收矩阵

| 编号  | 场景  | 必须证明的结果 |
| --- | --- | --- |
| VPC-A01 | 合法用户调用获准业务 | 网络、服务身份、用户委托与对象授权共同成功，不靠匿名健康检查替代 |
| VPC-A02 | 错租户／环境／deployment，或两个租户内网 IP 相同 | 绑定和 Runtime 双重拒绝错配；不发生跨租户数据读取 |
| VPC-A03 | 同一共享 Worker 的并发租户请求 | binding／签名／缓存不串用；失效的旧配置不能悄悄恢复 |
| VPC-A04 | 普通无权、撤权、服务凭证撤销 | 仍按正式语义拒绝；有 VPC 连接不等于有业务权限 |
| VPC-A05 | Host/SNI／证书／DNS／端口错误 | 明确失败，不降级证书校验，不选择其他客户或任意内网目标 |
| VPC-A06 | 隧道断开、Runtime 停止、Cloudflare／客户网络故障 | 错误可分类、脱敏且可恢复，无 DB fallback；共同故障点被明确记录 |
| VPC-A07 | 提交后丢响应与路径切换后的重试 | 同一操作身份返回原结果或可核实状态，不产生第二次 mutation |
| VPC-A08 | 旧新读取对照 | 同主体、相同范围及数据版本下结果一致；动态差异按时间解释，不伪报迁移错误 |
| VPC-A09 | 全部实际调用方 | BFF、协议门面、任务和回调逐项列明；未迁移调用方保留正式入口 |
| VPC-A10 | 性能及资源 | P50/P95、错误率、峰值、超时、CPU／内存、带宽和配置容量达预先冻结预算 |
| VPC-A11 | 凭据与日志 | 无 Token、Cookie、数据库秘密或敏感正文泄漏；管理变更可审计 |
| VPC-A12 | 回退与客户撤销 | 停用新传输后回到仍获准的同一 Runtime；已提交数据和回执保留 |
| VPC-A13 | 费用核对 | 仪表用量／实际账单与模型可解释，正常、峰值和重试情景均在批准预算内 |
| VPC-A14 | 非 Cloudflare 部署回归 | PM2／自托管仍按原边界工作，不被新 binding 依赖阻断 |

性能阈值优先复用现有发布基线；需要新增的阈值必须在测试前批准，不能测完以后为通过而调整。首次真实账单有结算滞后时，应明确额度和未确认风险，不把估算标成最终账单。

## 14. 切换、回退与退出原则

未来部署只切传输路径，不迁数据库、不改变领域写入方。每次切换记录租户、环境、调用方、旧新传输、配置版本、批准人与适用时间，保留相关发布制品。

**不自动故障降级。** 已选 VPC 发生异常时，先按既有失败语义处理；是否切回原 HTTPS 必须是预先批准的运维操作，目标仍为同一权威 Runtime，并核实原路径仍具备相同认证与保护。

**不双发写请求。** 切换时关注在途请求、操作回执和允许的幂等重试。传输回退不回滚已提交业务数据，也不重置 receipt、outbox 或调度所有权。

**不提前删除公共入口。** 先盘点 OIDC 协议、外部 webhook、定时任务、旧版本应用、运维与客户集成等调用方，逐项验证去向。公开的 issuer/JWKS/callback 与业务私有 API 可以有不同生命周期，不能一并删除。

**退出现有 VPC 连接也须有顺序。** 先恢复获准的正式调用路径、确认在途操作，再撤销相应 binding 和资源；保留必要审计，不保留无用网络权限或持续计费资源。成本失控、供应商政策变化、客户网络不适合或退出要求成立时，可以退出，不视为架构失败。
