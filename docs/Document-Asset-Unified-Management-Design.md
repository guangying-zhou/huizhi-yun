## 1 目标与结论

目标是把平台内的文档作为一类统一管理的资产：一处登记、版本可追溯、权限一致，并能被后续的 AI 检索安全地使用。

结论：

1. **不把 OSS 文档镜像进一个 Git 仓库。** 仓库的权限粒度是整库，无法承载逐份文档的权限；二进制文档不适合入仓；会形成两套版本并且无法干净删除。
2. **以 Codocs `documents` 为统一文档目录**，存储位置作为独立维度，同时支持 OSS 与 GitLab 仓库。
3. **文档归属按业务口径分层**：公司、部门、项目集/产品线、项目、个人。GitLab 群组与仓库只属于存储维度，不决定谁能访问。
4. **GitLab 文档在平台内只读。** 平台不向仓库写入或提交；仓库文档的修改在 GitLab 中按代码流程完成。既有的“在 Codocs 编辑并提交 GitLab 项目文档”能力废弃。
5. **AI 使用的是派生索引**，查询时按提问人的实时权限过滤，不直接读取存储。

### 2.3 GitLab 相关

- Foundation `gitIntegration` 经 Console 集成配置（`gitlab.default`）提供读文件、读目录、读提交，以及写入用的 `createGitCommit`、`resolveGitCommitActions` 和 `upsertGitIssue`（工作项与 GitLab Issue 关联）。
- 旧 Codocs 项目文档有 GitLab → OSS 同步与 OSS → GitLab 提交两个编排；按既定决策，旧 Codocs 项目文档不迁入 Enterprise。
- Enterprise Host 侧目前只有读：仓库绑定、按固定 commit 读取、需求规格导入。
- Console 项目注册表有 `project_type`（group/project/template）与 `repo_url`；Aims `project_portfolios` 有 `git_group`。

### 2.4 缺口

1. 需求规格、项目周报、两类附件不在主表。
2. 仓库来源的项目文档只在 Aims 有记录，主表没有。
3. 文件柜文件未转存时没有文档记录，不可检索。
4. 没有全文或语义索引，也没有文本抽取流程。
5. 权限口径两套并存（关系索引与访问策略），Aims 另有镜像字段。
6. `doc_type` 的 `git-project` 把归属和存储混在一起；"项目组"一词在不同位置含义不同。
7. 项目集没有成员关系，项目集归属的文档目前在 Host 上固定拒绝写入。

### 2.5 提交接口核查结果（2026-10-03，仅静态核对源码与授权种子）

调用链：浏览器 → 任一继承 Foundation 的应用的 `/api/git-integration/commit` → 该应用自己的服务身份 → Runtime `/v1/console/service/integrations/{code}/gitlab/commit` → GitLab。

| 环节 | 现状 |
| --- | --- |
| Foundation 处理器 | 只经登录中间件；处理器内没有任何人员权限、项目范围或仓库绑定检查。仓库、分支、文件动作、作者姓名与邮箱全部取自请求体；同目录的四个读取接口同样没有人员授权 |
| 幂等键 | Runtime 要求 `Idempotency-Key`，Foundation 直接取浏览器请求头，调用方可自带 |
| Runtime | 只校验服务令牌的 `integration_operations:execute` 与该服务客户端的操作白名单；不知道是哪个用户，也不限制仓库或路径 |
| 授权种子 | `gitlab.commit` 在 Aims 与 Codocs 服务客户端的白名单内；Enterprise 不在 |
| Enterprise Host | 该路径未登记为 Host 路由，且 Enterprise 身份无此授权，不可用 |

结论：**在独立 Codocs（以及未处于仅调度模式的独立 Aims）上，任何已登录用户都可以借应用的服务身份，向 GitLab 集成令牌可写的任意仓库提交内容，并可填写任意作者。** 这是一个越权写入缺口。未在任何环境发起请求验证；网关是否对独立应用按前缀整体转发、目标环境的实际授权是否与种子一致，需在环境中只读确认。

处置见 §6。

## 3 归属模型

### 3.1 三个独立维度

| 维度 | 字段 | 回答的问题 |
| --- | --- | --- |
| 业务归属 | `doc_type` | 这份文档属于哪一层 |
| 归属对象 | 所有者、部门、项目集/产品线、项目的稳定编码 | 具体属于谁 |
| 存储 | `storage_type` + 定位信息 | 内容实际放在哪 |

### 3.2 归属层级

| 层级 | 归属对象 | 参与人员来源 |
| --- | --- | --- |
| 公司 | — | 全员或指定范围 |
| 部门 | 目录部门 | 部门成员 |
| 项目集 / 产品线 | `project_portfolios` / 产品工作区 | 负责人与成员（项目集成员待建，见 §5） |
| 项目 | Aims 项目 | 项目成员 |
| 个人 | 用户 | 本人及分享对象 |

约定：

- **"项目组"一词在文档体系中停用。** 原"项目组文档"按实际归属记为项目集、产品线或项目。
- 项目集与产品线是同一层的两种对象：产品研发类归产品线，其它归项目集；一份文档只挂其中一个。
- GitLab 群组不是归属对象。项目集可登记 `git_group`，它只用于确定存储位置。

### 3.3 `doc_type` 规范

- `doc_type` 只表达业务归属，不表达存储。
- `git-project` 停用：拆为"归属=项目"与"存储=git"。
- 存量 `project`：按 `project_code` 对应的是项目还是项目集判定归属层级。
- 兼容期内读取时映射旧值、写入只写新值；兼容期结束条件是直接判断旧值的代码路径归零。
- **实施约束（2026-10-04 代码核对）**：`git-project` 目前不只是分类标签，它还是存储判别条件——Codocs 以它决定使用“项目文档桶”还是“文档桶”（`codocs/server/utils/oss.ts` 及版本、下载、质量评审等读取路径），Runtime 另有约 8 处按 `project`/`git-project` 成对筛选。因此在 `storage_type` 落地之前不能改写存量取值或停止写入该值；取值映射必须与 DOC-06 同批完成。

## 4 存储模型

### 4.1 `documents`

| 字段 | 说明 |
| --- | --- |
| `storage_type` | `oss`（默认）/ `git`；预留 `inline`、`external_url` |
| `storage_locator` | JSON。`oss`：桶、对象路径。`git`：集成代码、仓库、文件路径、跟随的分支 |
| `oss_path` | 保留给 OSS 文档；改为可空，Git 文档不写伪路径 |

仓库路径本身包含群组前缀，定位信息里不单独存群组。

### 4.2 `document_versions`

- 增加通用的版本定位：OSS 用现有 `oss_version_id` / `object_key`；Git 用 commit ID。
- `content_sha256` 两种存储都填写，作为跨存储统一的内容指纹，用于索引、去重与一致性校验。

### 4.3 两种存储的能力差异

| 能力 | OSS | Git |
| --- | --- | --- |
| 读取、预览、检索、被业务对象引用 | 支持 | 支持 |
| 在线协作编辑、快照发布 | 支持 | 不支持 |
| 版本 | 平台版本号与快照 | commit；可固定或跟随分支 |
| 写入 | 平台保存 | 不支持；平台内只读 |

规则：

1. 能力差异由服务端按 `storage_type` 判断，页面据此显示或隐藏入口。
2. 权限一律以平台的关系与策略判定。仓库自身的权限不作为放行依据；读取仓库使用集成凭证，且先通过平台判权。
3. 评审、基线和业务引用使用固定 commit；日常浏览可跟随分支，并显示当前 commit。
4. 不支持原地切换存储。需要时新建记录并保留来源关系。

### 4.4 收敛其它模块

- Aims `project_documents` 的 `repo_project_code`、`repo_file_path`、`repo_commit_id` 收敛为引用一条 `storage_type=git` 的主表文档。
- 已基线的需求规格版本、已发布的项目周报在主表补登记：内容留在原处，主表保存引用与版本锚点。
- 工作项附件、财务附件本阶段不纳入。是否纳入知识库另行决定。
- 文件柜文件不强制转存；可抽取文本的类型直接进入派生索引（§7）。

## 5 项目集/产品线的人员与权限

1. **项目集成员**：参照 `product_members` 的结构新增项目集成员关系（角色 manager/contributor/viewer、生效与失效时间、修订号）。产品线直接复用产品成员。
2. **授权合同**：项目集文档的人员资源、动作与数据范围在 Aims manifest 中定义；服务端判权使用 Foundation 统一授权 helper，不在业务模块复制算法。
3. **继承规则**（用户 2026-10-04 决定）：
   - 项目集/产品线成员可读本层文档。
   - 组内各项目的成员**默认可读**项目集/产品线文档；文档策略可逐份关闭。
   - **密级 L2 及以上不继承**：L2、L3 文档只有项目集/产品线成员本身可见，不因组内项目成员身份开放。
   - 继承只授予读取；编辑、删除、授权仍限项目集/产品线的相应角色。
4. **权限口径**：以 Codocs 的关系索引与访问策略为唯一判定来源；Aims 的镜像字段只用于展示。
5. 成员关系与授权合同落地后，再放开 Host 上项目集归属文档的写入（当前固定返回 409）。

## 6 GitLab 只读与写入能力的废弃

决定：平台对 GitLab 文档只提供读取（目录、文件、提交记录与差异、按固定 commit 引用）。不在平台内编辑或提交仓库文档，也不提供“发布到仓库”。

理由：

- 仓库文档与代码共用分支、合并请求与保护规则；平台用集成令牌代提交，会绕过这些规则，提交人也无法对应到真实的 GitLab 账号。
- 两处可写带来冲突与“哪个是正式版”的问题，而需求基线、评审引用只需要固定 commit 的只读内容。
- 现有提交通路存在 §2.5 所述的越权写入缺口；废弃写入比为它补齐完整的授权、路径限制与审计更简单，也更安全。

需要落实的事项：

1. 删除 Foundation `/api/git-integration/commit` 与 `createGitCommit`、`resolveGitCommitActions` 的对外入口；删除旧 Codocs 的 `gitlab-submit` 编排与页面入口。
2. Runtime 的 GitLab 固定操作移除 `commit` 与 `resolve-actions`；Console 授权白名单移除 `gitlab.commit`、`gitlab.resolve-actions`。授权变更属于环境写入，需按约定取得批准并做签发与反例验证。
3. **GitLab 集成令牌保留写权限，不降为只读**（用户 2026-10-04 决定：后续仍需通过平台提交 Issue，即保留 `issue-upsert`）。仓库内容只读由平台代码层保证，见下方“残余风险”。
4. 四个读取接口补人员授权：服务端按项目范围与仓库绑定判定，浏览器不能指定任意仓库；Host 侧继续使用已有的“绑定仓库 + 固定 commit”读取路径。
5. 存量：旧 Codocs 中 `gitlab-sync` 写入 OSS 的仓库文档副本，按 §4.4 改为 `storage_type=git` 的只读引用，或保留为历史副本并标注来源 commit；不再回写仓库。

### 残余风险（令牌保留写权限）

集成令牌本身仍然可以写仓库。“平台不写仓库”的保证不在凭证上，而在两处代码与授权边界：

- Runtime 的 GitLab 固定操作白名单：只含只读操作与 `issue-upsert`，令牌只在 Runtime 内使用，不下发给业务应用或浏览器。
- Console 对各服务客户端的操作授权：只列出允许的固定操作。

由此得到三条约束：

1. **不得再新增任何写仓库内容的固定操作**（提交、推送、分支、合并请求、文件写入等）。确有需要时必须先修订本设计并取得用户决定，不能作为普通功能迭代加入。现有契约测试（Runtime 白名单、Foundation 枚举、Console 授权脚本）是防回退的门，修改这些测试等同于修改本约束。
2. `issue-upsert` 只能写 Issue；实现不得接受可改变目标为仓库文件或分支的参数。
3. 令牌一旦泄露，影响范围是它在 GitLab 上的全部权限。现状（2026-10-04 核查）：集成账号 Wiztek Bot 在 platform、product、huizhi-yun 三个群组以及 huizhi-yun/account、huizhi-yun/codocs 两个直接项目上均为 Maintainer；同一令牌还被 Platform 控制面用于只读读取 release、tag 和文件；CI 不使用它。**收窄措施已决定、暂缓执行，由用户择时自行在 GitLab 上调整（DOC-02）**：把该账号在各项目上的角色设为 Reporter——可读取代码、创建和更新 Issue，但不能推送。执行时先记录原角色（回退依据），选一个项目验证读取与 Issue 回写正常且推送被拒，再批量调整；并确认 Platform 的只读读取不受影响。

如将来确有“从平台生成内容进入仓库”的需求，按新能力单独设计：以用户本人的 GitLab 身份发起合并请求，而不是用集成令牌代写。

## 7 AI 派生索引

1. **来源**：只索引生命周期为 formal、具有内容哈希的版本。草稿默认不入索引。
2. **抽取**：Markdown 直接切片；docx、pdf、pptx、xlsx 抽取文本后切片；无法抽取的类型只登记元数据。
3. **片段标注**：文档 `uuid`、版本、内容哈希、归属、密级。
4. **查询**：先按提问人的实时权限过滤候选片段，再交给模型；回答附文档与版本出处。
5. **一致性**：索引是可重建的派生物。文档删除、撤回、降级或权限收紧时，对应片段同步失效；不得以索引缓存替代实时判权。
6. **边界**：索引服务不持有可绕过平台权限的全量读取凭证；密级 L3 是否入索引需单独决定。

本节是新能力，索引的部署位置、模型选择、增量与删除同步机制另行立项设计。

## 10 后续方向（用户设想，2026-10-04，暂不实施）

**项目集/产品线文档进入文档的项目空间。** 设想：

- 在文档的项目空间里提供项目集/产品线一级的文档；项目集/产品线负责人可以对**已关联 GitLab 群组**的项目集/产品线显式创建项目集/产品线文档（不是自动为每个项目集建空间）。
- OSS 中新增 `groups` 目录，其下按项目集/产品线分目录存放这类文档。
- 是否在对应 GitLab 群组下创建一个 `group-docs` 仓库用于存储：用户表示“再讨论”，未定。

与现有结论的关系（落实前必须先回答）：

1. **与当前 5b/5c 的关系。** 现在项目集下不能直接新建文档，只能挂入已有文档（用户 2026-10-04 接受）。该设想等于补上“在项目集下直接创建”，前提是 Codocs 有项目集/产品线归属的表示（见实施细化稿 §9.1），应与 DOC-06c/6d 的分类规范一并设计，而不是把项目集编码写进 `documents.project_code`。
2. **归属单位。** 本设计 §5 的结论是以项目集/产品线（业务单位）而不是 GitLab 群组作为归属与授权单位。设想中“已关联 GitLab 群组”只是创建的前置条件；授权仍应来自项目集成员关系，不来自群组成员。两者不一致时以谁为准需要明确。
3. **与 DOC-01“平台不写仓库内容”的关系（待议）。** §6 的结论是 GitLab 文档在平台内只读，平台不向仓库提交。若采用 `group-docs` 仓库存储，就需要平台创建仓库并写入内容，与 §6 直接冲突，且重新引入 §2.5 审计过的提交入口风险（调用方可选仓库、分支与作者）。可选方向：a) 只用 OSS `groups` 目录，不建仓库（与 §6 一致）；b) 建仓库但只由人在 GitLab 侧维护，平台只读引用（与 §6 一致，等同现有“登记文档仓库”）；c) 平台写仓库（需要推翻 §6，并先解决人员授权、作者归属、分支保护与集成账号权限收窄）。在用户讨论确定之前，不实施任何向仓库写入的能力。
4. **存储路径与同名。** `groups/<类型>/<编码>/` 的目录命名需要把归属类型放进路径，避免项目集编码、产品线编码与项目编码同名时互相覆盖或串读。
