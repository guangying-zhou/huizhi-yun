# B-025 方案对比：入站服务令牌 introspection 拿不到租户 runtime

> 提出：2026-08-28 | 来源：[`Altoc-Finance-走查ISSUE清单-2026-09.md`](./Altoc-Finance-走查ISSUE清单-2026-09.md) ISSUE-B-025
> 归属：`foundation/` + `console/` 共享层 | 状态：**已查实，结论见 §5**

---

## 1. 问题收敛到哪一点

B-024 修好后，Altoc → Finance 的请求已能正确到达。Finance 在校验入站服务令牌时
向 Console 做 introspection，拿到 503，整条调用失败。

**不是**「请求到不了 Console」，也**不是**「Console 不认识这个租户」。

生产 tail 实测，Finance 收到的请求头：

```
authorization        ✓
x-hzy-gateway        ✓        x-hzy-gateway-token  ✓
x-hzy-tenant         ✓        x-hzy-deployment     ✓
x-hzy-environment    ✓        x-hzy-actor-uid      ✓
```

`consoleBackendHeaderNames`（`consoleOidc.ts:284-299`）会把上面这些转发给 Console，
且 `isTrustedTenantGatewayRequest`（`platformRuntime.ts:302-318`）的判据是
`x-hzy-gateway: tenant-gateway` + 匹配的 `x-hzy-gateway-token` —— **这个条件是满足的**，
所以 Console 能信任并读到 `x-hzy-tenant`。

**真正缺的是运行时定位信息**：转发链里**没有** `x-hzy-tenant-runtime-url` /
`-token` / `-audience`（及 `x-hzy-data-runtime-*` 等价物）。

而 introspection 的两步都必须读租户 runtime：

| 步骤 | 实现 | 依赖 |
| --- | --- | --- |
| 取 JWKS 验签 | `getPublishedJwks` → `getConsoleOidcPublishedJwks` | 租户 runtime |
| 查凭据与授权是否 active | `verifyConsoleOidcServiceTokenState` | 租户 runtime |

⇒ **Console 知道是哪个租户，但够不到那个租户的 runtime**，于是 503
`Console tenant-runtime is required for tenant data access`。

> 补充说明：这与 host 无关。我最初用 `console.huizhi.yun` 与 `wiztek.huizhi.yun`
> 做对照得到 503 / 200，容易误判成「host 不带租户上下文」。实际差别是后者经过
> Tenant Gateway、由网关注入了完整的一组 header；直接 curl 前者当然什么都没有。
> **走 Service Binding 也不会自动获得这些 header**，必须由调用方显式转发。

---

## 2. 三个方案

### 方案 A：补齐运行时定位 header 的转发链

让业务应用把 `x-hzy-tenant-runtime-url` / `-token` / `-audience` 一并转发给 Console。

**改动面**：`foundation` 的 `forwardedContextHeaders` 系列与 `consoleBackendHeaderNames`
（后者其实已含这些名字，需查实为何上游没有值——很可能 Tenant Gateway 对业务应用路径
本来就不注入）。若网关确实不注入，则改动会上溯到 Tenant Gateway 配置。

| | |
| --- | --- |
| ✅ | 改动最小，不动 Console 逻辑 |
| ✅ | 与现有「网关注入受信上下文」的模型一致 |
| ❌ | **把 runtime token 沿调用链多传一跳**。Altoc 的请求头里带着 Finance 之外还会到 Console，扩大了凭据暴露面 |
| ❌ | 依赖调用方正确转发。任何一个应用漏转发就再次 503，且症状与本次完全相同（难排查） |
| ❌ | 需先查实 Tenant Gateway 是否注入，可能牵出网关侧改动 |

### 方案 B：Console 按 tenant_code 自行解析 runtime（推荐）

Console 拿到受信的 `x-hzy-tenant` 后，从控制面自己查出该租户的 runtime 端点与凭据，
不依赖调用方转发。

控制面已有现成数据：`hzy_platform.tenant_runtime_instances` 有
`runtime_endpoint`、`runtime_token_hash`、`status`、`current_version`
（本次走查中已实际查询过该表）。

| | |
| --- | --- |
| ✅ | **调用方不再需要携带任何 runtime 凭据**，暴露面收敛到 Console 一处 |
| ✅ | 任何调用方、任何路径都能一致工作，不会因为漏转发而复现 |
| ✅ | 与「Console 是运行时授权事实源」的既定架构一致 |
| ❌ | Console 需要能拿到 runtime **token 本身**，而表里存的是 `runtime_token_hash`。需确认 Console 侧是否已有该凭据来源（如自身 vault / 配置），**这是本方案唯一的未知项** |
| ❌ | 改动在 Console 认证热路径上，需要更谨慎的回归 |

### 方案 C：业务应用不做远程 introspection，改本地验签 + 撤销列表

业务应用用缓存的 JWKS 本地验签，撤销状态改为低频拉取或推送。

| | |
| --- | --- |
| ✅ | 去掉每次调用一次 Console 往返，延迟与故障面都下降 |
| ❌ | **削弱安全边界**。现注释明确写着「Console introspection 是服务令牌的权威校验边界」，改本地验签后凭据/授权撤销存在传播窗口 |
| ❌ | 改动最大，涉及 JWKS 缓存、撤销传播、失效语义 |
| ❌ | 与根 `CLAUDE.md`「Console 是运行时授权事实源」的表述冲突 |

---

## 3. 建议

**选方案 B。** 理由：

1. A 只是把「谁忘了转发」这个脆弱点从一处搬到另一处。本次故障的症状——
   静默 503、跨三跳才暴露——正是转发链脆弱性的体现，A 保留了这个类别。
2. C 动了安全边界，代价与收益不成比例；本问题是「够不到 runtime」，不是「introspection 太慢」。
3. B 让凭据只存在于 Console 一侧，与既有架构定位一致，且对调用方完全透明——
   Stream A / Stream C 的应用不需要为此做任何改动。

**动手前必须先确认的一件事**：Console 能否拿到租户 runtime 的 token
（表里只有 `runtime_token_hash`）。若拿不到，B 不成立，需退回 A 并同时评估
runtime token 多跳传递的安全影响。

---

## 4. 无论选哪个方案都要做的

1. **失败必须可诊断**：现在 Console 只回一个笼统 503，调用方只能看到
   `service_token_introspection_unavailable`。应区分「租户未知」「runtime 不可达」
   「凭据已撤销」，否则下一次同类故障还是要靠逐跳 tail 才能定位。
2. **补契约测试**：覆盖「有 tenant 无 runtime 定位」这个组合。本次故障能长期存在，
   正是因为没有任何测试覆盖跨应用入站校验的完整链路。
3. **端到端验收**：诊断数据 `C-QA0901-RP` 保留可用。验收标准是
   `hzy_finance.invoice_request` 真正出现记录、Altoc 侧 operation 走到 `succeeded`——
   不能只看 Finance 有入站。

## 5. 查实结果与最终结论（2026-08-28）

### 5.1 方案 B 不成立

控制面**只存哈希，没有任何可还原形式**的 runtime 凭据：

```
hzy_platform.tenant_runtime_credentials : credential_mode, runtime_token_hash, runtime_token_last4
hzy_platform.tenant_runtime_instances   : runtime_token_hash, runtime_token_last4,
                                          control_token_hash, control_token_last4
```

C000001 的 `credential_mode = 'tenant'`（凭据归租户所有），生产 data-runtime 的
`HZY_DATA_RUNTIME_AUTH_MODE = static_token`。⇒ **Console 无法自行取得 runtime token**，
方案 B 在当前认证模式下不可行。

> runtime 本身支持 `jwt` 模式（`config.go:20 AuthJWT`），切过去后 Console 可用自身签名
> 密钥签发、无需持有静态密钥，B 才会成立。但那是一次认证模式迁移（runtime 重新部署 +
> JWKS 分发 + 灰度），不属于本问题的修复范围，可作为独立演进项。

### 5.2 真正的缺口比原先判断的更具体

Altoc 的**入站**请求其实带着完整的 runtime 定位 header（生产 tail 实测）：

```
x-hzy-data-runtime-url      ✓    x-hzy-data-runtime-token     ✓
x-hzy-data-runtime-code     ✓    x-hzy-data-runtime-audience  ✓
x-hzy-gateway ✓  x-hzy-gateway-token ✓  x-hzy-tenant ✓  x-hzy-deployment ✓
```

Finance 收到的却只有 5 个 `x-hzy-*`，runtime 定位那 4 个**在 Altoc 转发时被丢掉了**。

原因是**转发白名单在仓库里被各写各的**。

> **更正（实施时查实）**：这里原写「三份实现」，那只是按单一函数名 grep 到的数量。
> 实际是 **12 处**各自实现的白名单，其中三处残缺：

| 转发实现 | header 数 | 含 runtime 定位 |
| --- | --- | --- |
| `serviceTicketOpsKnowledgeOperation.ts`（**开票申请走这条**） | 5 | ❌ 0 个 |
| `altocFinanceSummaryOperation.ts`（Finance 回写走这条） | 1 | ❌ 0 个 |
| `sync-people-costs.post.ts` | 9 | ❌ 0 个 |
| 其余 9 处（`activate-delivery.post.ts`、`codocsApi.ts` 等） | 15 | ✅ 6 个 |

其中 `codocsApi.ts` 的函数名是 `forwardedCodocsContextHeaders`，按函数名 grep 完全
命中不到——最终是靠 §5.3 提到的那条防复发守卫扫出来的。

所以这**不是**架构缺陷，而是转发实现的碎片化：同一件事在仓库里各写各的，
覆盖面不一致，谁少转发谁静默失败。

### 5.3 结论：走方案 A，但必须一并消除碎片化

单纯给开票申请那条补 4 个 header 能让本次链路通，但会留下同样的坑给下一条链路。

**实施结果**：已按此执行（MR !29），12 处全部收敛。原建议如下：

1. 在 Foundation 提供**唯一**的跨应用转发 helper（比如
   `crossAppForwardedHeaders(event, { idempotencyKey })`），白名单集中定义一处，
   以 `activate-delivery` 那份 15 个为基准。
2. altoc / finance 现有三处转发实现全部改为调用它，删除各自的私有版本。
3. 补一条契约测试：扫描跨应用出站调用点，**任何一处自建 header 白名单即失败**——
   与 `integration_operation_clock_domain_test.go` 同一思路。

这样既修好当前链路，也让「漏转发」这个类别不再可能悄悄复发。

**安全说明**：runtime token 本来就由 Tenant Gateway 注入给业务应用，
转发给 Console 属同一信任域内的上下文传递，不扩大对外暴露面；
但仍应只转发给 Console 与目标应用，不得回传浏览器。

### 5.4 §4 的三条仍然适用

尤其第 1 条（失败可诊断）。本次从「静默 503」定位到「三份白名单不一致」花了很多轮
逐跳 tail —— 如果 Console 能区分「租户未知 / runtime 不可达 / 凭据已撤销」，
第一次看到错误就能定位。
