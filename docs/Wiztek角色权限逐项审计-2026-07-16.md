## 结论摘要

- 17 个企业角色均已物化且可分配；所有角色都有权限，不存在“空角色”。
- 应用菜单必须按“模拟角色权限 + 可选 baseline”过滤。默认 `includeBaseline=true`，所以所有有效用户仍会看到 baseline 提供的 Aims、Codocs、Finance、Workflow 最小入口；这不是角色越权。关闭 baseline 后只能显示模拟角色自身有 grant 的应用。
- 六个 P0 角色已按审计目标收敛：总经理不再持有业务 admin，项目总监不再兼任项目/费用经办，人力角色不再管理目录源，部门经理不再默认持有资产审批/文档发布，采购与资产管理员不再兼任资产审批。
- 生产 bundle 中 `roleDefaultScopes=5`、`assignmentScopes=24`。新增的 5 条角色默认范围全部属于 `assets:employee`，分别把工作台、资产台账、资产操作查看/申请和预警收敛到精确 `asset:user`；销售专员、销售经理、六名部门经理和两名副总的当前有效 assignment 仍逐项绑定 self/部门树范围，未来新增这些角色的 assignment 必须同步携带 scope，不能仅依赖角色名称。
- 17 条 active 职责冲突规则均为 `warning`；整改后按角色命中降为 7 条。允许兼岗的角色仍必须依赖实例级“非经办人审批/确认”校验，warning 不等于已完成职责分离。
- Insights 暂停处理：生产 bundle 仍有 22 条角色 grant 指向 Insights，但当前部署应用目录和 bundle manifest 不含 Insights。菜单过滤会忽略这些孤立条目，本轮不调整。
- Platform `authorization` 的 5 条 grant 属于 Console 内的控制面模拟/管理能力，虽然不进入租户业务应用目录，但不是孤立权限，不应删除。

### 本轮共性根因与修复

1. **业务应用错误依赖 Console 人类目录权限**：Altoc 通过 `GET /api/directory/users/{uid}` 渲染负责人姓名时落入 Console 管理目录接口，销售角色得到 403。Foundation 现将非 Console 应用的单用户读取收敛到最小共享投影，并仅给 `altoc.runtime` 安装 `console:directory-users:read`；没有给销售、人事或项目角色增加 Console 权限。
2. **模拟态触发 Console 管理写操作**：Console `/admin` 中间件会无条件调用 `POST /api/activation/bundle-refresh`，模拟态按设计阻断该高风险写入并产生 403。中间件现先确认不在模拟态且真实用户具备 `system_settings:admin`，否则不发请求。
3. **退出模拟后控制器权限缓存未恢复**：低权限模拟页面重载后会把模拟能力与企业角色目录缓存为拒绝，退出时原逻辑只刷新业务权限和应用菜单。现在退出与过期路径同时强制刷新真实操作者的模拟能力和角色目录，入口无需页面刷新即可恢复。
4. **应用目录首页与角色权限不一致**：Console 中 Assets 的兼容入口仍为 `/assets/overview`，而项目成员没有报表权限，首次访问会被送到 no-access。Assets 路由守卫现把 `/` 与 `/overview` 都视为应用落地入口，在目标页无权时按已有权限选择首个可访问页面；自助资产用户优先进入资产操作，完全无 Assets 权限仍失败关闭。
