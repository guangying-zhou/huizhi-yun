## 2. 设计结论与范围

**设计方向成立，当前进入内部试点产品化阶段。后续投入围绕真实业务闭环、发布可靠性和日常使用效果展开。**

继续保留以下设计：

| 设计 | 保留理由 | 执行约束 |
| --- | --- | --- |
| 按领域确定事实源 | Altoc 管经营，Aims 管交付，Finance 管财务，People 管人员，Console 管身份与目录 | 跨模块引用稳定业务键；业务应用不跨库读写，也不复制主档维护入口 |
| 客户侧 Tenant Runtime | 业务规则和数据访问集中在客户侧，应用保留 UI/BFF | 不恢复应用本地 DB fallback；缺接口时补对应 adapter |
| 可靠操作与目标回执 | 本地事实与 operation、目标 mutation 与 receipt 分别同事务，可恢复中断投递 | 保留冻结命令、幂等、租约、重试、死信与受控重放；复用已有设施 |
| 按工作类型简化 PIVR | 日常事务免立项，维保按服务周期，交付项目保留阶段门 | 验收必须区分 `routine`、维保和交付项目，不能统一强套立项流程 |

### 4.1 SAFE-01：资料与缓存治理

- **验收**：所有在管项目已建档且有负责人和成员；需要立项/里程碑审批的新业务走系统，`routine` 按免立项规则执行；9 月推广周有效参与率 ≥80%，并留存试点及推广连续两周数据。
- 阻断问题当日分类，影响日常使用的 P0 优先修复并留排障记录；未达目标显式顺延，不用集中补录伪造持续使用。

### 4.4 FIN-01 / FIN-02 / FIN-03：先确认事实，再修正确性

**FIN-01：历史 ISSUE 分诊**

- 逐条对照旧清单、当前代码、部署和业务证据，分别标记已关闭、待部署、待复验或仍需修复；不沿用旧文档的 P0 数量和工期估算。
- 已通过的“申请创建 → 审批启动”作为回归基线；剩余重点是审批结果、财务后续状态、金额、授权负向和通知恢复。
- **验收**：形成当前开放问题清单，包含范围、优先级、下一动作和证据；已关闭项可追溯到修复及验收。

**FIN-02：发票业务唯一性**

- 与财务确认唯一标识涉及的字段、历史票据兼容及作废/红冲语义；不直接假设所有历史票据都能仅凭 `invoice_no` 全局唯一。
- 先检查历史重复，再落实数据库约束、服务端冲突映射和前端可读提示；同一申请的重放继续返回原结果。
- **验收**：两张申请登记同一业务发票时不能生成重复财务事实；并发请求只有一个合法结果；冲突不返回泛化 500，不导致合同汇总重复累计。

**FIN-03：商机看板汇总**

- 服务端按完整筛选范围返回阶段数量和金额；卡片分页或分批加载与汇总解耦。
- **验收**：构造至少 201 条跨阶段商机，比较看板与独立全量聚合结果；筛选变化、空阶段、金额精度和权限范围均正确。
- 如该任务顺延，必须明确显示汇总范围或暂停不完整汇总展示，避免把局部金额展示为完整经营事实。

### 4.5 FIN-04：完整链路验收矩阵

故障注入、重复请求和边界数据在隔离验收环境完成。每个场景都记录业务结果及 operation/receipt，不以 HTTP 200、令牌签发或页面提示代替目标落库证据。

| 场景 | 最小动作 | 通过标准 |
| --- | --- | --- |
| 合同到交付 | 合同生效 → 创建/关联 Aims 项目 → 同步付款里程碑 → 验收完成 | 项目、合同、付款条款关联正确；指定回款计划变为可开票；重复投递不重复创建 |
| 收入完整主链 | 开票申请 → 审批通过 → 正式发票登记 → 到账 → 核销 → Altoc 摘要 | 两侧金额和状态一致；每跳有目标事实与成功回执，无手工补业务表 |
| 驳回与重提 | 审批驳回后按业务规则修改并重新提交 | 状态可恢复、历史可追溯；不跳过审批，也不复用错误的旧终态 |
| 分次与部分核销 | 分次开票、部分到账、部分核销 | 剩余金额正确；下一次合法操作可继续；不超额、不重复累计 |
| 幂等与并发 | 同键同载荷重放、同键异载荷、同一对象并发操作 | 同载荷返回原结果；异载荷冲突；数据库与汇总无重复事实 |
| 超时与响应丢失 | 目标已提交后丢响应、源 checkpoint 失败、Worker 重启 | 原 operation 可恢复；目标不重复 mutation；租约与旧 worker 隔离有效 |
| 后台恢复与告警 | 临时下游失败后停止人工请求，等待 scheduler；再覆盖永久失败 | 瞬态失败按策略恢复；永久失败不无限重试；通知送达有资格责任人，受控重放留审计 |
| 权限与职责 | 无数据范围、跨项目/部门越权、自审批、服务 capability 或绑定错误 | 按契约拒绝；失败不产生业务 mutation；依赖不可用与用户缺权可区分 |

**FIN-04 出口**：上述适用场景全部通过；不适用项写明业务理由。完整链路涉及的开放 P0 为零，其余问题有负责人和处理日期。

### 4.6 FIN-05 / FIN-06：真实业务启用

- 导入前由经营/财务确认有效客户、合同、回款计划的基准清单及金额；导入后核对数量、业务键、金额和项目关联。
- 启用到期/逾期通知并确认责任人实际收到，链接能打开本人有权查看的对象。
- 至少一份真实合同完成申请、审批、正式发票登记、真实到账、核销和经营侧回写；沿用实际业务事实，不为凑验收制造发票或到账。
- **验收**：双月目标逐项核对，保存脱敏证据；没有手工补业务表，金额与业务台账一致。若真实到账时点超出 10 月，明确顺延真实闭环验收，隔离环境通过不能替代它。
