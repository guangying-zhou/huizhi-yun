# APF 销售与财务功能差距及 B5 实施计划

日期：2026-10-06。代码基线：`d76e2a490acd5279431d5b5f2ad45d6e20e6c73e`，来自 `origin/feat/adr018-enterprise-integration`。本次交付为盘点与计划，不实施业务代码、schema 安装、数据迁移或部署。

## 1. 建议与范围

下一阶段优先让销售回答「该收谁的钱、何时收、谁跟进」，让财务完成「到账确认、分配核销、差异解释」，再完善合同变更、续约和经营报表。不要把已经存在的开票、到账、核销、费用、履约义务、续约机会重新建设一遍。

建议将 [APF UI 设计 B5](APF-UI-Redesign.md#b5销售与财务业务闭环及后置协作能力) 扩展为业务闭环计划，按 B5-A～G 分批：

1. **先交付 B5-A 应收工作台与催收指派**，复用结算计划、到期通知机制；先覆盖有可靠事实的当前业务，历史合同明确显示未就绪。
2. **B5-B 完成历史财务衔接与收款分配**。复用已实现的受审期初工具，解决历史明细与期初双计、护栏放开、批量核销及调整。这是迁移数据进入持续经营的关键门槛。
3. **B5-C 完善合同金额变更与开票对照**，保留原签约额，形成可回放的当前额/有效额，衔接已有开票流程。
4. **B5-D 履约与续约闭环、B5-E 经营报表**。前者减少漏办，后者基于已稳定的事实形成可钻取统计。
5. **B5-F 银行流水/付款计划、B5-G 共享视图/批量/附件协作后置**。完整总账、税务直连、跨币种核销、CPQ、MRP 不作为本轮默认目标。

这不是必须按字母串行的大版本：A 可独立上线；B 的历史财务启用不阻塞 A 的当前业务；D 可在确认来源与续约期限后独立推进。E 可先发布已存在事实的只读报表，历史比较与业绩归属必须等相应事实完成。任何批次不因文档获提交而自动获得环境写入批准。

## 3. 老 OA 与中小企业 CRM/ERP 对标

### 3.1 业务差距矩阵

「增强」表示超出已核实老 OA 能力；不把成熟产品常见能力冒称老 OA 已有。

| 场景 | 老 OA / 迁移基线 | 当前 Enterprise | 剩余差距与分类 |
| --- | --- | --- | --- |
| 合同回款、未收款 | 合同 exec_amount 是剩余应收/应付缓存，收入明细可追溯；存在缓存差异 | 有当前到账/核销和历史快照；历史财务写仍受护栏限制 | 历史事实接续是迁移衔接；应收到期/账龄/催收是增强 |
| 收款分配 | 部分收入没有合同，负数/零值不能丢 | 核销行模型及单次命令已有 | 多目标原子分配、预收/未分类处理、调整/撤销与防超额；不另建「收款余额表」 |
| 发票 | 源有发票记录，缺发票类型；缓存是剩余未开票额 | 已有新业务申请/审批/正式发票 | 历史保全不等于正式票可操作；补历史开票水位与当前差额对照，不能猜票种 |
| 合同变更/有效额 | 总额及独立人工有效额，不能据明细假造来源 | 原签约/当前金额字段及历史有效额已有；W1 §7A 尚为设计 | 追加式金额事件、补充协议、成分认定与 as-of，属于增强 |
| 履约/里程碑 | 有项目/系统/合同关系，不足以证明结构化验收闭环 | 已有义务、付款条款、项目/交付关系 | 工作台与验收证据、节点变更、可靠联动复核；复用 Aims 验收事实 |
| 维保/续约 | `wb_system` 及维护合同引用需保全；不能把合同类型猜成所有维保 | 服务协议、覆盖、续约机会已有 | 历史系统关联补齐、到期筛选、提醒、续约新合同闭环 |
| 经营报表 | 客户合同/有效额/应收缓存，直接/子树口径不一致 | 授权摘要和项目核算等已有 | 按期间/销售归属的统计、可钻取对照、缺失标识；不是直接照抄旧缓存 |
| 账户与银行对账 | 账户与多次余额登记，没有等价的逐笔银行流水闭环证据 | 账户/余额证据与截至日期查询已有 | 银行流水、未达项、账实匹配是增强；不能从余额差值生成收支 |
| 费用、付款计划 | 有支出和组织付款计划，很多支出无合同 | 有付款/费用/报销事实 | 历史映射、组织现金支出预测、退款/冲销和计划执行对照 |
| 档案与客户协作 | 档案页不等于文件可下载，关系/文件需分别验收 | 已有部分附件与知识引用 | 受控文件迁入、业务对象附件聚合、版本与来源；共享视图/受控导出属增强 |

W0/W1 已确认的规则继续有效：有效额含税且只扣第三方等非本公司收入部分；有效额不能参与应收/开票计算；NULL 不是零；日期与时区按 W1；旧 OA 详情 GET 曾写缓存，因此不用访问其详情接口做只读核查。

## 4. 优先级与成本

价值按 1–5 评估（5 为直接影响现金与日常交付）；成本 S/M/L 是相对工程复杂度。它们是本轮规划判断，未以工时数据计算 ROI。人日区间包含相关前后端、合同/隔离测试和浏览器验收，不包含等待业务确认、环境窗口、外部文件修复或税务/银行接入；不能直接相加当作交付日期。

| 优先级 | 缺口 | 价值 | 成本 | 原因与依赖 | 批次 |
| --- | --- | ---: | --- | --- | --- |
| P0 | 应收明细/账龄、到期日与催收责任 | 5 | M | 当前业务可先见效；无责任人就没有可靠提醒收件人 | A，6–10 人日 |
| P0 | 历史财务就绪与核销分配/调整 | 5 | L | 让老合同进入持续收款；防止历史明细与期初双计 | B，12–20 人日 |
| P1 | 合同金额事实/变更、开票进度对照 | 5 | L | 有效额及应收口径的长期基础；复用已有开票命令 | C，10–16 人日 |
| P1 | 履约待办、验收关联、续约提醒/转单 | 4 | M–L | 减少漏结算与漏续约；复用既有模型和调度 | D，8–14 人日 |
| P1 | 销售业绩、回款/开票、续约报表 | 4 | M | 先读事实再做图；历史业绩归属不能按当前 owner 漂移 | E，6–12 人日 |
| P2 | 银行流水、未达项、组织付款计划 | 4 | L | 对账价值高但需新增事实与历史映射；不能从快照推导 | F，12–20 人日 |
| P2 | 跨设备/共享视图、受控导出、附件聚合、批量 | 3 | M | 提升效率，不能优先于现金闭环 | G，6–12 人日，按子项选做 |
| 暂缓 | 税务直连、银企直联、跨币种核销、佣金自动发放、完整总账/CPQ/MRP | 待定 | L | 接入、会计政策、职责和数据前提尚不具备 | 不列入默认实施 |

推荐最小首发是 A 的当前应收和指派＋B 的受审历史就绪及分配，不捆绑银行流水和高级报表。已有 Finance 开票入口可以通过 A/C 的上下文导航更快到达，不必等待重做发票模块。

## 5. 共同数据与授权合同

### 5.1 单一事实源与时间口径

- **应收项继续等于 `altoc_billing_schedule` 的 receivable 行**；不新建平行应收主账。Finance 拥有到账、核销与应收调整，Altoc 拥有合同、条款、履约与结算计划。
- 当前未结金额建议统一定义为「应收原额 − 有效核销 − 有效应收调整」。调整不得伪装收款。新增调整时采用派生聚合读模型，首期不改生成列 `unreceived_amount` 的含义；所有使用该列作判断的写端、提醒、汇总均须改用同一余额计算器后才能启用调整。
- 账龄按业务日与款项 `due_date` 分桶：未到期、1–30、31–60、61–90、91–180、180 天以上、无到期日。`end_date` 是合同/服务到期，`collection_due_at` 是下一次催收办理截止，三者分别保存。
- 当前账龄可从现有事实派生。历史 as-of 不能只扣当前核销：必须回放当时已生效核销/撤销、调整、计划金额/到期日/取消变化。W1 提出的 `reconciled_at/reversed_at` 只解决收款部分；计划版本和调整事件不齐时拒绝历史日期并返回可查询起点，不给伪历史报表。
- 一笔已确认到账可多次分配，但总有效分配不得超过未分配余额；每个目标必须同币种、同合法客户/主体归属并在调用者范围内。跨集团代付不是同名匹配，另需明确付款方关系及显式规则。余款留未分配或进入已有预收模型，不能生成虚构应收凑平。
- 期间报表金额分币种，不自动汇总成人民币；父子合同去重延续已有集合规则并公开分母。历史未认定有效额单列缺失；业绩不是会计收入，也不是现金回款或净利润。

### 5.2 跨域写与通道分类

| 链路 | ADR-018 分类 | 约束 |
| --- | --- | --- |
| Finance 批量核销/调整 → Altoc 结算计划与财务摘要 | **共享事务**，延续现有 B2/B3 锁序模式 | owning typed 校验后同 Tx 写核销与余额投影；固定排序锁定父对象/摘要/目标/到账等现有锁集合，按当前实现扩展，不在持锁期调用 Directory |
| 合同金额变更 → 本合同汇总/计划重排 | **owning typed 入口＋同域事务** | 已核销/已开票节点不能被直接覆盖；需单独调整或冲销，不能把变更传播成跨域任意 UPDATE |
| Aims 验收/Assets 交付 → Altoc 可结算 | 优先复用已迁移的 **owning typed 入口/共享事务**；仍跨边界的路径用 **outbox** | 实施前沿现有完成链确认唯一 owner、固定业务键和源版本；不同时启用旧 Service API 与新同库消费 |
| 提醒 → Console 通知；外部票据/银行回执 | **outbox/可靠投递** | 固定目的、回执幂等、重放和撤销旧代；通知不修改开票/核销/续约状态 |
| People → Directory 的用户状态 | **跨边界异步**（复用现有） | APF 只读当前目录资格，不把该链纳入业务共享事务；新责任指派复用 owner guard |

新增用户固定操作归对应 `<domain>:enterprise-host:execute`；系统扫描归 `<domain>:scheduler:execute`；来源详情授权归 `<domain>:notification-detail:authorize`。不逐按钮新增 capability，不把用户 U permit 用于 S/P 通道。Manifest 是人员权限唯一事实源；新敏感动作需要显式定义，admin 不自动获得 confirm/issue/export/close 等能力，seed 与测试由同一事实同步。

新 Runtime 表经 Registry/domaininstall 受审子集安装，增量列/索引核验真实已安装基线；不直接修改 hzy0。存量无前缀 SQL 使用已批准的 B1 兼容视图策略时同步受控视图清单及双向 verify，或在专项迁移中统一用 `Resolved.Table`，不能单批混杂猜表名。跨租户、错来源、过期 permit、缺权限、重复意图、并发超额、乱序事件均纳入合同测试。

## 6. 分批实施

下列操作名与新表名为**建议合同名**，不是已经注册的 API。每批实施前先对照现有 API_SPEC/Manifest 合并重名能力，保留其所属域和语义。

### B5-A：应收工作台、账龄与催收责任（E＋新 R/W）

**范围**：当前结算计划应收，按客户/合同/负责人/法人/币种筛选、服务端总计、账龄钻取；维护款项到期日、催收负责人和下一次跟进时间，记录联系结果。历史合同未有已确认期初或就绪标识时明确排除并显示覆盖范围。

**Runtime 合同**：R `receivables-page/detail/aging-summary`，查询日期、日期口径和总数/金额同一快照；W `receivables-set-collection-owner`、`set-due-date`、`collection-followup-create`，绑定版本、当前对象范围与 owner guard。现有 sales 活动若不能准确表达应收跟进，新增 Altoc `collection_followup`，不得往客户备注拼接历史。跟进字段至少对象 code、结果、承诺付款日/金额（非实际收款）、下一次跟进、actor/time、幂等键；计划到期日变化留版本事件。

**Schema**：复用 `altoc_billing_schedule` 及已有 collection 字段；新增跟进及必要计划变更事件表，索引围绕合同/客户、due_date、状态与分页 ID，以实际查询计划核定。账龄桶不落库。不默认添加日快照表。

**页面/文件**：扩展 `/altoc/payments` 列表/详情（`enterprise/app/pages/altoc/payments/*`、现有 `AltocBasicReadPage.vue` 或拆应收专用组件）；客户/合同增加应收页签。读合同在 `enterpriseAltocReads.ts` 和 owning Runtime；新增写合同接 APF permit。无权 Finance 金额投影不可从客户汇总推断。

**验收**：同日/跨月/闰日、无到期日、部分核销、取消记录、多个币种均有夹具；桶合计等于筛选明细；100 条以上翻页无重复/漏项。指派保留主体/不可登录 UID 被拒，历史原值可读；Directory 故障时不发生新指派。到期通知无责任人不发，结清/改派后关闭旧提醒；正式启用需 S/P/grant/唯一 owner 证据。

**完成与批准点**：代码和隔离测试先完成；schema 安装、通知启用分别批准，不因页面能打开就启用扫描。当前账龄可先发布，历史 as-of 须等事件覆盖完整。

### B5-B：历史财务接续、原子分配与调整（复用工具＋新 R/W）

**范围**：受审期初应收到日常收款的接续；历史收入/发票/支出保全转业务事实的分期映射；到账分配编辑器、分配撤销、应收折让/尾差/部分坏账。先销售应收，不把采购期初应付偷偷纳入。

**Runtime 合同**：

- 复用 `wizbiztool/opening.go` 的 confirmation/review hash/verify，新增业务就绪读取与受审激活条件；Finance 历史写护栏改为检查已验证批次、合同期初、会计切分日期及业务事实覆盖，不是删除 `origin_type` 检查。
- R `allocation-candidates`、历史覆盖/差异明细；W `reconciliation-allocate-batch`（一笔到账、多行目标、同 Tx 全部成功或全部拒绝）、批次撤销。UI 可建议按到期日，但服务端重新计算容量、锁版本、复核每目标权限。
- W `receivable-adjustment-create/reverse`：原因、金额、类型、审批证据、职责分离、版本与幂等；不能仅修改结算计划 status 来表示部分坏账。

**Schema**：沿用 `finance_receipt/reconciliation/invoice/expense`；补批次/切分水位/来源身份及必要类型缺失语义，优先扩展迁移清单而非平行主账。新增 W1 建议的 `finance_receivable_adjustment`，补撤销指向/时刻/actor 以支持 as-of；原子分配可复用既有命令回执和 operation ID 作为组键，确需独立批次审计再加关联表，不增加第二余额字段。

**防双计合同（必须先落文档与测试）**：

1. 为每次切换固定 T0 和财务确认的期初未结金额；T0 之前历史收款/发票迁入时保留原始事实与审计，但不得再次冲减这个净期初。T0 之后的增量才进入新核销。
2. 旧明细能否核销到旧结算义务由受审重建合同决定，不能自动把旧收入全挂到唯一 opening 行。若选全历史重建，必须先验证与净期初路径余额相等，再作一次可追溯切换；两条路径不能同时 active。
3. 封存快照中 20 份差异合同沿 W1/W2 候选及逐合同确认处理；不以「差异接受」自动生成调整。零/负数收入、发票和费用各自分类为退款/冲销/历史特例，未定语义时停在保全台账，不跳过行。
4. 发票缺票种、开票主体等历史缺失不能猜值；先提供标明未核实的历史查询，满足正式票合同后才转换。关闭/中止历史合同不能消除未结应收，须允许财务后续处理或显式处置。

**页面/文件**：复用 Finance `receipts-*`、`reconciliation-*`、`FinanceLedgerList/Detail/Form` 与合同财务页签；新增受审财务接续预览，不把迁移页的只读差异按钮变成任意改数。代码范围为 `finance_ledger.go`、共享余额/锁序 helper、`wizbiztool`、相关安装子集及 `enterpriseFinanceLedger` BFF（以实际文件名定位）。

**验收**：到账 100 分配 60＋40、60＋50 超额整体拒绝、并发抢同一未结项、同 key 同/异 payload、撤销后再分配、跨客户/币种/主体拒绝；调整与核销并发不会出现负未结。两次导入、断点续跑、T0 前后混合收入、已有核销后回滚拒绝、未确认历史合同继续失败关闭。财务逐合同、逐币种对账而非只看总额。

**完成与批准点**：先交付当前业务的原子分配；历史激活单独验收。期初确认文件、历史明细映射、review hash、apply/verify、护栏启用均有独立记录；未批准则交付 dry-run 与可审阅差异，不写 hzy0。

### B5-C：合同金额事实、补充协议与开票对照（新 R/W＋复用开票）

**范围**：原签约额不变，当前合同额随生效变更变化，有效额按 W1 §7A 派生；合同/结算计划到开票申请和正式发票的业务对照。税务平台自动开票不在本批。

**Runtime 合同**：R `contract-amount-events`、`contract-amount-asof`、`billing-invoice-progress`；W 变更草稿/提交/批准生效/冲销按已有 Workflow 入口扩展，绑定合同版本和明确生效日期。历史有效额只通过受审 opening fact 回填，不能补造外采/分包分类。现有申请/审批/issue/红冲命令复用；新增聚合页面不暗示 admin 自动有 issue 权限。

**Schema**：实现 W1 §7A 的合同金额事实及变更事件关联（使用设计表名时核对安装清单），gross、扣除成分、effective_opening、source/event_ref/effective_date/reversal_ref；合同汇总同 Tx 重算。需要签约时销售归属快照的字段/关系在本批写入，供 E 统计，不用当前 owner 改写历史业绩。行级履约来源采用待签署前明确分类，未认定保留状态；已生效行不能直接绕过事实变更改金额。

**页面/文件**：合同详情「金额与变更 / 开票与回款」，变更复杂子表用独立页面；Finance 原开票申请/正式票页面加来源结算计划与差额钻取。涉及 `AltocContractsPage.vue`、合同详情、`altoc_contracts.go`、`altoc_contract_children.go`、`finance_ledger.go`、既有审批编排与 schema 子集。

**验收**：总额 100，扣第三方 20，有效额 80，税额不再扣；变更＋10后原签约仍 100，当前额 110，as-of 生效前后正确；历史有效额 NULL 和大于总额特例不被通用公式覆盖。已开票/已核销节点不得被变更静默缩小；申请批准不自动生成正式票；作废/红冲对统计与原票可追溯。开票总计不得把申请和正式票重复加总。

**批准点**：人工成分认定/冲销的审批与职责规则、历史事实回填的 review hash、schema 安装、变更功能启用分别确认。权限名由最终 Manifest 定义，不在计划里私自授予新角色。

### B5-D：履约工作台与续约闭环（E＋新 R/W/S/P）

**范围**：按客户/合同查看待履约义务、待验收、可结算和到期服务；续约机会从到期记录生成并跟进到赢单/流失、新合同关联。仅结构化有依据的到期日期；旧系统引用无法确认时入待补资料，不猜到期。

**Runtime 合同**：R `fulfillment-worklist`、`renewal-due-page`（到期范围、状态、负责人、服务协议、稳定排序）、详情证据聚合；W `renewal-from-agreement`、`renewal-link-successor` 和明确的失单原因。复用已有义务完成/验收和续约 CRUD；不提供绕过 Aims 验收的「一键全部完成」。新增 renewal-due 的 S 扫描与 P 详情复核，复用既有 Gateway wake、checkpoint/投递/关闭协议，不新增 cron。

**Schema**：复用义务、结算计划、服务协议/覆盖、续约机会；按缺口加来源协议/服务期/后续合同关联与唯一键（同源服务期只能生成一次有效续约机会），保存理由/结果事件。若通知族受闭集约束，同步扩展 operation 注册/安装合同/测试，不能只在 UI 加日期字段。

**页面/文件**：合同「履约与项目」工作区、`/altoc/service-agreements`、`/altoc/renewals`；`altoc_contract_children.go`、`altoc_renewals.go`、`due_notifications.go`、`enterpriseAPFDueDelivery.ts`、对应 Foundation 通知来源复核与已存在的 Aims/Assets typed 入口。

**验收**：验收通过仅推进其关联义务/结算计划；重复/乱序事件无二次生效；节点取消或重开有明确定义。续约多次点击只生成一条机会；改负责人/服务期关闭旧提醒，权限撤销后通知链接不泄漏对象；won 必须关联合法后续合同，lost 有理由。没有自动续约合同授权时不可自动延长服务期。

**批准点**：续约提醒提前量由业务选定（建议可配置 90/60/30 天，非既定 SLA）；通知授权/唯一 owner/安装启用独立核验。先发布到期列表和人工生成机会，再启用系统提醒。

### B5-E：可钻取经营报表（主要新 R，导出为显式 W）

**范围**：先四张报表：销售签约/有效额、应收账龄与回款、开票进度、续约结果。项目毛利只引用现有经授权成本摘要并说明完整性，不重建 People 工资或 Aims 工时主账。

| 指标 | 日期/金额/分母合同 |
| --- | --- |
| 签约规模 | 规范签约业务日期；原签约额；父子合同按公开去重规则；分币种 |
| 销售业绩 | C 的认定有效额与签约归属快照；未认定/归属未知单列；不按当前负责人回填旧业绩 |
| 回款 | 已确认到账业务日与金额；核销额单独展示分配日，二者不相加；退款/撤销按既定事实净额 |
| 应收/逾期 | 查询日、款项到期日、有效核销/调整；明细与桶/总计可复算，历史查询受覆盖起点约束 |
| 开票 | 正式票开票日及有效净额；申请金额另列；未知历史票类型/主体单列，不默认为完整 |
| 续约率 | 选定期间到期且可续约的服务期 cohort；分已续约/流失/未决，明确截止日；金额率与数量率分开 |

**Runtime/schema**：新增固定只读聚合/钻取合同，范围、维度、期间、币种、口径版本和完整性随响应返回；不开放任意 SQL/字段选择器。首版不新增汇总事实表，有证据的性能需要才做带 watermark/calculation_version 的可重建投影。历史业绩归属事实复用 C；月结冻结/重开如业务需要单独 W 合同，不从图表保存操作隐式产生。

**页面/文件**：新增 Enterprise 销售/财务报表页（建议 `/altoc/reports`、`/finance/reports`，显式注册）；客户/合同摘要链接到同一筛选明细。Runtime 新报表模块复用当前 `altoc_effective_metrics.go`、Finance ledger 与 A 的余额计算器，权限按每一来源复核，不把 Altoc view 当作 Finance 全量读。

**验收**：图表、表格、钻取和导出相同筛选/范围/口径；跨月、缺失有效额、隐藏父合同、多币种、改 owner、退款/红冲、历史截止日场景可复算。无成本数据不能显示零成本/100% 毛利；不同权限用户的缓存互不复用。导出仅显式 permit、字段白名单、短期下载和审计。

**批准点**：指标定义及销售归属原则先由业务确认。当前事实报表可先发；历史业绩/ARR/利润不满足前提则隐藏，不用推算填满仪表盘。

### B5-F：银行流水、未达项与付款计划（后置新 R/W/schema）

**范围**：文件导入逐笔银行流水、建议匹配已确认到账/支出、人工确认未达项；组织付款计划及实际付款对照。银企直联、会计总账和税务申报不包含。

**Runtime/schema**：新增 Finance `bank_transaction`、导入批次与来源唯一键、`bank_match_allocation`；匹配已有 receipt/expense，不与应收核销共用同一 target_type 来混淆两种对账。新增或扩展组织付款计划/执行关联，优先复用 `finance_payment_request` 可承载部分，不能把计划额当支出。固定 preview/import/match/unmatch、payment-plan-page/maintain 合同；文件 hash、行身份、同账户重复导入和已被引用撤销规则明确。

**页面/文件**：Finance「银行对账 / 付款计划」，到账/费用详情反查匹配；`finance_spend.go`、新 Finance 银行流水模块、安装子集、`finance/layer/entry.mjs` 及 Host 注册。历史支出从保全台账按原业务类型映射；无合同支出不强制绑合同。

**验收**：重复文件、部分重叠文件、同日同金额不同流水、手续费/退款、零/负数历史、跨账户/币种、拆分/合并匹配；确认前不改业务金额；撤销匹配不删除原到账/支出。账户余额快照、银行流水累计、内部账面余额各自带来源和时点，未达项解释差异但不自动抹平。

**批准点**：银行文件样式和目标账户确认、历史支出/付款计划映射、schema 与导入 apply 单独批准；历史迁入和新录入共享幂等去重边界。

### B5-G：业务协作与效率（继承原 B5 后置项）

**范围**：跨设备个人/团队共享视图、受控导出、业务对象附件聚合与授权上传、必要的批量负责人调整。逐项选择，不因本批列名全部实现。

**Runtime/schema**：视图定义表保存租户/owner/可见范围/版本及允许的查询字段，不存业务结果；附件聚合通过 owning 域引用/访问合同，上传与删除沿文件领域命令；批量指派逐对象鉴权/owner guard/版本/幂等，决定原子或逐项结果并在 UI 明示。导出复用 E 的同口径数据集与明确 export permit。

**页面/文件**：共用列表视图控件、对象附件页签、批量结果页；`enterprise/app/composables` 的偏好模块、相关 Host 页面、owning Runtime 写模块。B4 迁移事件读不替代所有对象业务时间线；需扩展时单列授权投影，不输出原始台账 JSON。

**验收/批准点**：共享视图不扩大接收者数据权限；切换用户/租户不串数据；附件权限撤销后失效；无完整账号/敏感人员字段导出；部分失败可恢复。涉及外部存储写入、历史文件迁入或新敏感权限时按对应制品单独批准。

## 7. 实施验收、依赖与启用顺序

每批都有代码、合同测试、隔离 MySQL 和真实浏览器 1440×900 / 390×844 证据。列表遵守服务端分页、防抖、URL 恢复、`useConfirm`、语义色和 Foundation 组件；覆盖加载、真空、筛选空、403、503、409 与网络结果未知，不能只验证成功截图。报表先返回服务端合计再分页，不下载所有页到浏览器求和。

| 批次 | 输入依赖 | 可先独立交付 | 不能提前宣称完成 |
| --- | --- | --- | --- |
| A | 现有结算计划/核销事实 | 当前应收与账龄、人工跟进 | 无指派/owner 证据的催收通知；无事件覆盖的历史账龄 |
| B | A 的余额口径、已验证主迁移批次/财务确认 | 当前业务原子分配 | 历史护栏未按就绪状态收敛、T0 双计未消除的历史经营 |
| C | W1 金额定义、现有审批与开票 | 金额事实/变更与开票对照 | 仅改展示字段就称有可回放事实；历史数据强行分类 |
| D | 现有义务/协议/续约与来源范围 | 履约/到期列表、人工生成续约 | 未启用 S/P/grant 的系统提醒，旧新 owner 并跑 |
| E | B4 摘要、A；历史指标再依赖 B/C/D | 现有口径只读报表 | 历史业绩/现金流/利润数据完整性未经验证 |
| F | 账户、当前/历史收支的稳定来源身份 | 银行导入预览与未达项 | 余额快照等同银行流水、导入即自动改账 |
| G | 已完成对象读写合同 | 本机视图复用，逐项增加协作 | 共享视图授予额外权限、附件链接存在即视为迁移成功 |

安装/迁移类操作沿受审 plan → review hash → apply → verify，shadow-copy、兼容视图安装、grant seed、配置切换、停旧 owner 分项批准。安装与业务迁入分离，回滚不删除已被核销/发票/文件引用的数据。验收报告分别记录「代码完成 / 隔离验证 / 目标环境已启用 / 用户业务验收」，不能合并为一个完成勾选。

本任务只提交本计划与 B5 链接更新。hzy0 仍只读，不改变数据或进程；没有访问 WizBiz 源码配置的必要。实施排期从用户选定批次和合同评审后开始，不编造日期。

## 8. 首批实施前需业务裁定的有限问题

这些问题不阻塞本计划交付，分别在对应批次启动时确认：

1. B：历史财务 T0、各合同期初确认、先净期初接续还是全历史重建。建议净期初先行，旧明细保全查询，禁止双计。
2. B/C：应收折让/坏账、人工金额成分、更正的审批职责与阈值；建议保持录入与确认分离，不为方便授予 admin 敏感动作。
3. C/E：业绩按签约日还是变更生效日、归属人员/团队如何冻结。建议原签约业绩归签约期，后续变更记生效期调整；没有历史人员证据的部分列未知，不用当前 owner 推断。
4. D：服务期续约提前量、自动生成机会是否默认关闭、哪些类型算可续约 cohort。建议先人工确认生成，只启用站内提醒。
5. F/G：优先银行格式、组织付款计划范围、可导出字段和附件存储；未确定前不接外部银行/税务，不发客户消息。

本轮估算在上述决策、读写合同和隔离数据验收后再细化。任何新增功能都应先证明使用现有领域事实可以闭环，再决定是否增加 schema。
