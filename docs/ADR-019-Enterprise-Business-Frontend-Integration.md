# ADR-019：企业侧前端按业务整合与统一工作台架构

## 1. 背景与问题

ADR-018 已确认通过 Nuxt Host 与 Layers 收敛企业前端，通过客户侧 Runtime 收敛业务后端，并整合同一租户的核心业务数据库。但“同一个构建产物”不自然等于“面向用户的一个业务系统”。

如果只是把 Aims、Assets、Altoc 等旧应用的菜单和页面放入同一个 Shell，用户仍然需要理解产品主档在哪个应用、版本在哪个应用、合同和客户资产如何跳转；相同对象仍可能出现多套入口、表单、权限提示和返回路径。

本 ADR 的目标是将前端的组织主线从“应用名与部署目录”逐步转向“用户任务、业务对象和履约链路”，而不借此重划全部后端领域或重写既有业务功能。

后续讨论进一步明确：技术宿主统一不应导致原树形菜单、项目集树或对象内导航丢失，也不应形成“旧 Console 外壳内再嵌一套 Enterprise 页头”的长期界面。少量横向入口可服务临时演示，但不能替代完整业务导航。恢复旧入口的可达性是迁移要求；原来的双栏外观不是必须永久保留的架构约束。

本轮进一步将人力资源从经营导航中独立：员工生命周期、岗位职级、人员成本事实和绩效管理形成独立业务区；经营聚焦财务、资金、业务核算和企业资源。增加的是业务发现入口，不是新的 People 独立应用、认证边界或数据库。

## 2. 决策摘要

采用以下目标路线：

> **单一 Enterprise Host + Foundation 共享能力 + 构建时业务 Layers + 面向业务对象的组合页面 + Runtime 查询/用例服务。**

核心决策：

1. 企业用户看到一个主 Shell、一个企业/环境上下文、一条统一业务侧栏和一套公共顶部栏；一级主入口固定为“工作台、产品、销售、交付与服务、经营、人力资源”，辅助入口为“协同文档、控制台”。Aims/Assets/Altoc 等保留为工程与业务主责标识，不再默认作为一级用户入口。
2. 信息架构按业务域组织。全局功能菜单最多三级，在同一侧栏按需展开；复杂工作围绕产品、客户、合同、项目、客户交付资产等对象形成工作台。功能菜单、业务对象树和对象内导航分别建模，不为减少菜单层级而删除项目集树或产品线树。
3. 优先采用现有 Nuxt/Vue 技术栈的构建时组合，不在首轮引入运行时微前端平台，也不把 iframe 作为所有业务页面的默认容器。
4. Host 管 Shell 与组合，领域 UI 管业务面板与交互，Runtime 管权威数据与业务规则。统一工作台不是新的业务主档、权限引擎或数据库。
5. 旧应用前缀 URL 保留兼容窗口；新业务 URL 由同一类型化导航契约生成，不把 URL 一次性改造作为先决条件。
6. 同一用户的已有有效权限按统一规则展示；业务工作视图不等于互斥安全角色，切换菜单不要求重新登录或更换角色。
7. 页面可以先消费现有正式服务契约，后台再按 ADR-018 替换查询路径；前端业务整合、业务合库和 Auth 迁移不强行同批切换。
8. 用 Aims + Assets 产品链做首个端到端试点，再逐步扩展商业履约链路；完成标准是业务任务可连续完成，不是减少了几个 Worker 或菜单。
9. 统一业务侧栏是最终默认样式；“业务区窄栏＋业务树”只作为有退出条件的过渡。两种呈现共用同一份导航声明和同一个主 Shell，不以应用切换器、重复页头或第二套会话作为整合方案。首轮不建设两套可长期切换的独立布局产品。
10. 原有可用入口必须有新归属或受控兼容去向。菜单映射、页面注册、BFF/API 接入和权限条件共同验收；不能仅凭页面已注册就宣布可用，也不能为使菜单可点击而放宽服务端鉴权。
11. “人力资源”独立承载组织岗位、员工生命周期、人员成本事实与绩效管理；经营保留业务成本归集、核算及财务口径的绩效金额。菜单独立不改变领域数据主责，不拆分统一 Host、会话或租户业务库，也不产生自动拥有全部人力资源数据的角色。

## 3. 目标与非目标

### 3.1 本次要实现

- 用户从业务入口进入，围绕对象查看、决策、执行并回到原上下文。
- 已迁移页面共享导航、会话初始化、权限快照、公共交互和错误语义。
- 跨域页面复用主责域的面板和命令，不复制另一套编辑与状态规则。
- 保持刷新、深链接、前进/后退、书签、外部通知链接及旧 API 合同可用。
- 支持逐租户/业务链路切换、故障降级与整包回退，不削弱客户侧边界。
- 保留完整树形业务导航、适用的项目集/产品线对象树与原业务入口的明确去向。
- 在已迁移流程中消除重复应用页头、重复通知/个人菜单和重复退出入口。
- 人事管理入口可从“人力资源”直接发现；个人事务继续通过工作台访问同一正式能力，人力资源与经营按既有权限协作。

### 3.2 本次不承诺

不一次性重做所有 ERP/CRM 功能，不实现通用低代码门户，不自动合并语义不同的产品/空间/合同/财务对象，不新增第二份中央关系主档。不把重命名目录、升级全部依赖、改全部业务 URL 或引入新的状态管理框架作为整合前置条件。

不照搬 Cloudflare 的具体产品目录或视觉像素；“Dashboard 样式”在本 ADR 中专指统一 Shell、业务分组与按需展开的侧栏，不表示需要 Cloudflare 专用前端技术。首轮不建设任意拖拽菜单设计器、独立权限引擎或双布局长期并行平台。

Platform 管理端保持独立。Codocs 编辑器、Collab、Workflow、通知、Connector 等按 ADR-018 首轮保留真实运行边界；适用 UI 可逐步整合，不等于它们的服务也必须一起合并。legacy Account 不纳入本 ADR。

人力资源入口首轮承接既有人员、任职、成本与绩效能力；招聘、考勤、培训、工资发放等没有纳入当前范围的能力，仍需单独评审，不为填满人力资源菜单新增空页面或默认承诺完整 HR 系统。

## 4. 企业侧信息架构

### 4.1 已确认的一级业务入口

在已确认的短名称基础上，将 HR（人力资源）从经营独立，形成“工作台、产品、销售、交付与服务、经营、人力资源”六个主入口与“协同文档、控制台”两个辅助入口，即“6＋2”。一级显示名称统一为“人力资源”，页面说明可使用“人力资源”。这里确认的是导航组织，不表示所有子功能均已实现或每个用户都应看到全部入口。


| 用户入口  | 位置   | 核心工作                                  | 可能贡献 UI 的内部领域                                       |
| ----- | ---- | ------------------------------------- | --------------------------------------------------- |
| 工作台   | 主入口  | 我的待办、任务、审批、个人事务与日常协作                  | Aims / Workflow / Console 等                         |
| 产品    | 主入口  | 产品目录、管理空间、功能、需求、版本、研发协同与产品资产；后续接入商业规格 | Assets / Aims；后续引用 Altoc 商业规格                       |
| 销售    | 主入口  | 客户、线索/商机、报价/投标、销售/维保合同、服务权益、结算跟踪与回款安排 | Altoc；按权限引用 Finance/Aims/Assets                     |
| 交付与服务 | 主入口  | 交付与维护项目、任务/工时、成果/验收、客户交付资产与持续服务       | Aims / Assets / Altoc 的适用能力                         |
| 经营    | 主入口  | 财务收支、账户资金、业务成本核算、经营分析和企业自用资源          | Finance / Assets 等；按权限引用 Altoc/Aims/People 的既有事实或汇总 |
| 人力资源  | 主入口  | 组织与岗位、员工生命周期、人员成本事实、绩效周期与评价结果         | People；按既有契约引用 Console Directory、正式人事事实源及其他领域       |
| 协同文档  | 辅助入口 | 跨业务文档发现、空间、协作、评审与复用；业务内仍保留上下文入口       | Codocs；其他领域引用同一文档                                   |
| 控制台   | 辅助入口 | 企业配置、目录、身份/权限、规则、流程、集成/运行与安全审计        | Console / Workflow 及相应领域配置能力                        |


“交付与服务”明确包含维护与持续服务；“经营”不只是看板，财务、核算和企业资源的二级分组必须直接可达；“人力资源”独立管理人员及其任职、成本基础和绩效，不要求先进入经营；“控制台”是企业配置与安全管理入口，不是 Platform 管理端，也不承载正常报销、入职、合同或项目办理。

人力资源中的“组织与岗位、员工管理、人员成本、绩效管理”分别成组，不再使用“成本与绩效”混合分组。经营中的项目/合同人工成本和绩效金额继续引用正式事实，不能因人力资源独立而移除必要核算视图或另建一套人员成本数据。具体边界见 §4.7。

通知、搜索、收藏与个人设置属于 Shell 公共能力，不成为另一套应用切换器。全局业务搜索可后续分步提供，不以未建搜索平台阻塞产品试点。

同一对象只维护一套正式详情与编辑实现，允许从不同业务入口发现它。研发项目可从产品进入，也可从项目总览进入；不复制为两种项目。资产按业务用途进入产品、交付与服务或经营，不因菜单归属调整改变 Assets 的数据主责。完整二三级菜单及归属细则仅在[配套规范](./Enterprise-Business-Navigation-and-Interaction-Spec.md)维护。

### 4.2 导航与权限的关系

模块 manifest 仍是资源、动作与角色技术事实源。增加业务导航声明，引用这些既有 capability/action 标识；构建时生成统一目录并检查引用，不在 Host/Platform/Console 手写三份权限表。

可显示入口 = 已有可达实现或批准的兼容入口 + 企业整体资格 + 适用的部署/配置条件 + 用户可见权限。该表达式只说明显示逻辑，不代替服务端最终授权。纯分组随可见子项出现，不要求用户同时拥有整个业务区的全部子权限，也不把经营权限作为人力资源入口的前置条件。员工基本信息、任职、成本与绩效分别遵守既有资源、对象和字段权限；能看员工档案或业务成本汇总，不自动获得个人薪酬、成本明细或绩效评价权限。

区分未实现、人员无权、能力未部署/配置和临时故障。未实现能力不以空白页冒充完成；临时故障不能自动切换旧数据源；原来可用但尚未迁入 Host 的入口必须有受控兼容去向。经授权的配置说明可以显示真实启用条件，不能显示“请购买模块”或泄漏无权对象。

普通用户使用现有合并权限；“销售视图”“研发视图”“经营视图”“人力资源视图”只调整排序、默认首页和展开偏好，不授予/撤销权限。管理员的权限模拟必须显式标识，不与实际授权混淆。业务导航组名也不能作为后端 appCode 或 scope 的替代值。

### 4.3 菜单层级与对象层级

全局功能导航默认最多三级：一级业务区、二级工作领域、三级具体业务页面。二级分组可以默认展开，用户不必机械地点击三次；工作台或已实现的业务首页可直接进入。

功能菜单与对象导航分别建模。产品线/产品、项目集/项目、文档文件夹属于业务对象树，按权限、分页/按需加载与上下文显示，不把所有对象展开到全局固定菜单中。进入对象后使用对象内分组、局部页签或同一侧栏中的对象导航，不继续堆砌全局第四、第五级功能菜单。

新增、编辑、审批、发布、分配等是业务动作，原则上保留为页面操作；菜单进入列表、工作区或办理中心，不为凑层级制造动作空页面。

### 4.4 默认呈现：单一 Dashboard Shell 与统一业务侧栏

最终默认采用类似 Dashboard 的一套公共顶部栏和一条统一业务侧栏，不再保留固定的“应用切换栏＋各应用业务树”。保留树形导航，取消的是“先选内部应用才能做业务”的使用方式，不是树形结构本身。


| 区域    | 职责                                    |
| ----- | ------------------------------------- |
| 公共顶部栏 | 汇智云标识、当前企业、必要的环境提示、搜索、通知与个人菜单；仅一套退出入口 |
| 统一侧栏  | 六个主业务入口；分隔区内放协同文档、控制台；同一栏按需展开二三级菜单      |
| 内容顶部  | 面包屑、当前对象、标题与主要业务操作；对象标题不构成第二套应用页头     |
| 内容区域  | 列表、详情、表单、看板及局部对象导航                    |


侧栏宽度以 248～280 像素作为桌面设计起点，可调整和折叠；它不是硬编码验收值，最终按最长标签、目标屏幕和可访问性测试冻结。表格和看板优先利用剩余内容宽度，表单可局部限宽。

菜单默认展开当前业务区，恢复其适用的分组状态，其他业务区默认收起；当前路由的祖先自动展开并定位。节点的进入首页与展开动作使用明确的不同点击目标。没有实际首页的纯分组只展开，不制造概览空页。

折叠/窄屏布局仍使用同一导航数据；支持键盘、焦点回退与可访问名称，不依赖鼠标悬停或只有图标。收藏/最近访问可以提升效率，但不是完整菜单的替代，也不是首批整合的前置功能。

### 4.5 对象工作区模式与返回路径

产品、合同等一般详情保留业务侧栏，在内容区使用少量对象分组。需要长期驻留的复杂项目工作区，可将同一条侧栏切换为项目上下文导航，并固定显示返回业务区入口和项目切换器；不另加一条长期常驻的项目导航栏。

项目切换器可打开项目集/项目树；产品或文档对象树放在相应业务页或选择面板中。禁止“应用栏＋业务树＋对象树＋多层页签”同时常驻并无限叠加。

对象路由决定工作区内容，经过验证的来源决定返回目标。来自产品的研发项目应能返回相应产品上下文，来自交付与服务列表的项目应能返回交付与服务列表；无可靠来源时回到登记的默认入口。返回时恢复允许的筛选、分页、排序和树展开状态；首次深链接、刷新、新标签页和前进后退同样可用，不能只依赖内存中的上次菜单点击。

### 4.6 双栏过渡与唯一外壳

过渡期可暂用“业务区窄栏＋业务树”，但外侧名称必须按 §4.1 组织，且共用同一份导航声明、路由、权限引用和主 Shell。它只是一种临时呈现，不建设另一套独立菜单/会话实现；退出条件并入 FE-1/FE-4 的台账。

旧 Console 容器与 Enterprise 在同一屏内组合时，必须明确哪一层拥有公共导航、通知和个人菜单；已迁移流程不得长期出现两套公共标题和退出按钮。可采用受控直接进入 Host 的路由，或经批准的无重复 chrome 兼容方式；不能通过扩大 iframe 权限、共享全权限 Token 或删除安全边界解决。

保留的旧独立应用仍可在过渡期采用原布局。仅当当前文档进入该兼容页面时才显示它的布局，并提供明确返回；不把该体验标成已完成常驻统一 Shell。未迁移页面不因新侧栏发布而丢失入口。

### 4.7 人力资源、经营、交付与服务与控制台的职责边界

人力资源独立是信息架构调整，不重新划分后端事实源。人力资源回答“有哪些人、如何任职、怎样评价、成本基础是什么”；经营回答“投入如何归集、形成什么收入、现金流与经营结果”。


| 业务内容                 | 主要发现入口      | 责任与协作约束                                                            |
| -------------------- | ----------- | ------------------------------------------------------------------ |
| 组织架构、岗位与职级           | 人力资源        | 读取或通过正式命令维护既有事实；Console Directory、People 与外部正式人事事实源的权威分工不变，不新建组织主档 |
| 员工档案、入职、任职变更、离职交接    | 人力资源        | 由既有人事领域办理；账号停用、资产回收通过正式协作链处理，不因人事操作授予安全管理员权限                       |
| 职级与成本标准、人员成本快照       | 人力资源        | 保留一套人员成本事实及生效期间、确认和历史快照；经营按权限引用                                    |
| 工时填报、项目投入与确认         | 工作台 / 交付与服务 | 复用既有工时与项目执行能力，不把工时记录迁成人事成本副本                                       |
| 项目/合同人工成本归集、分摊与核算    | 经营          | 按既有核算规则引用人员成本和投入事实，不独立维护另一份工资或人员成本基数                               |
| 绩效周期、贡献快照、评价与确认结果    | 人力资源        | 保留评价及确认语义；经营可引用获授权的结果，不改写评价事实                                      |
| 奖金、提成等财务口径的绩效金额      | 经营          | 继续由正式金额与核算契约处理，不与绩效评价混为一表，不据此新增工资发放系统                              |
| 登录账号、角色授权、服务身份及凭证    | 控制台         | 管理访问能力与安全治理，不替代员工档案、任职与绩效                                          |
| 我的工时、周报、报销及获准的个人绩效视图 | 工作台         | 复用正式业务对象的个人范围视图；不因为个人入口建立第二套状态或数据                                  |


协作主线为“人力资源提供人员成本事实 → 交付与服务提供工时与投入事实 → 经营按正式规则归集与核算”。当前人员成本调整不得反向覆盖已冻结的历史成本、核算或绩效金额；修正按既有版本、调整与审计机制处理。页面只展示当前用户获授权的字段和汇总，不要求获得全部底层薪酬明细权限才能使用获准的业务汇总。

控制台可以保留组织目录及适用人事配置的治理或快捷入口，但必须引用同一正式对象与实现；人力资源组织视图不因此成为第二份 Directory。员工离职与账号/资产处理保持原有审批、状态和失败处理规则，不能由浏览器跨域直接写表或临时扩大权限。

## 5. 面向对象的统一工作台

### 5.1 公共页面结构

采用“企业 Shell → 业务区 → 对象工作台 → 对象内页面”的结构。默认保留对象摘要、主要操作、状态、责任人与面包屑；切换对象内页面只替换内容，不重新初始化完整 Shell。

对象内部优先使用“总览 + 少量业务组 + 二级导航/页面锚点”，不把所有字段展开为十几个并列页签，也不叠加三级 Tab。列表筛选、分页与排序可在可分享 URL 中保存；临时交互状态和敏感草稿不放进 URL。

通用交互只统一具有共性部分：筛选和表格、空/无权/错误状态、确认、保存/取消、未保存提示、附件入口、时间/金额/状态显示、键盘焦点及窄屏布局。审批、结算和发布的专业语义仍由业务域控制。

### 5.2 首个试点：产品业务工作台


| 对象内分组 | 内容                       | 责任与范围                           |
| ----- | ------------------------ | ------------------------------- |
| 总览    | 当前产品定义、阶段状态、相关规划/发布与必要提醒 | 组合查询；不新建产品主档                    |
| 产品定义  | 基本信息、产品线、长期能力与资料入口       | 主档归 Assets；长期功能按 Aims 既有领域模型    |
| 规划与发布 | 产品管理空间、需求、版本、执行关联与发布证据   | Aims 负责；依据权限逐项提供                |
| 商业与客户 | 可售规格、合同关联、客户交付与在用情况      | 后续由 Altoc/Assets 等贡献；首轮未接入不虚报可用 |


**产品业务工作台是界面概念，不等于 Aims 的“产品管理空间”。** Assets 产品与 Aims 规划空间/组件的现有关系必须保留，不能默认一产品恰好对应一空间。以稳定产品 `code` 进入产品视图；规划空间有自己的受控标识和路由，关联通过已有 `product_component_sources` 等正式关系读取。无法唯一解析时展示用户有权选择的关联，而非取第一条或新建重复对象。

产品主档改名后，工作台的当前名称随后续正常查询更新；接纳决定、已发布版本和历史快照按 ADR-018 保留。UI 移除“同步名称”动作前，先验证该同步是否还承担授权过滤、水位或来源证据。

首轮在既有能力范围内完成“查找产品 → 看当前定义 → 进入相关规划/版本 → 查看执行进度 → 返回产品”，并验证权限与名称一致性；不以新增全部产品商业化功能作为试点验收条件。

### 5.3 后续：合同工作台与商业履约链

合同详情沿用已经讨论的分组，不把事实与执行混写：


| 一级分组 | 二级内容                               |
| ---- | ---------------------------------- |
| 总览   | 关键事实、履约进展、结算/回款摘要和待处理事项            |
| 合同事实 | 基本信息；合同标的（产品与服务）；合同条款（含付款/质保）；合同文本 |
| 合同执行 | 履约；结算与回款，内部按业务对象和锚点区分              |
| 合同管理 | 关联与管理；操作历史                         |


付款/质保条款属于合同事实；结算和回款属于执行。经营回款计划与 Finance 入账/核销事实分别引用，不能为了“一个页面”合并语义。

从合同进入交付项目、客户交付资产、维保与维护项目时保留来源上下文和授权边界。只携带必要对象引用，不在前端拼装一笔跨域事务；“发起项目”“形成交付资产”等写操作调用主责领域或 Runtime 用例服务。

### 5.4 项目工作台与项目集导航

项目工作台复用一套项目详情，依据项目类型与权限裁剪内容，而非按产品/交付与服务入口复制不同项目系统。默认对象内导航如下：


| 对象内分组 | 内容                     |
| ----- | ---------------------- |
| 概览    | 项目目标、状态、进展、风险与责任人      |
| 计划与执行 | 里程碑、目标、任务看板，以及适用的需求/变更 |
| 交付与质量 | 成果、验收、质量检查与项目文档        |
| 团队与投入 | 成员、工时、周报、资源与获授权的成本摘要   |
| 项目管理  | 设置、关联产品/合同与操作历史        |


这些分组规定现有能力的目标位置，不承诺未具备的项目类型已有全部功能。交付与服务区项目总览默认面向交付/维护，保留获授权的全部项目视图；研发项目从产品发现，日常事务从工作台发现。项目集树/项目树保留按需展开、收藏和定位能力，完整导航不依赖新增跨项目汇总服务。

### 5.5 个人入口、多入口发现与唯一对象实现

“我的任务、我的工时、我的报销、我的绩效”等原则上是正式业务页面的个人范围视图，不新增第二套数据表或业务状态机。文档评审待办可汇总到工作台，原文档页面仍保留相同评审入口和历史；产品资料、合同文本、项目文档继续在业务上下文中引用同一份文档。

同一对象允许多处发现，只有一个当前正式详情/编辑实现；快捷入口引用正式目的地并传递批准的过滤或对象上下文。无权限时不得利用其他入口绕过业务对象、字段或聚合权限。

## 6. 前端技术架构与责任

### 6.1 采用构建时组合

Nuxt Layers 用于共享配置、页面和 UI 能力；它是构建/文件组合机制，有覆盖优先级，并不提供独立进程或强隔离。[F1]


| 层次              | 应当负责                                                  | 不应当负责                            |
| --------------- | ----------------------------------------------------- | -------------------------------- |
| Enterprise Host | 唯一 app.vue、主布局、业务导航、会话 bootstrap 协调、路由注册、组合页面入口及薄 BFF | 数据库访问、权威 Session、复制业务写入规则        |
| Foundation      | 设计基础、请求/会话/权限客户端、可复用导航与状态约定、公共交互                      | 吸收全部业务对象逻辑或成为新的全局业务仓库            |
| 领域 UI Layer     | 领域面板、表单、已授权操作入口、明确路由/能力声明                             | 第二套 Shell、全局 appCode、默认全局插件/cron |
| 业务组合页面          | 跨域区块的布局、加载/错误状态、对象上下文和允许的动作编排                         | 用前端数据合并替代权威事实、私建权限规则或跨域事务        |
| Runtime 查询/用例服务 | 聚合 DTO、权威读写、范围/字段授权、事务及可靠任务                           | UI 布局和浏览器状态                      |
| 保留的独立能力         | 编辑、协作、协议等真实专用能力                                       | 因为同域名而获得 Host 的所有权限              |


组合页面建议放在 `enterprise/app/features/<业务工作台>/`，或同等用途的 workspace package；它不是新的后端服务，也不要求迁走所有原目录。单域功能留在领域 UI 的公开导出中；禁止依赖另一个 Layer 的私有 store 或 server utils。

### 6.2 不采用的默认路线


| 路线                                          | 当前判断                                             |
| ------------------------------------------- | ------------------------------------------------ |
| 只用网关把独立应用放在同域名                              | 可过渡；跨文档导航与第二次初始化仍可能存在，不能认定已完成统一 Shell            |
| 所有业务页面 iframe 化                             | 不采用；只有需要独立运行的编辑器等例外按受控嵌入合同保留                     |
| 首轮引入 Module Federation/WebFragments 等运行时微前端 | 不采用；现有 Nuxt monorepo 与统一发布目标优先构建时组合，不新增远程装载/兼容平台 |
| 整体重写为另一个前端框架                                | 不采用；与业务整合目标无直接关系                                 |
| 无限拆分/扩展 Foundation                          | 不采用；基础设施与业务页面保持边界                                |


只有实际出现独立团队发布、不可共用运行依赖或独立故障域需求，并以测量/发布证据证明当前方式不足时，才单独评审运行时微前端。并非达到某个菜单数量就自动切换架构。

### 6.3 导航注册与界面组件的职责

Host 维护统一导航编排，领域 UI 提供导航贡献、可复用面板与对象导航出口。Foundation 提供通用侧栏、折叠、焦点和上下文协定，不承载完整业务目录。

提取原侧栏时拆分导航 UI、项目/产品上下文和公共初始化；不得将旧 `default.vue` 连同心跳、全量预取、会话与权限初始化一起复制，造成多个业务 Layer 各自启动公共任务。

导航最小声明包括稳定节点 ID、标签、业务区/父节点/排序、节点类型、命名路由或正式目的地引用、活动状态匹配、既有权限引用和受控可用性。字段和文件路径是待冻结合同；本 ADR 不声称存在相应代码。运行时菜单、路由、API 就绪性不应各自手写互不核验的白名单；使用同源登记或双向一致性测试防止漂移。菜单引用权限，绝不生成新的授权事实。

根布局只负责业务区和对象模式切换。初期无需通用菜单设计器或远程插件平台；可以采用显式类型化配置和现有 Nuxt 注册机制，先服务 Aims/Assets 试点。完整字段建议见[配套规范](./Enterprise-Business-Navigation-and-Interaction-Spec.md)。

## 7. 路由、旧地址和跨业务导航

### 7.1 同时保留工程标识与业务标识

第一阶段可将旧页面显式挂载到 `/aims/...`、`/assets/...`；用户导航先改为业务名称。完成产品试点后，再引入 `/products/...`、`/product-spaces/...` 等业务路径。具体地址属于待冻结的路由合同，不能从示例反推现有端点。

逻辑路由名与物理路径分离。组件调用类型化导航函数/命名路由，传入对象种类、稳定 `code` 或正式不透明引用及允许的来源信息；不硬编码旧应用域名，也不把内部自增 ID 当成跨租户全局标识。旧数字 ID 到稳定引用的映射由经过授权的兼容解析处理，不改变原数据身份。

Nuxt 文件路由与 `extendPages` 可用于生成/调整路由；通过显式来源注册解决 Layer 路径冲突，不能简单给所有扫描页无差别加前缀。[F2]

### 7.2 兼容与重定向规则

一个逻辑业务目的地在某租户/环境/发布版本下只有一个当前实现。注册中保留旧地址、旧参数、query 白名单、必要片段标识、目标路由与回退路径。

简单且参数语义相同的地址可用 alias；需要 ID/code 转换、跨应用回退或参数翻译时使用兼容路由/解析器。首轮使用可回退的定向，不提前下发无法撤销的永久重定向。浏览器 hash 不发送到服务端；涉及旧锚点的映射需在客户端兼容层处理。

只对页面安全导航做 URL 重定向。POST/PUT/PATCH/DELETE、OIDC callback 和 webhook 必须保留专门协议/兼容适配器，不能靠页面 302 迁移，更不能重放写请求。

外部链接支持直接刷新、登录后返回、打开新标签页、浏览器前进后退。returnTo/来源地址仅允许本站受控路由或登记的外部 origin，禁止开放重定向；URL 不携带访问令牌、Secret 或敏感草稿。

### 7.3 菜单迁移映射与可达性闭环

原有每个可用菜单、隐藏但正式支持的深链接，以及相关动作页面，都必须登记目标业务位置、原/新路由与参数、权限、适用租户/环境/版本、兼容方式、负责人和验证证据。

菜单迁移状态至少区分“已接入 Host、旧正式兼容入口、后续规划、已退役”；这是待实现的登记语义，不是当前代码枚举。人员无权、缺少部署配置与临时故障是独立维度，不能混成一个 `enabled` 开关。

Host 可用入口的通过条件是“菜单/深链接 → 路由解析 → 页面 → 所有必要 BFF/API → 正式业务处理”的完整链路，含方法、参数、权限和失败场景。构建/契约测试应发现已注册页面依赖的正式接口被就绪性中间件错误拦截等问题。禁止为修复入口而全局放开 API，也不要求为所有未迁移功能复制新页面。

菜单不再列出不等于允许删除功能。未列入本版目标目录的既有细分能力必须在 FE-0 映射到所属业务页、对象工作区或受控兼容入口；删除依赖明确退役决定与消费者归零证据。

本轮将原方案“经营→人事管理”“经营→成本与绩效”中的人员业务迁入人力资源相应分组。已登记的业务节点 ID、正式目的地和权限引用应尽量保留，只更新业务区、父节点与排序；节点确需拆分时登记别名及偏好迁移，不能仅因重新分组而强制改 API、scope 或所有旧 URL。旧经营位置的书签、收藏和正式兼容入口继续解析到同一获授权对象，不重放业务写入。

## 8. 身份、状态与数据加载

### 8.1 一个可验证上下文，不是一个全权限身份

Host 复用 Foundation 与 ADR-017 的登录/会话路径，为当前文档建立一次去重的 bootstrap；后续按会话、策略到期或变更刷新，不按切入某个 Layer 重新登录。

bootstrap 只提供渲染需要的最小用户信息、tenant/environment、可用导航、权限版本、运行能力与非敏感状态，不附带全企业 Directory、Vault 内容或可调用所有后端的管理员令牌。

每次 Host → Runtime 请求保持服务身份与用户委托区分。请求绑定目标租户/环境/部署和业务动作；业务导航组名不作为授权模块身份。既有精确 scope 在合同迁移前继续有效，不以“统一 Host”放宽校验。

### 8.2 请求级隔离与上下文切换

服务端身份和连接上下文在每个请求中构造，浏览器状态按当前实例管理；禁止模块顶层可变单例保存当前租户、用户、Token 或请求客户端。Vue 官方指出 SSR 共享单例状态可能污染其他请求。[F3]

数据 key 包含适用的 tenant、environment、subject/有效权限版本、业务资源和查询参数。公共主题等非敏感数据可使用不同隔离级别，不强迫所有 key 携带全套字段。缓存 key 不是鉴权替代物。

企业/用户切换采用明确的切换屏障：处理未保存草稿 → 暂停新请求 → 取消旧请求与订阅 → 清理旧数据/KeepAlive → 服务端验证新 membership/context → 加载新 bootstrap → 恢复页面。每个请求携带本地上下文代次，旧代次迟到结果不得写入当前 store。切换失败进入安全状态，不把旧数据贴在新企业标题下。

多标签页的会话变更须通知其他标签清理并重新验证；通知不携带 Token，也不能作为授权证据。切换租户可选择完整文档导航作为安全实现，不强求全部切换都在 SPA 内完成。

侧栏展开、固定入口和上次访问属于偏好，按适用企业/环境/用户隔离；优先只持久化稳定菜单引用及非敏感偏好，不用本地存储保存无权对象名称或完整业务树。恢复偏好前重新过滤权限；撤权、退出及上下文切换后，旧对象名称、树节点、面包屑和迟到请求结果不得继续出现在新上下文。

### 8.3 页面数据与操作

首轮可由专用 BFF 通过明确白名单的正式 API 批量组合读取；已迁移业务优先调用 Runtime 聚合查询，避免浏览器 N+1。BFF 不成为业务事实源、通用代理或另一个数据库服务。

页面定义“必要区块”和“可选区块”。根对象无法验证或无权时，不继续显示其旧摘要；可选区块失败时局部显示明确状态。无权字段不进入 HTML、hydration payload 或仅 CSS 隐藏的 DOM。金额/总数不可用时不能用 0 假装真实业务结果。

用户写入调用主责命令；统一操作反馈展示成功、冲突、待处理和不确定结果。自动重试只用于已证明幂等的动作；跨域原子操作在 Runtime 执行，浏览器不以连续两个 POST 伪装事务。

## 9. 独立能力嵌入、性能与运行

保留服务可以通过统一业务入口打开独立页面，或对特定编辑器使用受控 iframe；必须标明这仍是独立文档/运行边界，而非假装 Shell 内存一直保留。已有编辑器的成熟方式优先保留，不借本 ADR 顺带重写。

嵌入合同至少约定允许 origin、CSP/frame 限制、最小权限、尺寸/主题/关闭/脏状态事件、认证和退出。`postMessage` 验证精确 origin、source 与消息 schema，不通过 `*` 广播凭据；消息里的 tenant/subject 不能代替服务端验证。[F4]

已迁移业务页面按路由和重组件懒加载；全量功能资格不意味着首次下载全部代码。常驻 Shell 不执行每个模块的全量预取，不将重编辑器、图表或所有图标集合放入全局插件。路由动态导入由构建产物验证，而不是只看文件是否被拆目录。[F5]

默认沿用可支持的现有 SSR/客户端策略；企业私有 HTML、敏感 API 和权限相关 payload 不公开预渲染或共享缓存。Cloudflare 与 PM2/本地 Host 的差异收敛到部署适配，数据与认证边界相同。

在 ADR-018 性能基线上测量初始加载、交互导航、会话请求次数、并发 SSR、Worker 上传/启动/内存、API/SQL 扇出、构建时间。统一发布扩大故障影响，页面错误边界不能隔离顶层插件或整个 Host 崩溃；必须保留整包回退。

## 10. 迁移阶段与通过条件


| 阶段                | 建设范围                                                             | 用户可见变化                                    | 放行条件                                            |
| ----------------- | ---------------------------------------------------------------- | ----------------------------------------- | ----------------------------------------------- |
| FE-0 盘点与冻结        | 原菜单/深链接完整映射；路由、身份、自动扫描、副作用、树与上下文、数据依赖及性能基线                       | 不改变生产路径；冻结八个入口（六主两辅）、人力资源旧入口映射、二三级试点子集和返回规则 | 每个旧入口有明确归属；路由、权限、必要 API、任务、兼容和回退合同明确            |
| FE-1 单一 Shell 与导航 | Host + Foundation + Aims/Assets 可组合入口；接入完整树形侧栏、权限过滤和受控旧入口；公共区域去重 | 默认走统一业务侧栏；暂可保留旧业务页面结构；确需双栏时仅作同源过渡         | 无第二会话/公共页头、无入口静默丢失；菜单→页面→必要 API、旧链接、隔离及返回路径回归通过 |
| FE-2 产品工作台        | 产品、规划空间、版本/执行组合；产品对象导航和研发项目返回上下文                                 | 从产品完成定义、规划、版本、执行的连续工作，不再拼接 Aims/Assets    | 当前事实一致、历史保留、权限不退化；产品线树与项目切换按场景可用                |
| FE-3 商业履约链        | 按用例扩展销售、交付与服务、经营、人力资源及文档/控制台适用能力                                   | 客户→合同→项目→客户资产/维护，以及人力成本事实＋工时投入→经营核算连续工作   | 每条链独立通过授权、数据、事务与真实岗位任务验收；人力资源独立可达，人员事实与经营核算不重复维护  |
| FE-4 收口与优化        | 删除已无人使用的旧入口/同步/身份；退出重复外壳及临时双栏；完善性能与可访问性                          | 企业侧不再以内部应用切换为默认方式；一套导航契约                  | 消费方归零、整包回退/恢复演练、角色/屏幕验证和性能预算通过后再删除              |


以上阶段不是工期承诺；每阶段允许多个小批次。FE-1/FE-2 可在物理合库完成前使用受控正式 API 落地。未经 ADR-017 凭据边界验收的 Console/Auth 路径不能因为前端迁移而被放行。

近期顺序是“先盘点并保住旧入口 → 单一 Shell 与统一侧栏 → 产品/项目/合同对象工作台 → 删除重复入口”。统一侧栏不是全量页面重写，导航改造、Auth 迁移和物理合库不捆绑同一次发布。各批次范围及剩余旧入口只在统一实施台账登记。人力资源一级归属与旧入口映射在 FE-0 冻结；已有正式人员能力可按批准范围在 FE-1 通过 Host 或受控兼容入口先行保留，不要求等全部人力资源功能迁入才显示已有入口，也不以建设完整 HR 系统阻塞产品试点。

FE-2 及之后的验收至少包含真实岗位的任务脚本，不只使用管理员账号检查菜单和截图。文档、构建成功或演示视频不能替代隔离、并发和失败路径测试。

路由迁移状态来自服务端受控配置并绑定租户/环境/发布版本，用户不能用 query/cookie 私自选择旧数据源。灰度时先固定用户/会话适用版本，旧资源保留兼容窗口；回退 UI 仍访问当前唯一权威存储。

## 12. 影响、取舍与衔接

收益：用户不再拼接应用；一级业务名称稳定，三级树和对象工作区保留复杂业务的可达性；统一设计与状态更容易，业务对象可跨域查看，前后端的物理布局不会强迫用户理解工程结构。

代价：Host 统一发布扩大共同失败范围；组合页增加跨域查询契约与权限场景；旧链接/会话/静态资源需要兼容窗口。统一侧栏还需控制长菜单、对象模式转换和偏好恢复。通过首批产品链、公开 UI 导出、单一导航注册、明确返回规则、严格请求上下文及可验证回退控制成本，不新建庞大插件市场或万能页面 DSL。

布局取舍：不把“应用菜单＋各应用菜单”保留为最终用户模型；默认统一侧栏更符合本项目已确认的八个入口（六主两辅）与一体化目标。业务区窄栏＋业务树可减小过渡改动，但必须共享同一合同并在验收后收口。未来若真实岗位测试证明统一侧栏定位成本显著偏高，再单独评审，而不是预先建设两套长期布局。

人力资源独立增加一个一级入口，使员工生命周期和评价工作不再埋在人事/财务混合分组中；通过按权限显示和默认展开控制长度，不回到应用切换模式。它不要求新增 People 独立部署、数据库或全权限“人力资源角色”。

本 ADR 在前端组织上细化 ADR-018，不改变 Assets/Aims/Altoc/Finance/People 的事实责任，不取消 ADR-017 的客户侧 Auth/Vault 权威位置。现有 `MODULE_CONTRACTS.md`、Foundation、各模块 manifest、Runtime API 与发布合同须随实际迁移同步更新；未迁移路径继续执行旧正式合同。
