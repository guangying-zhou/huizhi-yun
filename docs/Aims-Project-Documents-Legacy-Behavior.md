## 2. 原页面是什么样

### 入口与布局

项目详情中的“文档”页，独立端路径 `/projects/<项目ID>/documents`；另有 `/project-documents` 项目文档总览，按项目集组织项目，选项目查看。项目集详情的“项目集文档”是另一块独立区域，不是项目文档页里的同义分类。

项目文档页左侧为库与归属选择，右侧为文件夹树 / 文档列表，顶部可搜索和刷新：

| 页面分类 | 展示内容 |
| --- | --- |
| 规范文档（Markdown） | 下分“项目级文档”和各里程碑；里程碑显示阶段标记与文档数量 |
| 其他格式文档 | Word、Excel、PowerPoint、PDF、TXT、CSV、压缩包等；不是按每个里程碑再分一套左栏 |
| 全部 / Markdown / 其他计数 | 文件数量，不把文件夹算成文件 |

仓库里的 Markdown 和交付物文档可以进入列表，**不是另一个名为“仓库文档”或“交付物”的独立左栏页签**。文档选择弹窗才有“部门文档 / 项目组文档 / 项目仓库文档”三个来源页签。

列表与树展示标题、分类、上传人、更新时间，以及访问状态 / 安全级别等信息；预览附件时显示文件类型、大小与存储信息。搜索覆盖标题、分类和上传人。来源证据：旧 `aims/app/pages/projects/[id]/documents.vue:350、393、419、551、789、1200、1413`；`aims/app/pages/project-documents.vue:117`；`aims/app/components/AimsDocumentPicker.vue:68`。

### 页面实际提供的操作

- 规范库：新建 Markdown、上传 `.md`、新建文件夹；新建时选择项目级或某个里程碑，可放进已有文件夹。
- 其他库：上传其他格式文件；浏览器限制 10 MB，旧上传服务另有 100 MB 限制。这是两层限制不一致，不能把 100 MB 当作原页面可上传大小。
- 文档：点击预览；符合权限时删除、打开访问控制；附件可下载，支持的类型可在线预览，不支持则提示下载查看。
- 虚拟交付物文档：预览；不在这个页面删除或改访问策略，提示回到任务交付处调整。
- 文件夹：展开、在其下创建；删除需要经理权限。删除并非“回收站”操作。

**关联已有 Codocs / 仓库文件的主要入口是任务、交付等处的文档选择器**，本项目文档页没有单独的“关联仓库文件”工具栏按钮。选择器返回引用，任务 / 成果记录关联后再汇入项目列表。不要把后台具备索引登记接口等同于页面具备所有操作按钮。来源：旧页面 `:189、930、994、1028、1111、1315、1654`；`aims/app/composables/useAimsDocumentPicker.ts:113、155`；`data-runtime/internal/apps/aims/work_item_documents.go:212、304`。

## 3. 三种来源怎样创建、保存和打开

| 来源 | 创建 / 关联方式 | Aims 保存什么 | 内容在哪里 | 打开方式 |
| --- | --- | --- | --- | --- |
| Codocs Markdown | 新建 Markdown 或上传 `.md`；也能从文档选择器引用已有 Codocs 文档 | 标题、归属、父目录、分类、Codocs UUID 等索引；任务/成果另存引用 | Codocs 文档元数据与 OSS 正文；不是 Aims 表里的正文 | 先确认当前项目与精确文档的关系，再向 Codocs 读正文；嵌入预览 |
| GitLab 仓库文件 | 从本项目已关联仓库选择文件，保存仓库路径、文件路径、可选 ref / commit | 引用与快照信息，不保存 GitLab 文件本体 | GitLab | 先核对项目访问、成员与仓库绑定，再用集成凭据读文件；有 commit 时按该引用读取 |
| 上传附件 | 其他格式上传至 Codocs 项目文件柜，再把文件信息登记到 Aims | 文件 UUID、项目、标题、分类、大小、OSS 路径等 | Codocs `cabinet_files` 元数据 + OSS 二进制对象 | 检查查看/下载权限，再取得限时预览/下载地址；文本或支持格式预览，其余下载 |

Aims 索引逻辑表为 `project_documents`（生产此次核对记录的物理表名为 `aims_project_documents`）；Codocs 正文记录为 `documents`，文件柜为 `cabinet_files`，策略为 `document_access_policies` / `document_access_grants`。这些表名只是说明各系统负责什么，不是本次迁移或写库指令。

### 容易混淆的两个细节

1. **`document_source=repo` 不一定是 GitLab 文件。** 旧附件上传也写这个值，并将 OSS 路径放入 `repo_file_path` / `oss_path`。页面按类别 / 扩展名分出附件，服务按 OSS 前缀识别项目文件柜。因此不能只用这一个字段判定“仓库文件”或迁移存储。
2. **删除索引不等于删除全部内容。** 对项目文件柜附件，旧服务先删除其 backing file，再删除 Aims 索引；普通 Codocs 文档与 GitLab 引用删除时，没有在该流程中删除 Codocs 正文或 GitLab 文件。文件夹的索引子树可由外键级联删除，但未看到逐个清理整棵树的 Codocs / OSS 内容的编排。

来源：旧 `aims/server/utils/projectDocumentWrites.ts:155、190、213、239`；`projectDocumentUpload.ts:164、225、252`；`codocs/server/utils/projectDocumentCreation.ts:13、25、31、45`；`codocs/server/api/v1/project-cabinet/upload.post.ts:92`；`aims/docs/aims_schema.sql:1108`。

### 创建顺序与失败边界

旧 Markdown 创建先建 Codocs 正文/元数据，再登记 Aims 索引；附件先上传 Codocs 文件柜，再登记 Aims。跨这两个系统不是一个数据库事务：后一步失败可能留下未列入 Aims 的内容。反过来，通用“登记文档”接口对无 backing 的普通文档是先登记 Aims，再创建空 Codocs 正文。Codocs 初次正文上传可以在对象缺失时补写，已有对象不覆盖；这不等于所有跨系统失败都有完整自动清理。

这段是代码的失败边界，**不是已确认生产出现过的孤儿数据**。来源：旧 `projectDocumentWrites.ts:166、178、271`；`projectDocumentUpload.ts:225、238`；`codocs/server/utils/projectDocumentCreation.ts:31、45`。

## 4. 文件夹、里程碑、工作项与交付物

### Aims 文件夹不是自动创建的 Codocs 项目空间

项目页点击“文件夹”，创建的是 Aims 的 `project_documents` 文件夹行，带 `parent_id` 和明确归属。新建项目或打开文档页的链路中，没有找到“自动为每个项目创建一个 Codocs 项目根文件夹”的动作。

在文件夹里新建 Markdown 时，页面把父目录标题逐级拼成 `folderPath` 传给 Codocs；当前所依据的旧创建实现主要传项目编码与路径，**不会据此自动把这些 Aims 目录复制成 Codocs 的 `folders` 树**。Codocs 有独立的项目类型文档/文件夹查询，选择器能浏览已有的 Codocs 文件夹，但两套目录不是天然同步关系。

OSS 的“目录”又是第三件事：正文新建使用 `codocs/document-creations/<UUID>/<摘要>.md`；旧兼容路径生成器还支持 `codocs/projects/<项目编码>/docs/<folderPath>/<标题>.md`；附件使用 `codocs/projects/<项目编码>/cabinet/<UUID>-<摘要>.<扩展名>`。这些对象前缀不是产品里的项目空间或权限目录。

来源：旧页面 `:824、846、930、946`；`projectDocumentWrites.ts:155、277`；`codocs/server/utils/projectDocumentCreation.ts:25、39`；`data-runtime/internal/apps/codocs/document_lifecycle.go:38、117`；`adapter.go:1163`。

### 不同业务归属怎样汇在一页

- 一条 Aims 文档可归项目、里程碑、工作项或项目集中的一种；子目录沿用父目录归属。
- 里程碑文档进入对应里程碑分类；工作项文档可根据所属里程碑归到该分类。
- 成果（deliverables）里的文档以虚拟列表项汇入，保留成果来源；它不是新复制的一份正文，也不是可在此随意删除的 Aims 普通索引。
- 项目库里已有同一份文档时会做去重，不应把成果引用当成第二份内容。

来源：旧 `data-runtime/internal/apps/aims/project_documents.go:429、493、655`；`aims/docs/aims_schema.sql:1109`；`aims/server/utils/accessibleProjectDocuments.ts:166、212、229、247、413`；页面 `:1114、1130`。

## 5. 谁能看、谁能写，以及离开项目后怎么办

原系统不是“能进入项目就拥有所有文档权限”，而是多层判定：项目可见性 → 当前关系/动作资格 → 具体文档策略；正文还要过 Codocs 侧的读取检查，仓库另需项目与仓库绑定。

| 动作 | 旧页面 / 服务的主要门槛 | 补充条件 |
| --- | --- | --- |
| 看列表 | 项目当前可访问；返回筛选后的文档 | Codocs 文档逐项检查访问策略；仓库/附件的旧 `repo` 列表分支要求项目成员；文件夹为成员保留 |
| 看 Codocs 正文 | 当前 active 成员，或负责人、创建人、范围管理员等代码认可关系；文档必须确实关联本项目或成果 | Codocs 再核验，不因为有 Aims 引用就授予访问 |
| 仓库预览 | 当前项目成员 + 仓库已与项目绑定 | 仓库编码精确相等；用应用集成凭据不意味着用户有任意仓库读取权 |
| 新建 / 上传 | 页面为负责人、manager、member 显示；服务端另核成员、负责人、创建人或范围管理员 | 只读 viewer 不因被列为成员就必然看到创建按钮；具体服务与 Runtime 门槛仍需通过 |
| 删除普通文档 | 经理/负责人，或该文档上传人 | 服务还要解析真实项目与当前访问；上传人的旧删除分支未独立要求“仍为成员”，不能声称离组必然禁止删除 |
| 删除文件夹 | 经理关系 | 会删除索引子树；不是回收至 Codocs 回收站 |
| 改访问策略 | 项目经理、负责人或服务认可的管理关系 | 旧服务还核当前 Codocs edit 权限，不能仅凭经理身份覆盖独立文档 ACL |
| 查访问审计 | 项目成员 | 策略检查会记录访问审计，不因此修改正文或授权策略 |

来源：旧页面 `:165、174、189`；`projectDocumentAccess.ts:220、290、329、475`；`projectDocumentAccessPolicy.ts:59、77、93`；`accessibleProjectDocuments.ts:413`。

### 文档策略能设置什么

访问控制弹窗包括：草稿 / 正式 / 归档；L0–L3；默认拒绝 / 查看 / 下载；是否允许企业内部访问、是否允许跨项目访问；对用户、项目、部门、角色设置查看 / 下载 / 编辑及到期时间。归档按只读处理。

旧策略核心的顺序是：先禁止只读文档编辑；认可来源项目的主体可通过；非来源主体不能访问草稿；正式/归档时，低等级且允许内部访问可通过查看（下载还受默认权限限制）；再检查白名单。L3 不认可项目/部门类跨范围授权，用户/角色授权仍走具体规则。不能把“默认可查看”单独理解为向全公司公开。

**有一项旧实现必须作为历史局限保留说明**：Aims 向文档策略传的 `actorProjectCodes` 来源包括“用户可见的项目列表”，不只是 active 成员项目；Codocs 核心用这组编码判定来源项目。因此代码中的 `source_project_member` 名称不能证明全链路严格等价于成员关系。列表可见、策略检查通过、正文可打开也可能不是同一个集合。新产品合同不要直接照抄这个名字。

来源：旧页面 `:296、307、312、744`；`projectDocumentAccess.ts:248、260`；`data-runtime/internal/apps/codocs/document_access.go:370、380、394、400、412`。

### 非成员与离组成员

非成员并非总是看不到项目；可见的公开项目不等于文档可读。正式文档可能经策略授权显示，草稿与仓库路径更严格。移除成员后，关系判定在后续请求重算，原成员资格不会永久冻结在文档引用里；但独立 Codocs 用户授权、其他可见项目、创建人身份或上传人删除分支等可能仍生效。**“退出项目就撤掉所有历史文档权限”不是旧代码已证明的统一规则**，应由用户明确决定。

## 6. 只挂项目集的两份历史文档

原 `/portfolios/<ID>` 页面有“项目集文档”区域，查询 `portfolio_id`，能建文件夹/文档；新建请求直接携 `portfolioId`，点文档以 UUID 打开嵌入 Codocs 编辑器。这说明项目集文档是有独立入口的，不应当作坏数据删除。

同时，通用删除服务主要按项目/里程碑/工作项解析真实项目，对仅项目集的记录可能无法解析项目而拒绝；旧页面有按钮并不证明全部生命周期闭环正常。本文没有这两份文档的历史访问/删除成功证据。

用户提供的生产事实：只有 2 份仅挂项目集的文档，最后一份于 2026-03-29 创建；另有 4 份挂实际项目。当前 P1 选项 A 明确：无法权威解析到实际 projectId 的文档（含继承这种父目录者）写入在 Codocs / 数据库副作用前返回 `409 project_document_portfolio_owner_unsupported`；这些纯项目集文档不混入项目页列表。它们的人员权限与对象范围合同另行设计，不凭相同编码猜作项目。

来源：旧 `aims/app/pages/portfolios/[id].vue:166、238、291、594`；`projectDocumentAccess.ts:181、475`；当前 `data-runtime/internal/apps/aims/enterprise_project_document_write.go:30、52` 的 owner 解析及 `docs/MODULE_CONTRACTS.md` 的项目集迁移缺口。

## 7. 与现在 Enterprise 项目文档页的差异

下面比较产品行为与源码，不把尚未完成的生产验收写成已通过。

| 项目 | 一致 / 保留 | 改变或缺口 |
| --- | --- | --- |
| 页面组织 | 项目页的规范文档、里程碑、其他格式、树与搜索仍复用 Aims 页面 | 页头、地址与登录改由 Host 统一承载，不再以独立 Aims 为主入口 |
| 存储来源 | Aims 索引、Codocs/OSS 正文与附件、GitLab 引用仍分别保存 | 没有一次性把所有文件搬成 Enterprise 自有正文库 |
| 项目文件夹 | Aims 父子目录和文档业务归属保留 | 不新增自动 Codocs 项目空间，也未保证两套目录双向同步 |
| 服务调用 | owning 业务规则、Codocs 独立权限、仓库绑定保留 | Host 不再先通过 Aims HTTP 服务申请宽 `aims.read/write`，改为用户委托的固定 Runtime 操作；Codocs 接受受审的 Enterprise 来源 |
| 权限 | 项目范围与 Codocs 文档权限同时校验；经理不能覆盖 Codocs edit ACL | 当前写入明确使用 edit 权限，不能沿用旧“只读权限即可调用某些写用途”的漏洞；不承诺旧静态/关系混合的边界完全不变 |
| 文档正文打开 | 确认精确 UUID、实际项目和成员关系后读 Codocs | P1 后曾有残留宽 scope 导致 403，`1ca2d5c4` 已收口；上线情况需按发布回执确认 |
| 仓库预览 | 精确项目仓库关系与 GitLab 读取不变 | P1 单段正则曾错误拒绝 `huizhi-yun/huizhiyun`；`1ca2d5c4` 恢复多段路径、decode 后校验、≤255，拒绝 `..`/空段；commitId 规则不改 |
| 新建 / 附件 / 策略 | P1 typed 核心和固定写操作已接线；不授宽 scope | 是否在生产已完成每一种 OSS / Codocs grant 与真实写入验收，应按 P1 Runbook 逐项核对；不能凭接口存在判断全部可用 |
| 工作项文档关联 | 引用不授予其他人正文权限 | 企业 lane 新增源索引存在性与当前 Codocs view 复核；无 UUID 索引不再登记悬空关联；集合 DELETE 仍失败关闭 |
| 项目集文档 | 历史数据保留 | 暂不接受纯项目集写入、不把其加入项目文档页；原项目集编辑闭环未迁移为新的可用合同 |
| 删除 / 回收 | 保留索引删除与 backing 的分工 | 不能宣传为统一文档回收站；目录删除的外部正文清理与失败补偿需要另定 |

## 8. 需要用户决定的问题

以下均是待决定，不由本文授权实现、改数据或加权限。

1. **项目集文档如何保留？** 两份历史文档保留只读入口、转挂一个真实项目，还是继续做项目集专属空间？转挂前须确认业务归属与两套权限，不能只改 project_code。
2. **项目文件夹是哪一套目录的主目录？** 继续由 Aims 管业务分类、Codocs 只管正文；还是显式同步 Codocs 目录？如果同步，重名、改名、移动、删除和失败恢复怎样处理？
3. **附件继续放 Codocs 项目文件柜吗？** 是否统一最大上传大小（目前原页面 10 MB / 旧服务 100 MB 不一致）、在线预览格式和“其他文档”分类；是否为附件与 GitLab 引用拆开明确来源标识？
4. **离组后撤销到哪一层？** 仅取消项目关系，允许独立 Codocs 分享继续有效；还是连同项目授予的文档权限撤销？创建人、上传人删除权和历史白名单如何处理？
5. **列表是否必须保证每条都能打开？** 原代码可能因项目可见编码、成员关系和 Codocs ACL 的差异出现“列出但打不开”；是否统一在列表时完整复核并展示固定拒绝原因？
6. **经理能否删除别人的文档，以及“删除”删除什么？** 仅移除项目引用、连同 Codocs 文件回收，还是硬删除附件？目录级联删除应否提供预览清单 / 回收与外部内容补偿？
7. **仓库文档是跟随分支，还是固定版本？** 引用保存 commit 时按该版本预览；没有 commit 时跟随 ref。产品是否要求所有交付物固定版本，避免验收后内容随仓库变动？
8. **关联入口放在哪里？** 继续只通过任务/成果的选择器，还是在项目文档页增加“关联已有 Codocs / 仓库文件”？新增关联不应自动扩大文档权限。
9. **是否保留原访问控制弹窗的全部选项？** 草稿/正式/归档、L0–L3、内部/跨项目、角色/部门/用户白名单的组合较复杂；若简化，应先决定历史策略如何解释，不静默重置。
10. **何时确认旧部署基线？** 若需要逐项证明“生产原来就是这样”，还需由部署记录提供切换前 Aims/Codocs Worker 的提交或制品摘要，再复核本文历史快照与该制品的差异。当前文档可用于产品决策，但不能替代该证据。

### R2c 实施合同（候选，未部署）

附件统一 100×1024×1024 字节（与原独立端及 Codocs 文件柜上限一致，界面显示 100 MB）；页面、Host multipart、owning 上传核心共用 Aims shared 常量，Runtime 索引也拒绝超过上限的 contentSize。Markdown 文件在读取为文本前检查同上限，服务端按 UTF-8 字节检查。

移除项目成员只改变项目关系，不调用 Codocs 独立分享/授权撤销。删除文档只删除 Aims 项目索引，Host 与独立端都不删除 Codocs 文档/文件柜或 OSS 附件。Runtime 在 Serializable 事务内锁定目录树，先验证全树并拒绝含文档的目录（409 project_document_folder_not_empty），再移除空目录；任何失败不部分删除。

Host 仓库引用创建时经权威项目仓库绑定检查后读取确定提交并保存 repoCommitId；Runtime 拒绝没有固定提交的 Git 文档引用（附件文件柜索引不是 Git 文档）。预览内容来自保存的提交，另外读取同仓库同文件的当前版本标识；文件 blob 不同时显示“有更新版本”，不自动更新引用或正文。仓库其它文件变动而此文件内容不变不提示。已有无提交的历史引用不悄悄跟随分支：预览明确要求重新选择固定版本，本批不写历史数据。
