# 汇智 PIVR 项目管理实操指南 增补篇：周期型服务与常设事务 (V1.0)

## 0. 文档定位

### 0.1 与《汇智PIVR项目管理实操指南V1.0》的关系

本文是实操指南 V1.0 的**增补篇**，不替换、不修改任何既有条款。指南 V1.0 描述的是一次性项目的管理动作；本文补充两类它未覆盖的工作形态：

* **周期型服务**：维保服务、托管运维、年度技术支持等在合同期内循环运转、没有终验的长周期工作
* **常设事务**：部门日常、内部支持、临时协助等永远不会立项的非项目工作

### 0.2 要解决的问题

指南 V1.0 §3.1 已把维保服务和持续改进列入适用范围，但第 5 至第 10 章的全部控制点都建立在同一假设上：项目会推进、会验收、会关闭。周期型服务不满足这个假设，直接套用会产生四种典型失效：

| 失效 | 表现 |
| --- | --- |
| 阶段门失效 | 工单处理与质量抽检天天并行，阶段门要么被绕过，要么项目永久停在 I 阶段 |
| 状态失效 | 项目状态三年不变，违背 §2.4「状态即承诺」的本意，管理层无法从状态判断健康度 |
| 复盘失效 | §10.4 的复盘约束三年才触发一次，期间没有任何强制复盘节点 |
| 报表失效 | §12.5 的里程碑按期率、验收通过率在维保项目上恒为空 |

常设事务的问题更直接：指南 §6.2 要求管理层判断「是否属于日常事务而非正式项目」，但判断为「是」之后没有任何出口，事项与其消耗的工时一起离开系统。

### 0.3 核心主张

指南 V1.0 只使用了「项目类型」一个分类维度。本文补充**执行形态**这一维：

* **项目类型**回答「做什么」——产品开发、定制开发、实施交付、维保服务……
* **执行形态**回答「怎么运转」——一次性推进、周期循环、常设承接

两者正交。PIVR 的四段语义完全保留，改变的只是它的运行方式。

### 0.4 合并落点

本文各章在指南 V1.0 中的对应位置：

| 本文章节 | 建议落点 | 性质 |
| --- | --- | --- |
| 第 1 章 执行形态 | 指南 §3 新增 3.4 | 新增节 |
| 第 2 章 PIVR 的两种运行方式 | 指南 §5 新增 5.4 | 新增节 |
| 第 3 章 周期型服务操作指南 | 指南第 10 章之后新增，与 §7–§10 同级 | 新增章 |
| 第 4 章 常设事务与非项目工作 | 同上，紧随其后 | 新增章 |
| 第 5 章 既有章节补丁 | §9.5 / §11 / §12.5 / §13.2 / §14.2 | 条款补充 |
| 第 6 章 系统实现要求补充 | 指南 §12 | 条款补充 |

## 1. 执行形态（拟作为指南 §3.4）

### 1.1 三种执行形态

| | A 项目制 | B 服务制 | C 常设事务 |
| --- | --- | --- | --- |
| 结构 | 一次性，有明确终点 | 合同期内周期循环，无内部终点 | 常设，无起点也无终点 |
| 典型工作 | 产品开发、定制开发、实施交付、合规审计 | 维保服务、托管运维、年度技术支持 | 部门职能、内部支持、临时协助 |
| PIVR 用法 | 线性走一遍 P→I→V→R | 每个周期完整跑一次 P→I→V→R | 不使用 PIVR，只用工作项与工时 |
| 治理节点 | 立项、重大变更、里程碑验收、结项 | 服务启动评审、关期确认、季度服务评审、续约或终止 | 负责人指定、季度回顾 |
| 控制装置 | 阶段门（能否推进） | 关期门（能否关账） | 无门 |
| 核心指标 | 计划偏差、里程碑按期率、验收通过率 | SLA 达成率、积压进出比、重复问题率、权益消耗率 | 承接量、工时占比、可计费工时比例 |
| 结束方式 | 验收 + 复盘 + 关闭 | 合同到期或不续约 → 服务终止与移交 | 随组织调整变化，或升级为 A 轨项目 |

### 1.2 形态与项目类型的关系

形态与类型正交，默认映射如下，允许项目在启动时显式调整：

按 `aims_projects.category` 现有枚举逐项对齐：

| 项目类型 | 默认形态 | 说明 |
| --- | --- | --- |
| `product_dev` 产品开发 | A 项目制 | 版本节奏明确的可用 A + 滚动型里程碑 |
| `custom_dev` 定制开发 | A 项目制 | 终验后转入 B 轨维保，属于两个独立执行体 |
| `delivery` 实施交付 | A 项目制 | — |
| `maintenance` 维保服务 | B 服务制 | 按服务年度建项目，见 §3.3 |
| `compliance` 合规审计 | A 项目制 | 年度重复的审计按 B 轨管理 |
| `sales` / `presales` | 不作为 Aims 执行体 | 保留为统一语言，细粒度流程在 Altoc（指南 §3.2） |
| `improvement` 改进 | **建议下线** | 见 §1.3 |
| `routine` 日常事务 | C 常设事务 | 新增字典项。复用项目对象但关闭 PIVR 相关模块，见 §4.2 |

**一个合同可以同时产生 A 轨和 B 轨两个执行体**。典型场景：定制开发合同包含实施交付（A 轨，有终验）与后续三年维保（B 轨，循环运转）。两者共享客户与合同关联，但生命周期、控制点和指标各自独立，不得合并为一个跑三年的项目。

### 1.3 `improvement` 类型建议下线

`improvement`（现有代码中标签不一，出现「持续改进」「改进优化」「内部改善」「改进」四种叫法）没有独立的阶段语义、模板集和报表口径，改进类工作在三条既有路径上都有归宿：

| 改进类工作 | 归位 |
| --- | --- |
| 产品功能改进 | `product_dev` 的版本迭代（商用 MMP 阶段） |
| 已交付客户系统的持续优化 | `maintenance` 服务范围内；超出范围按 §3.10 转报价，形成新的 `custom_dev` 项目 |
| 内部流程与效率改进 | C 轨常设容器；达到 §4.5 阈值时升级为正式项目 |

**判断依据**：一个项目类型如果没有独立的模板集、阶段语义和报表口径，它就不应该存在——它只会在建项目时增加一个让人犹豫的选项，而选错类型会导致模板加载错误和模块开关错误。同一类型在代码中出现四种中文标签，本身就说明它缺少真实业务落点。

**下线步骤**（分两步，避免影响存量数据）：

1. **入口下线**：从项目创建与筛选入口移除该选项，保留 `category` 枚举值与展示映射。存量项目不受影响，无需数据迁移
2. **枚举清理**：确认生产库无 `category='improvement'` 的存量项目后，从 schema 枚举、data-runtime 模板分支和前端类型定义中移除

核查语句：

```sql
SELECT project_code, name, status, created_at
FROM aims_projects WHERE category = 'improvement';
```

存量项目按上表逐条归位后再执行第 2 步。

### 1.4 项目集承载执行形态

执行形态通过**项目集的默认分类**落地，不需要用户在每次建项目时手工选择分类。

`project_portfolios.is_product_line` 已有「产品线项目集下新建子项目自动归类为产品研发」的机制（前端在选择项目集时自动写入 `category='product_dev'`）。该机制泛化为字段即可支撑三种形态：

| 项目集 | `default_category` | 数量 | 约束强度 |
| --- | --- | --- | --- |
| 产品线（现有） | `product_dev` | 多个 | 默认值，创建时可覆盖 |
| 周期性服务 | `maintenance` | 起步一个 | 默认值，创建时可覆盖 |
| 日常事务 | `routine` | **全局唯一，系统预置** | **强约束，不可覆盖** |

**约束强度差异的理由**：产品线与周期性服务项目集下可能存在例外项目（如维保项目集中的一次性改造项目），应允许覆盖；日常事务容器一旦被改为其他分类，§4.4 的工时闭合即出现缺口，因此必须强约束。

**统一总览**：项目总览页已按项目集分组展示。三类项目集并列后，一次性项目、周期性服务和日常事务在同一视图内可见，无需为日常事务另建入口，也不应将其从列表中过滤——这些工作消耗真实工时，在总览中隐形会使工时口径失去意义。日常事务项目集可默认折叠并排在末位。

`is_product_line` 在 `default_category` 回填后转为派生值，前端有多处依赖，保留一段时间后再清理（见 §6.5）。

### 1.5 形态判定规则

* 形态在服务启动或立项时确定，由项目发起人确认，PMO 复核
* 判定标准只有一条：**这件事有没有一个由交付内容本身决定的终点**。有终点走 A；终点由合同期决定、内容循环重复的走 B；没有终点也没有合同的走 C
* 形态一经确定不允许随意切换。确需切换（如维保合同转为改造项目）必须新建执行体并做关联，不得原地改形态——原地切换会使历史周期数据与阶段数据混在同一对象上，报表口径失真
* C 轨事项升级为 A 轨项目的通道见 §4.5，属于新建而非切换

## 2. PIVR 的两种运行方式（拟作为指南 §5.4）

### 2.1 线性推进（A 项目制）

即指南 §5.1 定义的既有方式：

```
立项 -> P -> I -> V -> R -> 关闭
```

每个阶段进入一次、退出一次，阶段门控制的是「能否推进」。

### 2.2 周期循环（B 服务制）

```
服务启动 -> [ P -> I -> V -> R ] -> [ P -> I -> V -> R ] -> ... -> 服务终止与移交
              第 N 周期                第 N+1 周期
```

外层生命周期只有两个一次性节点：**服务启动**与**服务终止**。中间是无限重复的周期单元，每个周期单元内部完整跑一遍 PIVR，控制装置是**关期门**，控制的是「上一周期能否关账」。

### 2.3 周期内的 PIVR 语义

沿用《汇智PIVR项目管理生命周期模型说明书V1.0》对 maintenance 类型的定义，不引入新术语：

| 阶段 | 周期内含义 | 典型动作 |
| --- | --- | --- |
| P 周期规划 | 开期 | 值班排班、巡检计划、上期结转项接收、本期重点、资源与预算 |
| I 任务处理 | 执行 | 工单处理、例行巡检、变更窗口、问题升级 |
| V 质量抽检 | 核对而非验收 | SLA 结果核对、质量抽检、客户周期确认 |
| R 复盘优化 | 关期 | 重复问题归因、SOP 与知识库更新、下期资源调整、超范围事项识别 |

### 2.4 与阶段门的关键差别

指南 §2.3 规定阶段门刚性控制、不得绕过。该原则在周期循环中保留，但落点变化，必须显式声明以下两条，否则 §2.3 在服务制下无法执行：

* **V 与 I 常态并行，不设互斥门**。周期内的质量抽检和工单处理同时发生，不存在「I 阶段全部完成才能进入 V」的排他关系
* **刚性控制的对象是关期，不是阶段推进**。周期内的 PIVR 是节奏标签，用于组织动作与责任；真正的强制校验发生在关期时点（见 §3.8）

## 3. 周期型服务操作指南（拟作为指南新增章，与 §7–§10 同级）

### 3.1 适用范围

执行形态为 B 服务制的全部执行体，包括维保服务、托管运维、年度技术支持，以及按固定周期重复的合规审计。

### 3.2 服务启动

服务启动**取代反复立项**，在服务期内只发生一次。

#### 3.2.1 管理层必须确认的事项

指南 §6.2 的立项确认项在此不适用（合同已签，不存在「要不要做」）。管理层需要确认的是：

* 服务范围边界：哪些工作在范围内、哪些属于超范围
* SLA 承诺：响应时限、解决时限、可用性要求及对应违约后果
* 资源包：投入人力、值班安排、成本预算
* 计费方式：包干、按量、按工时或服务权益扣减
* 周期节奏：月度、季度或其他
* 服务负责人

#### 3.2.2 必备信息

* 服务名称与关联合同
* 客户与服务对象范围（系统、环境、资产清单）
* 服务期起止
* 周期规则
* SLA 条款快照
* 服务负责人与值班团队
* 资源预算与计费方式
* 初始风险与已知遗留问题（尤其是从 A 轨交付项目转入时的遗留清单）

#### 3.2.3 系统控制点

* 未确定周期规则时，不允许启动服务
* 未登记 SLA 条款或明确标记「无 SLA 承诺」时，不允许启动服务
* 未指定服务负责人时，不允许启动服务
* 未确定服务范围边界时，不允许启动服务——范围边界缺失会使 §3.10 的超范围判定无法执行
* 服务启动后，系统自动创建第一个周期单元并进入 P

### 3.3 周期结构：服务年度 + 关期节拍

采用两层周期，**不要合并为一层**。两层都复用 Aims 既有机制，不新增对象类型：

| 层 | 载体 | 长度 | 管什么 | 复用的现有机制 |
| --- | --- | --- | --- | --- |
| 外层：服务年度 | **项目** | 1 年，跟随合同年度 | 计费、续约、年度评审、成本归集、结项 | `aims_projects` |
| 内层：关期节拍 | 周期里程碑 | 默认月度，可配季度 | 关账、结转、指标、复盘 | `milestones.mode=periodic` + `recurrence_rule` + `milestone_cycle_snapshots` |

**为什么不能只保留年度层**：一年才关一次账，积压趋势、SLA 差异、成本超支要到年底才暴露，等同于 §0.2 描述的复盘失效与报表失效原样保留，只是周期从三年缩短为一年。

**为什么不能只保留月度层**：没有年度层则无法对齐合同年度做计费、续约与成本核算，且项目永远不会结项，§0.2 的状态失效仍然存在。

#### 3.3.1 服务年度项目

* 全部服务年度项目归入**「周期性服务」项目集**（`default_category='maintenance'`，见 §1.4），在项目总览页作为独立分组呈现
* 起步使用一个项目集即可。维保客户较多时（建议超过 15 个）按行业或客户群拆分，**不必按客户拆分**——同一客户历年项目由 `service_line_code` 串联。项目集回答「属于哪个业务板块」，服务链回答「同一条服务的哪一年度」，两者层级不同
* **一年一个项目**，服务年度结束时真实结项。这使项目状态重新具备信息量，直接解决状态失效
* 名称展示形如「某客户 某系统 维保 2026」，但**周期标识必须是结构化字段，名称中的年份仅用于展示**。依赖名称字符串会使续约链路、跨年对比和历史查询全部退化为文本解析
* 建议字段：

| 字段 | 作用 |
| --- | --- |
| `service_line_code` | 服务链标识，把同一客户同一服务的历年项目串成一条链 |
| `service_period_seq` | 服务年度序号，如第 1 年、第 2 年 |
| `service_period_start` / `service_period_end` | 服务年度起止 |
| `service_period_label` | 展示标签，如 `2026.03–2027.02` |

* **`service_line_code` 是续约谈判的基础**。客户会问「合作三年，累计工单多少、重复问题有没有下降、响应是不是更快了」。缺少服务链，每个年度项目彼此孤立，跨年趋势无法计算
* **合同期不是自然年时**（如 3 月至次年 2 月），标签必须使用起始月区间，禁止简写为单一年份，否则「2026」在计费与考核中产生歧义

#### 3.3.2 关期节拍

默认月度，服务规模小或工单量低的可配置为季度。三种节拍的动作轻重不同：

| 节拍 | 动作 | 目标耗时 |
| --- | --- | --- |
| 月度关期 | 系统自动汇总工单数、工时、积压与结转；服务负责人只处理异常项 | 10 分钟内 |
| 季度关期 | 增加客户确认与周期复盘 | 半天 |
| 年度关期 | 完整服务年度评审，产出续约输入与下一年度资源建议 | 1–2 天 |

关期门五项校验（§3.8）按节拍分级执行：

| 校验项 | 月度 | 季度 | 年度 |
| --- | --- | --- | --- |
| 1 工单终态或明确结转 | 强制 | 强制 | 强制 |
| 2 超时与高优先级工单说明 | 强制 | 强制 | 强制 |
| 3 工时确认与成本归集 | 强制 | 强制 | 强制 |
| 4 SLA 结果核对 | 强制 | 强制 | 强制 |
| 5 复盘与客户确认 | 可登记豁免 | 强制 | 强制，并产出续约输入 |

**月度关期必须做成轻量动作**。如果每月关期需要服务负责人手工填写大量内容，它会在三个月内退化为走过场，关期门随之失效。系统应把可自动计算的部分全部算好，只把需要人判断的异常项推给负责人。

#### 3.3.3 跨年结转

服务年度结束时的未闭事项需跨项目移入下一年度项目，比月度结转重：

* 必须保留原始工单标识、原服务年度、累计结转次数，不得作为新建工单处理
* 跨年结转项在新年度项目的 P 阶段必须逐条确认责任人
* SLA 计时口径不因跨年重置，仍以经营侧原始时点为准
* **不续约时不做结转**：未闭事项进入 §3.12 的遗留问题交接流程

#### 3.3.4 周期单元内容

周期单元是关期节拍的承载对象，不是里程碑的附属属性。管理层按周期看趋势，而不是看一个永远处于 active 的项目。

每个周期单元至少包含：

* 周期起止日期与周期序号
* 计划量：本期计划工作项、巡检计划、值班安排
* 承接量：本期新增工单与工作项
* 完成量与结转量
* 本期工时与成本
* SLA 结果快照与差异说明
* 周期复盘记录
* 关期确认人与确认时间

### 3.4 P 阶段：开期

#### 服务负责人的动作

* 接收上期结转项，逐条确认责任人与本期处理计划
* 编排值班与巡检计划
* 明确本期重点（如专项优化、版本升级配合、重大变更窗口）
* 核定本期资源与预算

#### 系统控制点

* 上期结转项未全部指定责任人时，不允许关闭本期 P
* 有 SLA 承诺的服务未安排值班时，系统必须提示确认
* 巡检计划为空时，系统应提示确认「本期无巡检」，而不是默认通过

### 3.5 I 阶段：执行

#### 日常动作

* 工单接收、分派、处理与关闭
* 例行巡检执行与记录
* 变更窗口内的操作与回退预案
* 问题升级与客户沟通

#### 系统控制点

沿用指南 §8.4 中与工作项相关的控制点，另补充：

* 工单进入处理前必须完成**范围内 / 范围外 / 待判定**判定（见 §3.10）
* 工单必须归属某一个周期单元；跨期未闭工单在关期时转为结转项，不允许无归属悬空
* 超出 SLA 响应或解决时限的工单，系统自动通知服务负责人和相关管理角色
* 待判定状态的工单超过约定时限未判定的，自动升级提醒

### 3.6 V 阶段：周期核对

周期核对**不是验收**。它回答的是「本期服务达没达到承诺」，而不是「交付物合不合格」。

#### 典型动作

* SLA 结果核对：以经营侧（Altoc）SLA 判定结果为准，交付侧核对差异并记录解释
* 质量抽检：按比例抽取本期已闭工单复核处理质量与记录完整性
* 客户周期确认：取得客户对本期服务的确认（月度可轻量，季度必须有正式记录）

#### 系统控制点

* SLA 结果与交付侧记录存在差异时，必须登记差异原因，不允许静默通过
* 抽检结论必须带抽检人、抽检范围和结论
* 客户确认必须带确认人、时间与结论类型（见 §5 对 §9.5 的补丁）

### 3.7 R 阶段：关期与复盘

#### 典型动作

* 重复问题归因：识别本期反复出现的同类问题并定性（治标 / 治本 / 待立项改造）
* SOP 与知识库更新
* 下期资源调整建议
* 超范围事项汇总与经营出口确认

#### 系统控制点

* 连续两个周期无复盘记录的服务，标记为治理异常并上报管理层
* 复盘识别出的改进项必须有责任人和计划关闭时间（沿用指南 §10.4）
* 归因为「待立项改造」的问题应生成前置池事项，进入 A 轨立项判断

### 3.8 关期门

关期门是服务制的核心控制装置，取代阶段门。关期时系统必须校验以下五项：

| # | 校验项 | 不满足时的处理 |
| --- | --- | --- |
| 1 | 本期工单全部有终态或明确结转 | 阻断关期，列出悬空工单 |
| 2 | 超时与高优先级工单已逐条说明并有补救动作 | 阻断关期，不允许批量勾选通过 |
| 3 | 本期工时已确认，成本已归集 | 阻断关期 |
| 4 | SLA 结果已核对，差异已记录 | 阻断关期 |
| 5 | 周期复盘已完成，客户确认已取得或明确豁免 | 月度可登记豁免，季度阻断关期 |

**关不上的周期，必须自动生成结转项进入下期，并登记例外原因、责任人、补救动作和计划关闭时间**——这是指南 §2.3「例外必须登记」在周期场景下的落点。

**绝不允许静默滚动。** 周期到期自动开启下一期是系统行为，但上一期是否合规关闭必须留下明确结论。

### 3.9 结转规则

* 结转项必须保留原始工单或工作项标识、原周期归属、结转次数
* 同一事项连续结转三期以上时，自动升级为治理异常并通知管理层
* 结转不改变 SLA 计时口径；SLA 判定仍以经营侧原始时点为准
* 跨期风险与问题必须显式结转，不得随关期消失（见 §5 对 §11 的补丁）

### 3.10 服务范围外事项

这是维保服务最容易漏掉收入的环节，也是与指南 §8.5 变更控制最容易混淆的地方。

**判定规则**

* 工单登记时必须判定范围内 / 范围外 / 待判定，判定人为服务负责人
* 判定依据是服务启动时确认的范围边界与合同条款，不由个人经验决定

**处理规则**

判定为范围外的事项自动生成「服务范围外事项」记录，只有两个合法出口：

1. **转报价**：进入经营侧（Altoc）形成商机或合同变更
2. **扣减服务权益**：客户已购权益范围内，按约定扣减并留痕

**禁止事项**

* 不允许以指南 §8.5「重大变更」名义在交付侧内部消化超范围工作
* 不允许在无判定结论的情况下直接开工

**管理意义**：这一条落地后，维保服务才从成本中心变成可经营对象。范围外工作量应作为服务健康度和续约谈判的输入。

### 3.11 服务健康度与预警阈值

指南 §12.5 的项目制指标在服务制下不适用。服务制健康度按以下五项判定：

| 指标 | 定义 | 预警阈值 |
| --- | --- | --- |
| 积压进出比 | 本期新增工单 ÷ 本期关闭工单 | 连续两期 > 1 → 黄灯 |
| 重复问题率 | 本期重复类问题 ÷ 本期问题总数 | > 20% → 黄灯 |
| 权益或资源消耗率 | 已消耗资源 ÷ 合同总资源 | 超出时间进度 15 个百分点 → 红灯 |
| SLA 达成率 | 以经营侧判定结果为准 | 低于合同承诺 → 红灯 |
| 复盘完成情况 | 周期复盘记录是否存在 | 连续两期缺失 → 治理红灯 |

黄灯由服务负责人在下期 P 阶段给出应对措施；红灯必须上报管理层并在季度服务评审中形成结论。

### 3.12 服务终止与移交

指南第 10 章只提供了「关闭」和「进入下一周期」两个出口，缺少服务制的真正终局。合同到期、客户不续约或提前终止时，必须触发终止流程：

* 知识移交清单：运维手册、SOP、常见问题、变更历史、遗留问题清单
* 账号与权限回收：服务期内开通的全部客户侧账号、跳板机、VPN、代码与数据访问权限
* 资产归还：客户提供的设备、介质、证书、密钥
* 遗留问题交接：未闭事项逐条交接并取得接收方确认
* 客户终止确认：正式确认服务结束与交接完成

#### 系统控制点

* 未完成账号与权限回收，不允许标记服务终止
* 未取得客户终止确认，不允许归档
* 遗留问题未逐条明确去向的，不允许关闭

**这既是审计要求，也是信息安全控制点**：服务期内开通的访问权限如果没有强制回收环节，会长期悬空。

### 3.13 角色职责差异

在指南 §4 角色表基础上，服务制的差异如下：

| 角色 | 服务制下的差异 |
| --- | --- |
| 管理层 | 不做反复立项审批；负责服务启动评审、季度服务评审、红灯处置和续约或终止决策 |
| 服务负责人（对应项目经理） | 对 SLA 达成、周期关期质量、资源消耗和客户满意负责；承担范围内外判定的最终责任 |
| 商务/财务 | 负责范围外事项的报价出口、权益扣减核对和服务期计费 |
| PMO | 负责关期门执行情况抽查、治理异常跟踪、跨服务口径统一 |

### 3.14 退出条件

**周期退出条件**（关期）

* 关期门五项校验通过，或未通过项已登记例外并生成结转
* 本期成本已归集
* 复盘完成，改进项已分配责任人

**服务退出条件**（终止）

* 服务期结束或终止决策已确认
* 知识移交、权限回收、资产归还完成
* 遗留问题全部明确去向
* 客户终止确认已取得

## 4. 常设事务与非项目工作（拟作为指南新增章）

### 4.1 定位

常设事务是**不进入项目生命周期、也不应进入前置池**的日常工作。它不需要治理机制，它需要的是被承认和被计量。

指南 §3.3 规定未立项事项以前置池管理。前置池的语义是「等待立项判断」，而日常事务永远不会立项，长期堆在前置池会使其失去筛选功能。因此需要独立承载。

### 4.2 常设容器

#### 4.2.1 容器形态：按部门建，一个部门一个

常设容器**复用项目对象**，项目分类为 `routine`（日常事务）。这样工时归集只有 `time_entries.project_id` 一条路径，项目页面、成员、权限和工作项看板全部复用，不需要新建一套并行的工时科目体系。

全部容器归入**「日常事务」项目集**（`default_category='routine'`，全局唯一且系统预置，见 §1.4），容器按**部门 × 年**建立：

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 按部门建还是全公司一个 | **按部门建** | §4.3 要求每个容器有明确负责人，全公司单一容器无合理负责人；Aims 数据范围按项目成员控制，单一容器会导致人力、行政等事务全员可见 |
| 是否按年切分 | **按年切分** | 常设工作无终点，不切分则容器无限增长；按年切分与服务年度、财务年度口径一致 |
| 部门归属字段 | 复用 `aims_projects.dept_code` | 现有字段，无需新增 |
| 项目命名 | 「研发部 2026」 | 语境由项目集提供，名称中不再重复「日常事务」 |

容器有负责人、有工时科目、有工作项，**没有阶段门、没有验收、没有立项、不使用 PIVR**。创建时通过 `module_config` 关闭里程碑、需求、版本等模块，只保留工作项与工时。

容器项目通过项目集分组与常规项目区分，**不做列表过滤**。日常事务项目集在总览页默认折叠并排在末位；历史年度容器随项目集内的年度分组收起。

#### 4.2.2 部门事务与跨部门协助：工作项标记，不是两个容器

部门事务与跨部门协助**不设为两个容器**。二者的负责人是同一个人（均为提供方部门负责人），负责人相同即不构成独立容器。区分下沉到工作项：

| 标记 | 取值 | 说明 |
| --- | --- | --- |
| `routine_scope` | `department` | 本部门既定职能范围内的工作，含例行事务与本部门突发事项 |
| | `cross_dept` | 超出本部门既定职能、为其他部门投入的工作 |
| `beneficiary_dept_code` | 部门编码 | `cross_dept` 时必填，用于成本流向统计 |

**判定标准**唯一：**这项工作是否属于本部门的既定职能**。

* 属于 → `department`。IT 部门处理报修、行政处理办公事务、人力处理招聘事务，都是各自部门的既定职能，不是「协助」
* 不属于 → `cross_dept`。研发临时借调支援交付、市场协助制作客户演示材料

**不要按「是否临时」划分。** 「临时」是时间属性，「本部门 / 跨部门」是归属属性，两者混用会使同一件事同时符合两类定义——突发的跨部门协助既属于「临时」也属于「跨部门」，归类将完全取决于填报人习惯。

#### 4.2.3 计划外工作标记

「临时」这一属性本身有管理价值，作为独立的工作项标记保留：

* 工作项增加 `is_unplanned` 标记，两种 `routine_scope` 均可使用
* 派生指标：**计划外工作占比** = 计划外工时 ÷ 容器总工时
* 该比例持续偏高说明部门处于救火状态，是季度回顾的重点议题，也是编制与资源调整的直接依据

这样既避免了维度混用，又保留了「临时事务」分类真正想表达的信息。

### 4.3 治理规则

只保留两条，多一条都是负担：

1. 每个容器必须有明确负责人，默认为部门负责人
2. 每季度必须有一次回顾，确认容器是否仍然需要、承接量是否异常、计划外工作占比是否异常、是否有事项应升级为项目

季度回顾中需确认跨部门工时流向：某部门长期向另一部门输出大量工时，通常意味着编制配置不合理，或该协助已具备升级为正式项目的条件。

### 4.4 工时口径闭合

**每个人的每一小时，只能落在项目、服务期约、常设容器三者之一。**

这是让以下两个经营指标真正成立的前提：

* 项目成本核算：非项目工时不闭合时，项目成本会被系统性高估或低估
* 可计费工时比例：这是软件企业最核心的经营指标之一，缺少非项目工时基数则无法计算

#### 系统控制点

* 工时提交时必须归属三类载体之一，不允许无归属工时
* 个人周工时合计与考勤存在显著差异时，系统提示补记
* 常设容器工时占比超过阈值（建议 40%）的部门，在季度回顾中必须给出说明
* `routine_scope=cross_dept` 的工作项必须填写受益部门，否则工时无法参与成本流向统计
* 计划外工作占比超过阈值（建议 30%）的部门，在季度回顾中必须给出说明

### 4.5 升级为项目

常设容器中的事项满足以下任一条件时，系统提示「是否升级为项目」：

* 累计投入超过 10 人日
* 涉及两个及以上部门
* 产生对外交付物或客户可见成果
* 存在明确的完成标准与截止要求

升级动作**一键带着已发生的工时、工作项和记录进入立项流程**，原容器中的事项标记为已升级并保留追溯。

这给了指南 §6.2 那条判断一个真正的出口：判定为日常事务不再意味着事项离开系统，判错了也能回来。

### 4.6 明确不适用的事项

以下情况不得使用常设容器，防止其变成规避项目治理的通道：

* 有明确交付物和客户承诺的工作
* 有合同或收入关联的工作
* 需要跨部门资源承诺的工作
* 已被判定为项目但因流程麻烦而改记为日常事务的工作

PMO 应在季度回顾中对上述情况做抽查。

### 6.1 核心对象补充

在指南 §12.1 对象清单基础上补充：

* 服务年度项目（B 轨执行体，复用项目对象 + 服务链字段）

* 关期记录与结转项

* 常设容器（`category=routine`，按部门 × 年建立，复用项目对象）
* 服务终止移交清单

### 6.2 状态机要求补充

* 周期单元状态与服务期约状态分离。服务期约在整个合同期内保持 active，健康度由指标承载而非状态承载
* 关期是一个受控状态迁移，必须经过关期门规则引擎校验
* 周期自动滚动与周期合规关闭是两件事，必须分别留痕
* 常设容器不设状态机，只有启用与停用；年度容器在服务年度结束时归档，未完事项转入下一年度容器

### 6.3 权限要求补充

沿用指南 §12.3，另补充：

* 关期确认权限必须与服务负责人角色绑定，不得由普通成员执行
* 范围内外判定权限必须与服务负责人绑定
* 服务终止与权限回收确认必须双人复核

### 6.4 与 Aims 当前实现的差距

按当前仓库模块文档与 schema 判断（标记为缺失的项未逐一核对代码实现）：

| 能力 | 现状 | 判断 | 缺口 |

### 6.5 新增字段清单

汇总本文涉及的 schema 变更，供实现时参照。以下为建议定义，实际以 tenant-runtime adapter 与迁移脚本为准。

**项目分类扩展**（§4.2）

```sql
ALTER TABLE `aims_projects`
  MODIFY `category` ENUM('product_dev','custom_dev','delivery','maintenance',
                         'sales','presales','improvement','compliance','routine')
  NOT NULL DEFAULT 'product_dev' COMMENT '项目分类';
```

`improvement` 在入口下线阶段保留于枚举中，确认无存量数据后再移除（§1.3）。

**项目集默认分类**（§1.4）

```sql
ALTER TABLE `project_portfolios`
  ADD COLUMN `default_category` ENUM('product_dev','custom_dev','delivery','maintenance',
                                     'sales','presales','compliance','routine') DEFAULT NULL
      COMMENT '子项目默认分类，NULL=不预设',
  ADD COLUMN `is_system` TINYINT(1) NOT NULL DEFAULT 0
      COMMENT '系统预置项目集，不可删除',
  ADD KEY `idx_portfolio_default_category` (`default_category`);

UPDATE `project_portfolios` SET `default_category` = 'product_dev' WHERE `is_product_line` = 1;
```

`default_category='routine'` 的项目集全局唯一，由应用层校验并随初始化预置（`is_system=1`）；不依赖函数索引实现唯一性，以避免 MySQL 版本兼容问题。`is_product_line` 保留为派生值，前端 8 处引用改造完成后再清理。

**服务年度字段**（§3.3.1，用于 `category=maintenance`）

```sql
ALTER TABLE `aims_projects`
  ADD COLUMN `service_line_code` VARCHAR(64) DEFAULT NULL
      COMMENT '服务链标识，串联同一客户同一服务的历年项目',
  ADD COLUMN `service_period_seq` SMALLINT UNSIGNED DEFAULT NULL
      COMMENT '服务年度序号',
  ADD COLUMN `service_period_start` DATE DEFAULT NULL,
  ADD COLUMN `service_period_end` DATE DEFAULT NULL,
  ADD COLUMN `service_period_label` VARCHAR(32) DEFAULT NULL
      COMMENT '展示标签，如 2026.03-2027.02',
  ADD KEY `idx_service_line` (`service_line_code`, `service_period_seq`);
```

**日常事务标记**（§4.2.2、§4.2.3，用于 `category=routine`）

```sql
ALTER TABLE `work_items`
  ADD COLUMN `routine_scope` ENUM('department','cross_dept') DEFAULT NULL
      COMMENT '日常事务归属(仅 routine 类项目)',
  ADD COLUMN `beneficiary_dept_code` VARCHAR(50) DEFAULT NULL
      COMMENT '受益部门(routine_scope=cross_dept 时必填)',

      COMMENT '计划外工作标记',
```

部门归属复用既有 `aims_projects.dept_code`，不新增字段。关期门校验结果与结转登记字段扩展在 `milestone_cycle_snapshots` 上，具体列在实现时按 §3.8 五项校验确定。

## 7. 推行顺序

按「先让规则成立，再让数据成立，最后让钱成立」推进：

1. **概念先行，不动代码**：本文第 1、2 章并入指南，统一口径。这一步只花文档时间，却决定后续所有系统规则的落点
2. **服务年度项目 + 关期门**：维保按服务年度建项目并补 §3.3.1 服务链字段；复用已落地的 rollover 与关期快照表，补 §3.8 五项校验和结转登记字段。同期从创建入口下线 `improvement`
3. **上服务制看板**：§3.11 五项指标。让管理层第一次看得懂一个维保服务健不健康
4. **常设容器与工时闭合**：新增 `routine` 分类与项目集 `default_category`，预置「日常事务」「周期性服务」两个项目集，按部门 × 年建立容器，补 §6.5 三个工作项标记字段。工时口径闭合后，项目成本与可计费比例才是真数
5. **超范围转经营与服务终止移交**：接通经营侧出口，补齐服务终局

## 8. 一句话结论

PIVR 不需要为长周期服务和日常工作另起一套方法论，它需要的是承认这三类工作的节拍不同：项目制走一遍，服务制循环跑，常设事务不跑。把阶段门换成关期门，把验收换成周期确认，把超范围换成报价，把日常工时从黑洞里捞出来——PIVR 才是覆盖全公司的治理底座，而不只是研发项目的管理模型。
