# 冲突处理操作对比

## 📋 概述

本文档对比三种冲突处理方式，帮助用户和开发者理解不同操作的效果。

## 🔄 三种处理方式

### 1. 使用GitLab版本 (use-gitlab-version)

**接口**：`POST /api/v1/projects/{project_code}/use-gitlab-version`

**效果**：用GitLab版本**覆盖**OSS文件

**适用场景**：
- ✅ GitLab版本更优
- ✅ OSS修改有误需要回退
- ✅ 团队需要统一到GitLab版本

---

### 2. 忽略冲突 (ignore-conflict)

**接口**：`POST /api/v1/projects/{project_code}/ignore-conflict`

**效果**：**保留**OSS文件，标记已处理

**适用场景**：
- ✅ OSS版本更优
- ✅ GitLab更新不重要
- ✅ 需要保留OSS的编辑

---

### 3. 手动合并 (手动编辑 + submit)

**接口**：`POST /api/v1/projects/{project_code}/gitlab-submit-docs`

**效果**：手动合并后提交到GitLab

**适用场景**：
- ✅ 双方都有重要修改
- ✅ 需要综合两边优点
- ✅ 复杂的合并需求

---

## 📊 详细对比表

### OSS文件内容

| 操作           | OSS文件内容 | 说明             |
| -------------- | ----------- | ---------------- |
| 使用GitLab版本 | **改变** ✏️  | 被GitLab版本覆盖 |
| 忽略冲突       | **不变** ✅  | 保留用户编辑     |
| 手动合并       | **改变** ✏️  | 用户手动修改     |

### GitLab仓库

| 操作           | GitLab仓库 | 说明             |
| -------------- | ---------- | ---------------- |
| 使用GitLab版本 | **不变**   | 已是最新版本     |
| 忽略冲突       | **不变**   | 不提交           |
| 手动合并       | **改变** ✏️ | 提交合并后的版本 |

### 元数据变化

| 字段                      | 使用GitLab版本   | 忽略冲突         | 手动合并         |
| ------------------------- | ---------------- | ---------------- | ---------------- |
| `gitlab-commit-id`        | latest           | latest           | new commit       |
| `gitlab-latest-commit-id` | latest           | latest           | new commit       |
| `synced-last-modified`    | 新的lastModified | 当前lastModified | 新的lastModified |
| `conflict-status`         | '0'              | '0'              | '0'              |

### 临时文件

| 操作           | temp/{file} | temp/{file}.diff |
| -------------- | ----------- | ---------------- |
| 使用GitLab版本 | **删除** ✅  | **删除** ✅       |
| 忽略冲突       | **删除** ✅  | **删除** ✅       |
| 手动合并       | 用户决定    | 用户决定         |

### 前端需要

| 操作           | 需要重新加载文档？ | 需要刷新元数据？ |
| -------------- | ------------------ | ---------------- |
| 使用GitLab版本 | **是** ✅           | 是               |
| 忽略冲突       | **否** ❌           | 是（仅元数据）   |
| 手动合并       | **是** ✅           | 是               |

## 💡 实际场景示例

### 场景1：文档错误修复

**情况**：
- GitLab：修复了文档中的技术错误
- OSS：添加了一些格式调整

**建议**：使用GitLab版本，然后重新做格式调整

**操作**：
```typescript
await useGitLabVersion(ossPath, projectCode)
// 然后在新版本上重新调整格式
```

---

### 场景2：内容重组

**情况**：
- GitLab：修改了一个链接
- OSS：重新组织了整个文档结构

**建议**：忽略GitLab更新，稍后手动添加链接修改

**操作**：
```typescript
await ignoreConflict(ossPath, projectCode)
// 手动修改链接
// 再提交到GitLab
await submitToGitLab(ossPath, projectCode, '更新链接')
```

---

### 场景3：同时修改同一段落

**情况**：
- GitLab：更新了API参数说明
- OSS：添加了使用示例

**建议**：手动合并，保留双方的修改

**操作**：
```typescript
// 1. 查看diff
const diff = await viewDiff(ossPath)

// 2. 手动编辑，合并双方修改

// 3. 提交到GitLab
await submitToGitLab(ossPath, projectCode, '合并API文档更新')
```

## ⚙️ 技术实现对比

### 使用GitLab版本

```typescript
// 后端操作
1. 获取 temp/{file}（GitLab版本）
2. 复制到主文件位置（覆盖OSS）
3. 更新元数据
4. 删除temp文件

// 前端需要
1. 调用接口
2. 等待响应
3. 重新加载文档内容 ← 关键
4. 隐藏冲突提示
```

### 忽略冲突

```typescript
// 后端操作
1. 不修改OSS文件
2. 更新元数据（commit-id设为latest）
3. 删除temp文件

// 前端需要
1. 调用接口
2. 等待响应
3. 隐藏冲突提示
4. 文档内容无需重载 ← 关键
```

### 手动合并

```typescript
// 前端操作
1. 查看diff
2. 用户手动编辑OSS文档
3. 保存OSS文档
4. 调用提交接口

// 后端操作
1. 读取OSS文件
2. 提交到GitLab
3. 更新元数据
4. 可选：删除temp文件
```

## 🔔 注意事项

### 使用GitLab版本时

⚠️ **不可逆操作**
- OSS的修改会被完全覆盖
- 建议先下载OSS版本备份

⚠️ **需要重新加载**
- 前端必须重新加载文档内容
- 否则显示的还是旧内容

### 忽略冲突时

⚠️ **不是永久忽略**
- 只是标记当前冲突已处理
- GitLab再有新提交会重新检测

⚠️ **可能需要后续处理**
- 建议记录忽略的原因
- 定期审查被忽略的更新

### 手动合并时

⚠️ **需要理解diff**
- 用户需要能看懂diff格式
- 建议提供可视化diff工具

⚠️ **可能出错**
- 手动合并可能遗漏内容
- 建议提供合并指引
