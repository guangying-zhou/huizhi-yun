# 角色权限系统升级方案 v1

## 1. 背景

当前平台权限体系已经具备 `应用 / 资源 / 角色 / 权限` 的基础能力，但随着 `aims` 等业务系统接入，现有模型开始暴露几个问题：

- 角色同时承载了“身份、岗位、职责、范围”多种语义
- 相同授权组合需要重复配置，缺少批量复用机制
- 平台级权限与业务系统内上下文权限边界不清
- 数据范围没有统一模型，容易在各模块内各做各的
- 前端菜单权限、页面权限、接口权限、数据权限之间缺少统一闭环

本次升级目标不是简单补几个角色，而是形成一套可持续扩展的统一授权框架。

## 2. 目标

本次升级目标如下：

- 建立统一的角色权限模型，适用于 `account`、`aims` 及后续模块
- 分离“角色定义”和“批量授权”，引入权限模板
- 将“功能权限”和“数据范围”拆成两个独立维度
- 明确 `account` 与各业务模块的职责边界
- 保证运行时只依赖一套有效授权结果，避免多套语义并存
- 支持逐步迁移，不影响现网角色与权限使用

## 3. 设计原则

本方案遵循以下原则：

- 单一运行时语义：运行时只判断“用户有效权限”，不直接判断模板
- 平台统一建模：资源、角色、模板、范围规则由平台统一定义
- 业务模块解释上下文：项目成员、参与者、负责人等业务关系由模块自行解释
- 角色表达职责，不表达过多范围组合
- 模板负责批量授予，不直接承载原始权限点
- 数据范围独立建模，不塞进角色名或权限名中

## 4. 总体模型

统一授权体系分为五层：

1. `资源权限`
   例如：
   - `account:profile:view`
   - `aims:projects:edit`
   - `codocs:documents:view`

2. `角色`
   角色是权限的承载体，负责定义“能做什么”。

3. `权限模板`
   模板是一组角色组合，用于批量授予。

4. `分配规则`
   模板或角色可以绑定到用户、部门、岗位等主体。

5. `用户有效权限`
   系统在运行时计算用户最终拥有的角色、权限和范围规则。

## 5. 角色分类

建议将角色统一分为四类。

### 5.1 system 角色

表示平台最高级管理角色，例如：

- `super_admin`
- `org_admin`
- `app_admin`

用于少量高权限治理场景。

### 5.2 base 角色

表示基础身份，例如：

- `internal_user`
- `guest`

这类角色只承载最基础的平台能力，如登录、个人资料、我的应用等。

### 5.3 job 角色

表示岗位属性，例如：

- `job:developer`
- `job:sales`
- `job:hr`

这类角色主要表达“这个人是什么岗位”，不建议直接挂大量业务系统权限。

### 5.4 app 角色

表示在某个应用中的职责，例如：

- `aims:member`
- `aims:pm`
- `aims:admin`
- `account:user_admin`
- `codocs:editor`

这类角色是应用级权限的主要承载体。

## 6. 权限模板

为解决大批量重复授权问题，引入权限模板机制。

### 6.1 模板定位

模板不是新的运行时权限层，而是“角色组合包”。

即：

- 角色负责定义权限
- 模板负责批量授予角色

### 6.2 模板示例

例如：

- `tpl:rd_staff`
  - `internal_user`
  - `aims:member`
  - `codocs:editor`

- `tpl:pm_standard`
  - `internal_user`
  - `aims:pm`
  - `codocs:editor`
  - `workflow:approver`

### 6.3 模板绑定对象

模板可绑定给：

- 用户
- 部门
- 岗位

建议优先顺序为：

- 岗位默认模板
- 部门补充模板
- 用户例外模板

### 6.4 模板原则

模板不直接挂权限点，只挂角色。运行时不判断模板，只判断模板展开后的有效角色和权限。

## 7. 功能权限模型

功能权限继续采用现有 `app + resource + action` 形式。

建议标准化为：

- `app_code`
- `resource_code`
- `action`

例如：

- `aims:projects:view`
- `aims:projects:edit`
- `aims:projects:admin`

动作继承关系可保持：

- `admin` 隐含 `edit` 和 `view`
- `edit` 隐含 `view`

但建议由服务端统一实现继承逻辑，而不是只靠客户端解释。

## 8. 数据范围模型

数据范围必须纳入统一方案。本次建议将数据范围作为与功能权限并列的独立维度。

### 8.1 数据范围定义

数据范围回答的问题是：

- 用户能看哪些数据
- 用户能编辑哪些数据
- 用户能审批哪些数据

它不等于功能权限，也不等于角色名称。

### 8.2 通用范围规则

第一版建议支持以下通用范围：

- `all`
- `self`
- `department`
- `managed_departments`
- `creator`
- `owner`
- `member`
- `participant`

### 8.3 通用表达结构

建议使用统一结构：

- `scope_type`
  - `all`
  - `org`
  - `relation`
  - `attribute`

- `scope_value`
  例如：
  - `org:department`
  - `org:managed_departments`
  - `relation:member`
  - `relation:owner`

### 8.4 设计原则

平台统一定义范围规则格式，但不直接解释业务关系含义。具体如何判断 `member`、`owner`、`participant`，由业务模块实现。

## 9. account 与业务模块边界

这是整套方案最关键的边界。

### 9.1 account 负责

- 应用注册与应用可见性
- 资源清单同步
- 角色定义
- 模板定义
- 权限点与范围规则绑定
- 用户有效角色与权限汇总
- 统一审计与授权追踪

### 9.2 业务模块负责

- 业务关系解释
- 上下文权限判断
- 数据查询过滤
- 对象级授权控制

## 10. aims 的接入方式

`aims` 作为首个重点接入模块，建议采用“两段式授权”。

### 10.1 平台级授权

由 `account` 判断：

- 用户是否可访问 `aims`
- 用户是否拥有 `aims` 内某类功能权限
- 用户对 `aims` 资源拥有哪些范围规则

例如：

- `aims:projects:view + relation:member`
- `aims:projects:edit + relation:manager`

### 10.2 业务级授权

由 `aims` 自己判断：

- 当前用户是否为该项目成员
- 是否为项目经理
- 是否为负责人/参与者/审批人
- 当前对象是否落在授权范围内

也就是：

- `account` 决定“有没有资格”
- `aims` 决定“对这个项目/任务有没有权”

## 11. 应用可见性与应用权限

应用权限还应拆成两层：

### 11.1 应用可见性

用户能否看到、进入某应用。继续由 `applications + app_access_rules` 管理。

### 11.2 应用功能权限

进入应用后可访问哪些页面、接口、操作。由 `resource + action + role + scope` 管理。

两者不能混为一谈。

## 12. 运行时授权链路

建议统一成三段判断：

1. 应用可见性  
   用户是否可进入该应用

2. 功能权限  
   用户是否对该资源拥有相应动作权限

3. 数据范围与业务上下文  
   当前对象是否在允许范围内

统一表达为：

`Allow = AppAccess && Permission && ScopeMatch && ContextMatch`

## 13. 数据模型建议

建议在现有模型上做增量扩展。

### 13.1 保留

- `applications`
- `resources`
- `roles`
- `role_permissions`
- `user_roles`
- `app_access_rules`

### 13.2 建议新增

- `permission_templates`  
  模板定义

- `template_roles`  
  模板与角色关系

- `template_bindings`  
  模板绑定关系，包含：
  - `subject_type`：`user | department | job`
  - `subject_id`
  - `template_id`
  - `status`
  - `priority`

- `role_scopes`  
  角色与范围规则关系，表示某角色对某资源动作对应哪些范围

- `effective_user_roles`  
  可选缓存，用于运行时加速

- `effective_user_permissions`  
  可选缓存，用于运行时查询和审计快照

### 13.3 roles 扩展字段

建议给 `roles` 增加：

- `role_type`
- `app_code`
- `is_assignable`
- `is_template_only` 可选

## 14. 迁移策略

建议采用双轨迁移，避免一次性切换。

### 14.1 阶段一：盘点现状

梳理当前角色，分为：

- 基础身份角色
- 岗位角色
- 应用职责角色
- 混合角色
- 待废弃角色

### 14.2 阶段二：建立新模型

新增模板与范围规则表，不影响现有运行逻辑。

### 14.3 阶段三：建立映射

例如将 `user:developer` 重构为：

- `job:developer`
- `tpl:rd_staff`

模板中包含需要的基础角色与应用职责角色。

### 14.4 阶段四：双轨验证

同时输出：

- 旧模型授权结果
- 新模型展开后的授权结果

做差异对比，确认无误后切换。

### 14.5 阶段五：切换运行时

逐步切换：

- `account` API
- 前端菜单过滤
- 页面路由守卫
- 服务端接口权限校验
- 业务数据过滤

## 15. 支撑能力

为了让新模型可运营，建议补齐以下能力：

- 模板展开预览
- 授权影响面预览
- 用户有效权限查看
- 角色/模板变更审计
- 例外授权标记
- 自动同步与冻结机制
- 差异比对工具

## 16. 第一版落地范围

建议第一版只实现最关键能力：

- 角色分类
- 权限模板
- 通用数据范围结构
- 有效权限汇总接口
- `aims` 首个接入
- 服务端统一授权入口

暂不建议第一版就做复杂属性规则引擎和全量缓存体系。

## 17. 风险

主要风险如下：

- 旧角色语义混杂，拆分时可能引起授权变化
- 模板与人工直授并存时，容易出现例外逻辑混乱
- 数据范围若解释不一致，会导致模块间语义漂移
- 前端权限与服务端权限切换不同步，可能出现页面可见但接口失败

## 18. 回滚策略

- 新模型先增量上线，不直接删除旧逻辑
- 运行时保留旧判断开关
- 每个模块单独切换
- 出现差异时可快速回退到旧授权链路

## 19. 建议的下一步输出

建议继续形成三份配套文档：

1. 《角色与模板字典》  
   明确每个角色、模板的用途和边界

2. 《数据模型与 API 草案》  
   明确表结构与接口调整方案

3. 《AIMS 接入与授权落地方案》  
   明确 `aims` 如何解释 scope 和收口服务端权限
